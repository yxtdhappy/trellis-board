# 个人版执行增强

## Goal

把 Trellis Board 从“展示任务和推导阶段”增强为个人执行控制面，让用户能够快速判断现在该做什么、哪些任务被阻塞，以及任务为什么变慢。

个人版采用轻量 Kanban 和短迭代，不引入完整 Scrum 流程。

## Background

- SQLite 持久化迁移已经完成，Trellis 任务文件继续作为任务、状态、负责人和流程产物的唯一事实来源。
- 当前看板已经支持跨项目扫描、阶段推导、父子任务归组，以及按项目、负责人和关键词筛选。
- 当前缺少截止日期、里程碑、标签、保存视图、任务依赖、阻断状态和可信的操作时间线。
- 用户已确认“推荐任务 → 注意力队列 → 轻量 Kanban + 流动信号”的首屏信息层级，静态原型位于 `.audit/personal-execution-mockup/`。
- 历史指标只接受从事件记录启用后开始累计；旧任务明确显示“历史缺失”，不使用文件修改时间回填或推测。

## Task Map

| 子任务 | 交付范围 | 前置依赖 | 独立验收重点 |
| --- | --- | --- | --- |
| `10-30-personal-plan-attention` | 计划字段、组合注意力视图、快速编辑、可信事件基线 | 无 | 字段重启后保留；视图叠加筛选稳定；事件只记录启用后的真实操作与观察 |
| `10-30-personal-risk-flow` | 依赖阻断、解除阻断队列、软 WIP、DoR/DoD 缺口 | 计划与注意力子任务完成 | 阻断关系可校验、可解除；风险只提醒不阻止操作 |
| `10-30-personal-history-insights` | 操作历史、最近一次可逆操作撤销、执行指标 | 前两个子任务完成 | 历史可追溯；撤销可读回；指标可由事件重建且明确缺失范围 |

父任务保留本源需求、跨切片验收和最终集成检查，不直接承担某一个切片的实现。

## Requirements

### Slice 1：计划与注意力

- R1-1 任务可维护截止日期、里程碑和标签；这些看板扩展字段只写入 Board SQLite，不写回目标仓库的 `task.json`。
- R1-2 用户可从任务列表或任务详情快速修改上述计划字段，成功后必须从 API 重新读回。
- R1-3 提供 P0/P1、临近截止、长时间未动、实现中、检查中等内置注意力视图，并允许组合优先级、阶段、标签、截止窗口和停滞天数；阻断状态条件在风险切片可用后扩展。
- R1-4 自定义筛选可命名、保存、再次使用和删除；内置视图始终可用。
- R1-5 从事件功能启用时开始记录计划字段、人工阶段等用户操作，并记录扫描首次观察到的阶段变化；事件包含时间、来源、操作者和前后值。
- R1-6 对启用前没有事件的任务显示“历史缺失”；首次纳管时只建立追踪起点，不虚构此前阶段时间。

### Slice 2：风险与流动

- R2-1 任务支持 `blocked by` 与 `blocks` 关系，并记录阻断原因、创建时间和解除时间。
- R2-2 阻断关系必须与父子任务关系分离；拒绝缺失任务、自引用、重复关系和循环依赖。
- R2-3 提供“当前被阻断”和“解除阻断后可推进”队列，阻断时长从可信事件计算。
- R2-4 实现中任务支持软性 WIP 上限提醒；达到上限时仍允许用户继续操作。
- R2-5 根据现有流程证据提示 DoR 或 DoD 缺失项，只提示，不阻止启动、检查或归档。
- R2-6 依赖创建、解除和循环校验失败均不得留下部分写入。

### Slice 3：追溯与复盘

- R3-1 任务详情展示按时间倒序的可信事件和操作历史，区分人工操作、扫描观察和系统追踪起点。
- R3-2 用户可以撤销当前任务最近一次尚未撤销的可逆操作；撤销本身追加新事件，不删除原始历史。
- R3-3 根据事件计算追踪后的 Lead Time、Cycle Time、阶段停留、阶段回流次数和阻断时间占比。
- R3-4 指标必须标明 `missing`、`partial` 或 `tracked` 完整度；证据不足时返回空值和缺失原因，不输出猜测值。
- R3-5 任务从活动目录归档后，历史、计划字段和指标仍通过稳定任务身份保持关联。

## Cross-Slice Constraints

- 每个 Slice 必须能够独立检查、提交和归档；后序 Slice 不得要求前序 Slice 范围外的功能同时上线。
- Trellis 的 `task.json`、状态、负责人、父子关系、阶段证据和归档位置仍是流程事实来源；Board SQLite 只保存扩展字段、依赖、视图和事件。
- 现有扫描、筛选、阶段推导、人工检查点、项目管理和任务详情行为不得回归。
- 所有新增写操作必须在任何持久化前完成输入、白名单、任务路径和领域校验；多行写入使用 SQLite 事务。
- 浏览器输入不得直接成为任意文件路径；API 通过 `projectId + taskPath` 解析当前任务，再在服务端使用稳定身份落库。
- 所有新增 UI 必须沿用现有 `state + renderX/bindX` 模式，动态文本经过 `safe()`，并支持键盘操作、可见焦点和 `prefers-reduced-motion`。
- 指标只从事件启用后的观测计算；文件修改时间、当前最终阶段和归档位置不得被用来补造历史时点。

## Acceptance Criteria

- [ ] Slice 1：计划字段写入 SQLite，服务重启后仍可读，且目标仓库 `task.json` 内容不变。
- [ ] Slice 1：优先级、阶段、标签、截止和停滞条件可组合筛选，保存后重开页面仍可使用。
- [ ] Slice 1：任务列表和详情均可进入计划字段编辑，失败时保留输入并显示中文错误。
- [ ] Slice 1：用户操作和扫描观察生成带时间、来源、操作者及前后值的事件，不产生伪造历史。
- [ ] Slice 2：能区分阻断任务与可推进任务，并拒绝缺失、自引用、重复和循环依赖。
- [ ] Slice 2：解除阻断后任务进入待推进队列，阻断时长由创建和解除事件计算。
- [ ] Slice 2：WIP、DoR 和 DoD 只显示提醒，不改变原有操作可用性。
- [ ] Slice 3：历史时间线包含原始操作和对应撤销，刷新后顺序与内容稳定。
- [ ] Slice 3：最近一次可逆操作撤销后，计划字段、人工阶段或依赖状态通过 API 读回为撤销前值。
- [ ] Slice 3：同一事件流可重复计算相同指标；证据不足的任务返回缺失状态而不是数字。
- [ ] 三个 Slice 各自通过相关 Node 测试、JavaScript 语法检查和真实页面端到端验证。
- [ ] 最终集成检查证明现有项目扫描、筛选、阶段、团队、归档和任务创建行为未回归。

## Out of Scope

- 完整 Scrum 角色、Sprint 仪式、故事点和团队速度。
- 燃尽图、复杂甘特图和任意拖拽跳阶段。
- 团队认证、RBAC、远程仓库 Agent 和多实例部署。
- Git、分支、PR、MR 和 CI 状态联动。
- 评论、决策记录、每日摘要和通知推送。
- 回填或推测事件功能启用前的周期、停留、回流和阻断历史。

## Product Decisions

- 个人版保持轻量 Kanban，不引入额外流程阶段。
- 阻断关系独立于父子任务关系建模。
- 历史指标只从事件功能启用后累计，旧数据明确标记缺失。
- 首屏围绕“下一次动作”组织，数字必须解释下一步决策，不做纯装饰性仪表盘。
