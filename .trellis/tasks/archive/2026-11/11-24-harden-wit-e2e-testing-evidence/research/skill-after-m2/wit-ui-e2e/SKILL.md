# WIT 页面端到端验证（UI E2E）

> 本技能只负责浏览器阶段：页面、交互、前端渲染、Network、Console、截图。
> 接口契约、本机后端、真实落库和后端日志由 `wit-api-e2e` 负责；需要这些证据时回到接口阶段，
> 不在本技能里复制代理、日志读取器或接口脚本。

## 铁律

1. **基线 → 一次操作 → 操作后快照 → 判定**。只截一张“页面看起来正常”的图不算通过；必须有一次操作前后的对照，并核对 Network/Console。
2. **不预设项目**：页面地址、登录方式、路由、选择器、前后端版本全部先求证（问用户、看 Network、看页面实际 DOM）。不确定就问，不猜。
3. **先确认前后端最新代码分别在哪里运行**：环境前端 + 本地后端、前后端都在本地、前后端都已部署，三种场景的测法不同；不确定时先查构建产物/提交号/接口行为，不要直接去环境里点。
4. **只读优先**：默认只做浏览、点击、输入等可回退操作。提交、删除、审批、发布等写操作必须落在用户已授权的测试范围内，否则先取得确认。
5. **凭据只由用户提供，不从浏览器存储/抓包自行提取**：不读取、不复制、不打印 token、Cookie、localStorage/sessionStorage 中的凭据；登录态由用户当前浏览器提供。凭据禁止出现在报告、截图说明、Console 摘录和提交内容里。
6. **失败先分类**：选择器/测试脚本问题、环境/链路问题、前端代码缺陷、后端接口缺陷。分类清楚再决定是否改代码；后端缺陷回到 `wit-api-e2e` 复现。
7. **报告先落盘，再宣布完成**：结论写入项目约定的报告文件（任务目录下的 `research/`、`docs/` 或项目指定位置）；只在对话里汇总不算完成。

## 0. 阶段边界

| 当前任务 | 使用技能 | 说明 |
| --- | --- | --- |
| 浏览器页面、点击/输入、前端渲染、Console/Network、截图 | `wit-ui-e2e` | 本技能 |
| 纯接口/API、本机后端、契约/持久化/副作用 | `wit-api-e2e` | 不在本技能里发接口用例 |
| UI 阶段需要本地后端/代理/后端日志 | 先 `wit-api-e2e` 搭链路 | 搭好后拿 base URL/账号/数据前缀回来做页面 |
| 接口契约尚未验证就要做页面 E2E | 先 `wit-api-e2e` | 契约未验证，页面失败无法归因 |
| 只改后端、页面来自环境 | `wit-api-e2e` 起本地后端 + 代理 | 本技能只负责在页面上操作和核对界面 |

## 1. 前置检查

- **前后端版本**：先确认页面来自哪个前端构建、后端 latest 代码跑在哪里；只改后端时，页面仍可来自环境，但请求必须转发到本机后端（由接口阶段搭好并验证）。
- **入口可达**：页面 URL、登录态、目标路由；Network 里能看到页面自己的请求。
- **基线状态**：打开目标页，记录 URL、视口、页面标题、关键区域文本/选择器数量、Console 是否有既有报错、Network 基线；截图保存到证据目录。
- **选择器**：优先用稳定的 `data-testid`/`role`/可见文本；避免依赖随机 class、绝对 XPath、会随数据变化的序号。
- **测试数据**：需要新建数据时先用可识别前缀命名，确认清理方式；写操作先取得授权。
- **报告路径已定**：先确定报告文件落点与截图/证据目录，避免测完再补。

## 2. 三种运行场景

先判断“环境上的前端是否已含最新前端改动”和“环境上的后端是否已含最新后端改动”：

1. **只改了后端（最常见）**：直接去对应环境登录前端、照常操作；浏览器侧转发把发往后端的请求转到本机服务。动手前先用一次请求 + 本地后端日志确认转发生效。本技能只做页面操作和界面核对；本地链路是否生效由 `wit-api-e2e` 先验证。
2. **前后端都改了、且环境上两个都没发**：前端也要在本地启动最新代码，并起最小代理把前端请求转到本地后端，同时处理网关/微前端路径前缀（如 `/xxx-web`、`/appgw`）。代理和路径前缀由 `wit-api-e2e` 搭好并验证，本技能只访问前端 dev server 地址。
3. **前后端都已完成并部署到对应环境**：直接到该环境做端到端测试，本地不起服务。

## 3. 单步闭环

每一步都执行：

1. **基线**：记录 URL、视口、关键选择器/文本、Console 现状、Network 现状、截图。
2. **一次操作**：只点一个按钮/填一个字段/走一个路由；不要连点多个再一起看结果。
3. **操作后快照**：记录 DOM/文本变化、目标元素状态、Network 中对应请求的方法/URL/状态码/响应摘要、Console 新增错误、截图。
4. **判定**：页面是否符合预期；对应请求是否发出、是否成功；Console 是否有新增错误；失败属于哪一类。
5. 把「操作 → 页面变化 → Network/Console 结论」记成一行，最后汇总成报告。

## 4. 用例设计

| 类型 | 作用 | 例子 |
| --- | --- | --- |
| 正向 | 证明页面可用 | 打开列表、点击查询、表单提交后出现目标数据 |
| 反向 | 证明失败可控 | 必填为空、非法格式、无权限 → 明确提示、不白屏、不吞错 |
| 回归 | 证明没破坏别处 | 相邻页面、分页、弹窗关闭、返回后状态 |
| 对照 | 校准预期 | 参考产品、旧版本、接口返回与页面展示对比 |

验收标准要可判定：目标文本、元素数量、URL/路由、Network 状态码、Console 无新增错误；避免“看起来正常”。

每个用例标注验证层级：

| 层级 | 通过条件 | 不能替代 |
| --- | --- | --- |
| 页面级 | DOM/文本/样式/路由符合预期 | 不能证明接口成功或已落库 |
| 网络级 | 对应请求发出，状态码/响应符合预期 | 不能证明后端业务成功 |
| 持久化级 | 页面回读/刷新后仍是新值，且接口阶段有写后读回 | UI 单独不能证明落库 |

页面刷新后数据消失、列表不更新、Console 报错，都按失败或未验证处理，不能只凭操作瞬间的提示判定成功。

## 5. 证据采集（Chrome DevTools MCP）

优先使用 `mcp__chrome-devtools__*`，复用用户当前浏览器窗口、标签页和登录会话；不要为了绕过登录态另开隔离浏览器。

- 打开/切换页面：记录最终 URL、标题、视口；需要时开新标签，避免污染用户当前页面。
- 点击/输入：用稳定选择器；操作前确认元素可见、可点击，操作后等待目标状态，不用固定 `sleep` 代替判定。
- DOM/文本：读取目标区域 `innerText`/`textContent` 或属性值，记录操作前后差异。
- Network：记录对应请求的方法、URL（脱敏 query）、状态码、响应摘要；不要把完整响应体或凭据写进报告。
- Console：记录操作前后的错误/警告差异；既有噪音与本次新增分开。
- 截图：基线和操作后各一张，文件名带用例编号；截图说明只写页面状态，不写凭据。

MCP 不可用时记录阻塞原因，不静默改用其他浏览器或无会话的新 profile。

## 6. 失败处理

- **选择器/脚本问题**：元素不存在、被遮挡、动画未结束、iframe/shadow DOM 未定位 → 修正选择器/等待条件后重跑该步；不要把它记成产品缺陷。
- **环境/链路问题**：页面打不开、登录态失效、请求打到旧后端、前端缓存旧数据 → 先修链路或清缓存，再重跑；请求是否到本机后端由接口阶段证据确认。
- **前端缺陷**：页面渲染错误、交互无响应、Console 新增异常、Network 成功但页面不更新 → 记录复现步骤、DOM/Console/Network 证据，交开发修复后用同一路径复测。
- **后端/接口缺陷**：Network 显示 4xx/5xx 或业务失败 → 回到 `wit-api-e2e` 用接口用例复现并抓后端日志，不在 UI 层猜后端原因。
- **前端缓存**：列表/对象树可能缓存旧数据；重新加载页面或走到对应刷新入口后再判定。

## 7. 测试数据与环境

- 探针数据用可识别前缀命名，本轮结束即清理；清理可以通过页面操作，也可以交给接口阶段按前缀删除，但要在报告中写明方式。
- 多副本/集群环境：页面可能连到不同副本；出现“刚建的数据看不到”时先确认副本/路由，不直接判产品缺陷。
- 有列表条数上限的页面：把探针数据放在可见范围内（例如按排序靠前命名），否则会误判为“数据不存在”。

## 8. 收尾

1. **先写报告**：按 [references/report-template.md](references/report-template.md) 生成报告文件，包含拓扑、证据表、结论、未验证项、清理记录；未落盘不得宣布 UI E2E 完成。
2. 清理探针数据并校验；证据截图/Console 摘录保留到任务提交/归档。
3. 把验收结论逐条回写；没有页面证据的项标为未验证，不勾选。
4. 确认报告、截图和 Console 摘录中无 token、Cookie、密码等凭据。
5. 需要后端日志/落库证据时，把请求信息交给 `wit-api-e2e` 补证，不在 UI 报告里伪造日志。
