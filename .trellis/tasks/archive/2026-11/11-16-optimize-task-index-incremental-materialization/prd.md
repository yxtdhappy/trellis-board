# 优化团队任务索引增量物化性能

## Goal

消除 Team 服务在正常运行时因一个任务变化而对整个任务空间重新落盘、递归扫描、解析和重建索引的问题，同时保证已提交 revision 不丢失、旧投影不覆盖新 revision、跨任务关系完整重算、失败时保留上一份一致 Board。

## Background

当前 Team 每次快照 revision 提交后都会触发 taskSpace 投影。投影会读取全部未删除文件、在系统临时目录重新写入整棵 `.trellis/tasks`、调用 `scanRepository()` 扫描全部任务，并全量删除、重插 `sync_task_index`。

已观察到的实际现象：

- 本地端已经正确执行增量扫描：一次新任务只解析 `1` 个目录、复用 `108` 个目录，本地扫描约 `2.849s`。
- 服务端提交 revision 后，Board 分别约 `40s` 和 `93s` 后才看到新任务。
- 当前运行库中仅一个 taskSpace 就有 `330` 个任务目录、`1615` 个活动文件和约 `10.58M` 字符正文；另一个 taskSpace 有 `147` 个任务目录和 `1615` 个活动文件。
- 使用相同快照重放服务端全量物化，开发机上单次约 `5.69s`，连续重放时出现约 `11.3s`、`13.2s`、`16.3s`；同步提交的多个 revision 还会排队放大端到端延迟。

因此问题不在本地 watcher，也不在“必须保留旧 revision 才不丢数据”。文件正文已经在快照事务中提交；需要优化的是从已提交快照生成派生索引的过程。

## Requirements

### R1 增量物化

- 服务进程已有可信投影基线时，单任务 revision 只读取并扫描发生变化的完整任务目录。
- 未变化任务不得重新读取正文、不得重新解析 `task.json`、不得为了扫描而重新写入临时目录。
- 首版允许服务重启、缓存缺失或基线不可信时执行一次全量重建；不得为了跨重启增量而引入持久化 schema。

### R2 完整性与一致性

- 每次增量结果必须包含当前快照中的全部有效任务；`sync_task_index` 不得残留已删除任务，也不得遗漏新增、移动或归档任务。
- 单任务变化后仍必须基于全部当前任务重算父子关系、分组、父任务阶段继承、执行身份冲突、标签、依赖、WIP、风险和手工阶段投影。
- 增量 Board 必须与对同一快照执行全量重建得到的任务集合、任务身份、阶段、关系、筛选字段和风险摘要一致。

### R3 revision 与并发安全

- 只有任务空间当前最新 revision 的投影可以提交；扫描期间出现新 revision 时，旧结果必须丢弃，不能写索引、缓存或 `indexed_revision`。
- 提交事务内必须再次校验 revision，堵住“扫描结束后、事务开始前又有 revision 提交”的竞态窗口。
- 多个快速 revision 必须合并为尽可能少的后续投影；同一 taskSpace 不得并发物化。
- 已提交文件、CAS、冲突、删除墓碑、归档移动和审计语义保持不变。
- 丢弃旧 revision 的派生投影不等于丢弃文件行；如果后续 revision 合法覆盖同一路径，当前快照以后续内容为准，但并发覆盖必须由 CAS/冲突流程拒绝。

### R4 数据库写入控制

- 正常增量投影不得固定执行 taskSpace 全量 `DELETE` 后再全量 `INSERT`。
- 只更新新增或字段发生变化的索引行，只重建受影响任务的标签，并删除已不存在的任务索引。
- Board 缓存、索引、任务分配投影和 `indexed_revision` 必须在同一事务中一起成功或一起回滚。

### R5 失败关闭与回退

- 缓存不完整、目录指纹不一致、worker 返回不完整、任务身份无法确认或事务失败时，不得发布部分 Board。
- 基线不可信时必须自动回退全量重建；全量重建也失败时保留上一份一致 Board，按现有退避策略重试。
- 投影失败不得删除或修改 `sync_task_space_file` 中已提交的任务正文。

### R6 可观测性

- 结构化记录每次投影的模式（全量或增量）、排队时间、目标 revision、变化目录数、实际扫描任务数、复用任务数、读取正文行数、worker 耗时、关系投影耗时、数据库替换耗时和总耗时。
- 指标不得记录任务正文、绝对本地仓库路径、Agent 凭证或冲突正文。

### R7 手工投影输入

- 人工阶段等不改变快照 revision 的输入发生变化后，任务详情和 Board 必须使用最新投影，不能长期复用旧内存状态。
- 无证据时不得把人工阶段、计划字段或执行扩展数据写回任务快照文件。

## Constraints

- 不修改 Agent 上传协议、revision 生成规则、文件级 CAS、冲突处理、删除墓碑或归档协议。
- Team 服务端仍只能读取 `sync_task_space_file`，不得读取项目 Git、workspace、scripts、spec、config 或 workflow。
- 不引入服务端 Git/Python 子进程，不引入多实例共享缓存，不建设完整任务历史版本浏览器。
- 保持现有 HTTP、SSE、数据库 schema v12 和可回滚兼容性；本任务只改变派生索引实现和进程内缓存。
- 服务端唯一业务事实源仍是已提交快照；内存投影只能是可丢弃的派生缓存。

## Acceptance Criteria

- [ ] 已有可信基线时，修改一个任务只扫描该任务目录；指标显示 `changedTaskCount=1`、`scannedTaskCount=1`，其余任务复用且未读取正文。
- [ ] 健康任务空间的单任务 revision 不再执行“全部快照写入临时目录”和“全部任务重新解析”。
- [ ] 单任务新增、修改、删除、活动目录到归档目录移动后，索引任务集合与有效 `task.json` 目录集合完全一致。
- [ ] 修改父子任务、`children` 或 `meta.*Task` 引用后，未直接变化的父任务和子任务也得到最新分组与阶段继承结果。
- [ ] 重复任务 ID 的执行身份冲突仍在全任务范围内识别，不会因增量扫描只看到局部任务而漏报。
- [ ] 对同一批新增、修改、删除和归档操作，增量 Board 与全量重建 Board 的任务集合、任务身份、阶段、关系字段和风险摘要一致。
- [ ] 扫描期间提交新 revision 时，旧结果返回 superseded，不更新索引、缓存或 `indexed_revision`；下一轮使用最新快照完整收敛。
- [ ] 提交事务开始后若 revision 再次变化，事务整体回滚，不出现缓存是新 revision、索引是旧 revision 的混合状态。
- [ ] 构造 revision 412 后紧接着 413 的场景，确认 412 不会覆盖 413；最终文件和附件完整，合法更新不会因索引优化被额外删除。
- [ ] 连续多个 revision 只保留一个在途物化和一次最新待处理物化，不按 revision 数逐一执行全量任务空间扫描。
- [ ] 服务重启或内存基线缺失时自动全量重建一次；重建结果正确，随后恢复增量模式。
- [ ] 人工阶段修改后无需等待新的 Agent 上传即可在任务详情和 Board 中生效。
- [ ] 投影失败时最后一个成功 Board 保持可读，`sync_task_space_file`、冲突、审计和快照 revision 均不丢数据。
- [ ] 在开发机当前规模夹具（至少 `300` 个任务目录、`1500` 个活动文件）上连续执行至少 `20` 次单任务 warm 更新，服务端投影 P95 不高于 `3s`。
- [ ] 真实 HTTP/E2E 中，普通单任务更新从 revision 提交到 Board API 可见的 P95 不高于现有产品目标 `3s`；不得再稳定出现几十秒级等待。
- [ ] 结构化日志能区分 full/incremental/superseded/failed，并能定位耗时主要位于读取、worker、关系投影还是数据库提交。
- [ ] 新增自动化测试覆盖 Node 内置测试、真实 HTTP 和真实服务重启；本任务不涉及前端，不需要执行前端构建。

## Out Of Scope

- 跨服务重启持久化未变化任务正文或完整任务对象。
- 多实例共享任务空间队列、分布式锁或共享 SSE。
- 修改桌面 Agent 的本地增量扫描、上传批次、分支归属或冲突处理。
- 改变任务查询 API、Board 输出形状或数据库 schema。
- 优化任务详情正文体积、Markdown 渲染或前端轮询策略。

## Notes

- “增量”只针对任务快照到派生索引的物化过程；快照上传本身仍按完整任务目录和 CAS 事务处理。
- 选择进程内基线是为了保持本任务最小、可回滚且不升级数据库。若冷启动仍成为生产瓶颈，再另开任务评估持久化投影缓存。
