# 桌面同步残留锁与强制恢复设计

## 1. 边界与状态模型

修复范围集中在 Agent 单实例锁和 Tauri sidecar 生命周期，不改变同步协议、任务快照或
项目接入流程。

桌面端把后台同步明确为以下状态：

| 状态 | 条件 | 托盘动作 |
| --- | --- | --- |
| 运行中 | child 存在且未暂停 | 暂停同步 |
| 已暂停 | 用户主动暂停 | 恢复同步 |
| 重试中 | child 已退出，未超过 5 次退避 | 恢复同步 |
| 待强制恢复 | 重试耗尽 | 恢复同步，并弹出系统模态框 |
| 强制恢复中 | 正在执行 kill、清锁、start 或客户端重启 | 正在强制重启，禁用重复操作 |

托盘不能再只依据 `paused` 判断；`running=false` 时点击必须直接恢复。

## 2. 锁回收

### 2.1 本地锁语义

`agent.lock` 位于当前用户的本地 Agent 根目录，不使用跨机器共享语义。接管时按以下顺序判断：

1. 读取并解析锁 metadata 和 mtime。
2. PID 必须是正整数。
3. `process.kill(pid, 0)` 返回成功或 `EPERM` 时视为锁仍被活进程持有，返回 `LOCKED`。
4. `process.kill(pid, 0)` 明确返回 `ESRCH` 时视为死锁，无论 hostname 和锁年龄均允许回收。
5. 锁文件损坏且未超过陈旧窗口时保守阻塞；超过陈旧窗口后允许回收。

删除死锁前重新读取锁文件，确认 token 和 mtime 没有变化，避免删除另一个进程刚创建的新锁。
hostname 仅作为诊断字段保留，不再决定本地死锁是否等待 24 小时。

### 2.2 PID 复用

自动回收只在 PID 明确不存在时执行。PID 仍存在时即使 metadata 中的 hostname 不一致也不删除，
避免系统复用了 PID 后误删另一个进程的锁。强制恢复由用户明确触发，可在终止所有
`trellis-agent.exe` 后再次校验锁 PID；仍无法确认时报告失败，不删除无法证明已失效的锁。

## 3. 正常重启时序

项目关联成功后的 `restart()` 改为受控重启：

1. 设置 paused=`false`，递增 generation，终止当前 child 进程树。
2. 等待旧 child 退出，并等待 `agent.lock` 被释放；等待窗口建议 5 秒。
3. 旧锁消失或已确认属于旧 child 后启动新 child。
4. 新 child 启动后恢复正常监督和托盘状态更新。

短时等待可吸收 Windows 进程退出延迟，但不对确定性锁冲突进行无限重试。

## 4. 自动重试与模态框

- 保留现有 5 次退避重启，`STABLE_RUN` 仍用于重置重试计数。
- 第 5 次重试失败后进入“待强制恢复”，不再自动拉起 sidecar。
- 每个失败周期只弹一次系统模态框，使用已注册的 `tauri-plugin-dialog`。
- 弹窗标题为“后台同步连续启动失败”，正文包含失败次数和当前错误摘要，按钮为
  `MessageDialogButtons::OkCustom("强制重启同步")`。
- 用户关闭弹窗不改变“待强制恢复”状态，托盘仍显示“恢复同步”。

## 5. 强制重启

### 5.1 单飞控制

`SidecarState` 增加 `force_restarting` 原子标记。弹窗按钮、托盘恢复和菜单事件在进入链路前
先抢占该标记；抢不到时直接忽略重复请求。

### 5.2 Agent 级强制恢复

按顺序执行：

1. 重置暂停和重试计数，更新托盘为“正在强制重启”。
2. 终止当前 child 进程组。
3. Windows 下执行 `taskkill /F /T /IM trellis-agent.exe`，清理历史孤儿进程。
4. 轮询 `tasklist`，最多等待 5 秒确认没有同名 Agent 进程。
5. 如果 `agent.lock` 仍存在，将锁文件改名为 `agent.lock.force-restart-<UTC时间>.bak`。
6. 启动新 Agent。
7. 最多等待 15 秒，确认 lock metadata 的 token 已变化、PID 指向 `trellis-agent.exe` 且连续稳定
   2 秒。这里不要求 runtime 心跳成功，避免网络降级时把仍存活的 Agent 误判为启动失败。
8. 成功后清空失败状态，关闭弹窗，托盘显示“暂停同步”。

锁备份只复制/移动锁文件，不触碰 `config.json`、凭证、事件游标、任务游标、备份目录或任务文件。

### 5.3 客户端重启兜底

Agent 级恢复失败或无法确认新进程存活时：

1. 记录脱敏后的失败原因。
2. 调用 `sidecar::shutdown()` 清理当前进程树。
3. 使用 Tauri `AppHandle::restart()` 重启整个客户端。

客户端重启只允许由本次用户强制重启触发，不能在普通退避重试中自动执行。新客户端启动后仍按
正常 5 次重试和模态框策略工作，避免无限快速重启循环。

## 6. 托盘菜单

- `build_tray()` 保留同一个 `MenuItem` handle，放入可管理状态。
- 新增统一的 `update_sync_menu(app)`，按 state model 调用 `MenuItem::set_text()`。
- 菜单事件不再调用 `toggle_pause()`，而是：
  - `is_running=true`：暂停。
  - `is_running=false`：清除暂停和退避并启动一次。
- sidecar start、exit、pause、resume、force-restart 和 prompt 状态变化后都更新菜单。
- 强制恢复期间菜单显示“正在强制重启”，并临时禁用，避免重入。

## 7. 数据流

```text
项目关联完成 / 登录完成
  -> 有序 restart
  -> 旧 child 退出并释放锁
  -> 新 child start

child 异常退出
  -> 1/2/4/8/16 秒有限退避
  -> 5 次失败
  -> 状态改为“待强制恢复”
  -> 系统模态框 + 托盘“恢复同步”

用户点击“强制重启同步”
  -> kill 全部 Agent
  -> 等待进程退出
  -> 备份残留锁
  -> start
  -> 验证新进程
  -> 失败则 AppHandle::restart()
```

## 8. 兼容与风险

- 锁文件路径、字段和退出码保持不变；旧锁只要 PID 已死亡即可回收。
- `taskkill /IM trellis-agent.exe` 会清理同一用户环境下的历史 Agent 进程，与 NSIS 钩子策略一致；
  该命令只在用户明确点击强制重启时执行。
- 客户端重启会丢失未提交的纯界面输入，这是用户已确认接受的兜底代价。
- 服务端不可达、凭证失效或 sidecar 文件缺失无法被进程重启修复；此时新客户端仍会显示失败入口。
- 新增系统模态框复用现有 dialog 插件，不增加依赖。

## 9. 验证策略

- Node：覆盖 hostname 不一致但 PID 死亡、活 PID、`EPERM`、锁 token 变化和有限重试。
- Rust：覆盖状态到菜单文案映射、强制恢复单飞、锁备份、Agent 存活验证和客户端重启分支的纯逻辑。
- Windows 桌面：真实启动客户端，构造 hostname=`local` 的死 PID 锁，确认首次启动自动回收。
- Windows 桌面：构造持续失败，确认第 5 次后弹窗；点击按钮后 Agent 恢复或客户端重启。

## 10. 回滚

- 锁回收、托盘文案、强制恢复和客户端重启均为进程内行为，不涉及数据迁移。
- 回滚时删除锁备份处理、动态菜单和强制恢复链路即可恢复旧行为；现有配置和任务数据不受影响。
- 已生成在 Agent 目录中的 `agent.lock.force-restart-*.bak` 保留用于诊断，不参与下次启动。
