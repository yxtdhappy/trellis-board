# 提高任务同步批量上限至 1024 文件和 64 MiB

## Goal

将 Team Board 任务快照与实时同步的单批上限统一提高到 1024 个文件、64 MiB，
解除大型任务目录首次接入失败的问题，并确保当前已持久化的 250 文件 pending 批次无需
重新关联、清空游标或删除服务端数据即可自动恢复。

## Background

- 当前 `mdp-backend-service / dev` 的初始同步停在 revision `26`。
- 客户端已持久化 `10-03-e2e-oracle` 的 pending 批次，共 250 个文件、5,648,600 字节。
- 服务端当前单批限制为 64 文件、8 MiB，因此该批次持续返回“团队服务执行失败”。
- 本地项目共有 135 个任务、1518 个可通过同步协议读取的文件；其中三个任务超过 64 文件：
  250、110、67 个。
- 失败不是网络、项目绑定、数据库损坏或 CAS 冲突；服务端在同一 pending 批次上稳定执行
  文件数校验拒绝。

## Requirements

- 任务快照和实时同步使用同一组批量上限：
  - 单批最多 1024 个文件。
  - 单批所有文件解码后的 UTF-8 正文总和最多 64 MiB。
  - 单文件 1 MiB 上限保持不变。
- 64 MiB 是正常文本任务的业务目标，不包含 JSON 包装、路径、摘要和字段名。
- HTTP 运输硬上限为编码后的 JSON 请求体 96 MiB，不按解码后正文重新放宽。请求体超过
  96 MiB 时直接返回 413，即使解码后的文件正文不超过 64 MiB；该限制用于避免 JSON 转义
  最坏膨胀导致的超大内存占用和拒绝服务风险。
- 客户端上传统计、服务端请求校验、实时同步分批和服务端批量校验使用同一来源的常量，避免
  各层上限再次漂移。
- 客户端接收完整快照和单任务目录时，也不得被旧的 16 MiB 响应上限提前截断。
- 超过 1024 文件或 64 MiB 的批次必须整批拒绝并返回可理解的 413，不得写入部分文件或推进
  revision。
- 现有 250 文件 pending 批次必须在服务端升级后使用原 `batchId`、`clientSequence` 和文件内容
  自动重试；不得要求用户重新绑定项目、删除本地 cursor 或清空服务端 taskSpace。
- 文件级 CAS、批次幂等、整任务目录原子性、任务移动原子性、5 批/秒限流和错误处理语义保持不变。
- 1024 文件和 64 MiB 必须贯穿上传、服务端快照拉取、单任务目录拉取和客户端应用链路。
- 本次只调整容量上限，不改变任务文件白名单、UTF-8/LF 规范化、摘要算法、数据库 schema 或
  Agent 协议版本。
- 部署顺序必须支持先升级服务端：新服务端继续接受旧客户端当前发送的 250 文件批次；再发布
  包含新常量和更大响应上限的新客户端。
- 若部署环境经过反向代理，必须确认代理请求体限制不低于传输层上限；该环境检查不能替代程序
  自身的业务上限校验。

## Acceptance Criteria

- [x] 共享任务快照工具在恰好 1024 个文件时通过，在 1025 个文件时拒绝。
- [x] 共享任务快照工具在正文总和恰好 64 MiB 时通过，超过 64 MiB 时拒绝。
- [x] 客户端实时同步按 1024 文件和 64 MiB 分批，并向服务端发送不超过该范围的批次。
- [x] 服务端 `/changes`、`/preflight` 和冲突覆盖路径对同一任务目录接受 250 文件批次。
- [x] HTTP 请求层可以接收超过旧 9 MiB、但不超过 96 MiB 运输上限的合法请求；超过
      96 MiB 时返回 413，且不进入业务写入。
- [x] Agent 可以接收超过旧 16 MiB 响应限制、但不超过新任务同步范围的完整快照和目录响应。
- [x] 现有 `10-03-e2e-oracle` pending 批次在服务端升级后自动重试成功，taskSpace revision 从
      `26` 向前推进，250 个文件可在服务端快照中完整读取。
- [x] 初始同步继续上传其余本地独有任务，最终 `initialSyncCompleted=true`，135 个本地任务
      全部进入同一 taskSpace，且没有任务内容被跳过或截断。
- [x] 超过 1024 文件或 64 MiB 的批次返回 413，taskSpace revision、文件快照和索引保持不变。
- [x] 单文件超过 1 MiB 仍被拒绝。
- [x] 同一 `batchId` 的 pending 重试仍遵循原幂等和 `clientSequence` 单调规则。
- [x] 同一任务目录仍整批提交；CAS 冲突不会因提高上限而写入部分文件。
- [ ] `npm test` 全部通过，Web 生产构建和 Windows 客户端构建通过。
- [x] 使用真实运行中的 Team Board 完成 pending 自动恢复和 135 任务同步 E2E，不修改或清空
      真实服务端数据库。

## Notes

- `64 MB` 在本任务中按代码现有容量单位解释为 `64 MiB`，即 `64 * 1024 * 1024` 字节。
- `96 MiB` 是 JSON 编码后的硬运输上限。64 MiB 正文中的反斜杠、控制字符等经过 JSON
  转义后可能超过 96 MiB，此类请求必须按硬运输上限拒绝；不得把运输上限提高到数百 MiB
  来覆盖理论最坏膨胀。
- 提高容量上限不等于放宽内容安全校验；扩展名、路径、UTF-8、摘要和目录完整性规则保持原样。
