# 项目 PRD 编制设计

## 1. 文档定位

正式文档定位为“面向产品与业务干系人的现行产品说明书”，不是技术架构文档，也不是归档任务索引。
读者应能在不读源码的情况下理解：

- Trellis Board 解决什么问题；
- 哪些用户以什么方式使用；
- 当前有哪些产品能力；
- 为什么这样设计；
- 核心操作如何完成；
- 哪些边界和限制必须提前知道。

## 2. 事实优先级

遇到信息冲突时按以下顺序取值：

1. 当前源码、测试和配置；
2. 当前 `README.md`、`apps/web/README.md`、`apps/desktop/README.md`、
   `docs/team-operations.md`；
3. 已归档任务中的最终决策与验收记录；
4. 归档任务中的早期背景方案，仅用于解释演进。

发生替代关系时，正文写当前行为，证据索引写“历史任务 → 当前替代实现”。例如：

- 服务端 Git 稀疏克隆 → 客户端 Tasks-only 快照；
- Node SEA sidecar → Rust 单 EXE 进程内 Agent；
- 单活动团队切换 → 全部授权团队聚合与团队筛选。

## 3. 文档结构

正式 PRD 采用以下结构：

1. 文档信息与阅读说明；
2. 产品摘要、问题与价值；
3. 目标用户、角色与典型场景；
4. 产品形态与运行模式；
5. 信息架构与全局交互；
6. 核心功能域：
   - 任务流水线与个人执行控制；
   - 任务详情、证据与协作；
   - 团队查询、归档与跨项目视图；
   - 任务创建、派发与操作闭环；
   - 本地项目接入与任务空间同步；
   - 团队、权限与管理台；
   - 插件；
   - Windows 桌面客户端与分发；
7. 设计思路与关键取舍；
8. 状态、错误与异常交互；
9. 非功能要求；
10. 非目标与当前限制；
11. 验收与成功标准；
12. 证据索引。

## 4. 功能描述模板

每个功能域至少回答：

- 用户问题：没有该能力时哪里低效或不可控；
- 当前能力：产品实际提供什么；
- 设计思路：为什么这样拆、这样排序或设置门禁；
- 核心交互：入口、主要动作、系统反馈、失败路径；
- 边界：哪些情况不能操作，系统如何处理。

内容以表格、短段落和编号流程为主，避免长篇代码解释。只在必须解释产品语义时提技术名称。

## 5. 交互叙事基线

- 首屏遵循“当前该做什么 → 哪些任务需要关注 → 任务处于流程哪一步”的决策顺序。
- 任务详情遵循“状态与进度 → 条件检查 → 阶段证据 → 风险依赖 → 产物 → 派发操作”的阅读顺序。
- 所有破坏性或跨边界操作必须显式确认，包括覆盖服务端任务、替换本地分支绑定和撤销设备。
- 软提醒不阻止个人流动；强门禁只用于权限、数据一致性、目标 Agent 不可用和分支不匹配等风险。
- 长操作使用独立操作项、阶段状态、重试和取消，不提前伪造正式结果。
- 服务端不可见或未授权的数据按不存在处理，前端隐藏不能替代服务端校验。

## 6. 术语约定

- “任务”指 Trellis 任务目录及其 `task.json` 和任务产物。
- “阶段证据”指能证明流程阶段的文件、人工检查点或子任务汇总。
- “任务空间”指规范化 Git 远端加分支形成的同步范围。
- “本地关联”指 Windows 客户端中的仓库路径、分支和任务空间绑定。
- “操作项”指创建/改派命令的独立状态记录，不等同于正式任务卡。
- “团队模式”指启用账号、团队和项目权限的 Team Board；“独立模式”等同 standalone。

## 7. 一致性与风险控制

- 不写未来承诺，除非当前 README 或任务明确列为非目标。
- 不用归档任务中的早期验收 checkbox 代替当前状态。
- 同一能力在摘要、功能域和交互章节出现时，信息必须相互一致。
- 对“当前可做”“受条件限制”“明确不做”使用固定措辞。
- 写完先按功能域检查覆盖，再按源码和 README 反查所有现状结论。

## 8. 验证策略

- 文件级：确认正式 PRD 存在、无 TBD、无旧术语和错误替代方案。
- 结构级：确认 12 个主章节和所有核心功能域齐全。
- 事实级：逐项对照当前 README、关键源码入口和归档任务证据索引。
- 阅读级：检查摘要、功能表、交互流程和边界是否足以支持新成员独立理解产品。
