# 修复团队实时同步阻塞主线程与误弹窗

## Goal

让团队实时同步在正常 Git 操作和真实未提交任务编辑下都可预测：不让 Git 已收敛的写入误触发责任人确认，不让全量实时重投影阻塞 Board HTTP 主线程，也不让确认窗口在服务异常时无法关闭或反复抢占焦点。

## Background

### 已确认事实

- 2026-11-10 15:45，用户在 `D:\wit\mdp-backend-service` 执行 `git merge origin/dev`。该合并写入了 `11-06-project-ds-sync-reconcile` 和 `11-06-workflow-task-development` 等 `.trellis/tasks` 文件。
- 桌面 Agent 监听已批准项目的变化，把上述 Git 写入作为实时本地修改上报；由于任务责任人是 `zhangxuan`，服务端返回 `ASSIGNEE_CONFIRMATION_REQUIRED`，桌面出现“正在修改他人负责的任务”窗口。
- 当前服务端在[live-sync.js](../../../server/team/live-sync.js:827)收到成功实时变更后同步调用[reapplyProject](../../../server/team/live-sync.js:1107)。该函数在 Node 主线程复制整个 `.trellis/tasks` 和 `.trellis/workspace`、调用 `scanRepository()`、重建任务索引并删除临时目录。
- 以当前的 `mdp-backend-service` 项目副本测量，135 个任务的复制、扫描和临时目录删除合计耗时约 19.3 秒，尚未包含 `buildBoard()`、SQLite 索引写入和系统负载。
- Board 在 15:53:53 出现 Agent 心跳请求超时，15:54:05 出现事件流长时间无数据，15:54:25 自动重连。该现象与主线程被同步全量重投影占用一致。
- Agent 对 HTTP 请求的 30 秒超时统一映射为“Agent 请求已取消”，导致“取消并恢复”“继续推进”“接管任务”都表现为无法完成。
- [show_control](../../../desktop/src-tauri/src/sidecar.rs:230)每个控制事件都会 `show`、`unminimize` 并 `set_focus`；批量文件变化会产生多个待确认事件，持续打断用户当前操作。
- 当前“取消并恢复”仍请求服务端最新实时文件；因此服务端无响应时，该按钮也不能本地关闭。

## Requirements

### R1 Git 已收敛的写入不得误触发责任人确认

- Git merge、fast-forward、checkout 等操作只改变工作区文件、但结果已经与当前 Git HEAD 一致时，不得作为“用户正在修改任务”进入责任人确认。
- 真实存在未提交任务内容修改时，仍必须保留现有责任人确认能力。
- 通过 Git 操作产生但最终与 HEAD 相同的文件变化，不得生成新的实时 revision、责任人警告或 Board `tasks.changed` 通知。
- 不修改用户的 Git 全局配置，不要求用户先 commit，也不得忽略真实未提交修改。

### R2 实时重投影不得阻塞 HTTP 主线程

- 实时变更的持久化确认与全量任务重投影必须解除强耦合；HTTP 健康检查、心跳和确认请求不能等待整个项目重新扫描完成。
- 同一项目短时间内的多个文件批次和定时刷新必须合并为有界次数的最新状态重投影，不得每个批次都复制并扫描整个项目。
- 重投影期间项目 Board 可以短暂使用上一个一致快照，但必须最终收敛到最新 revision，并通过现有 `tasks.changed` 事件通知页面刷新。
- 失败的重投影必须保留可重试状态和可诊断日志，不能回退已持久化的实时 revision。

### R3 确认窗口不得反复抢占焦点

- 同一任务、同一责任人和同一待处理修改不得生成多个视觉上重复的确认窗口。
- 保留独立确认窗口；本次客户端进程生命周期内，首次待确认事件可以显示并获得一次焦点。
- 用户主动关闭或选择“稍后处理”后，后续事件不得再次自动显示或强制获得焦点。
- 托盘菜单提供“处理实时确认”入口；用户主动点击时才重新显示并聚焦待确认窗口。

### R4 服务不可用时确认窗口仍可退出

- 用户必须能够关闭或隐藏确认窗口，不得依赖服务端请求成功。
- 关闭窗口不能静默丢失待确认修改；待确认事件仍需保存，并可在服务恢复后继续处理。
- 服务不可用、请求超时和处理失败必须显示可区分的实际错误，不能把 30 秒超时统一显示成“Agent 请求已取消”。
- “取消并恢复”需要服务端数据时，应明确显示正在等待或失败状态，并允许用户退出窗口而不是锁定界面。

## Acceptance Criteria

- [x] 在已批准项目执行只改变工作区文件、但结果与 Git HEAD 一致的 merge/fast-forward/checkout，不弹出责任人确认窗口。
- [x] 对他人负责的任务产生真实未提交 `.trellis` 修改时，仍按现有流程弹出责任人确认并可继续或接管。
- [x] 使用至少 300 个任务的真实项目触发实时修改时，`/api/health` 连续请求的最大响应时间不超过 1 秒。
- [x] 重投影期间的 Agent 心跳与待确认请求不因全量扫描而超时。
- [x] 同一项目连续收到多个实时批次时，最终只执行一次针对最新 revision 的完整重投影。
- [x] 重投影结束后 Board 能通过 `tasks.changed` 或等价刷新机制看到最新任务状态。
- [x] 重投影失败不会降低 `project_live_revision`，并保留后续重试状态。
- [ ] 同一任务的多个重复警告在桌面端只显示一个可操作项（源码与 Rust 单测已补，待 Cargo 执行）。
- [ ] 客户端启动后首次待确认事件可以自动显示一次并获得焦点（待 Windows WebView2）。
- [ ] 用户关闭确认窗口后，新到事件不能自动显示或 `set_focus` 再次打断操作（待 Windows WebView2）。
- [ ] 用户可从托盘“处理实时确认”主动恢复隐藏的待确认窗口（待 Windows WebView2）。
- [ ] 服务端不可达时，用户可以立即关闭或隐藏确认窗口，待确认事件仍保留（代码路径已实现，待实机）。
- [ ] 服务恢复后，用户可从明确入口重新打开待确认事件并完成取消、继续或接管（待实机）。
- [x] 超时和连接失败显示不同错误文案，用户能判断是服务未响应还是确认已失效。
- [x] 自动测试覆盖 Git 已收敛过滤、批量重投影合并、失败重试、主线程延迟基线、窗口去重和关闭不丢事件。
- [ ] Windows 桌面真实 E2E 覆盖 Git merge 不误弹、服务离线可关闭、服务恢复后继续处理和连续文件变化不抢占焦点。

## Technical Notes

- 现有团队实时协议、责任人确认语义、审计记录和 `project_live_*` 版本模型继续复用，不另建第二套同步协议。
- `server/team/live-sync.js` 的最终索引仍必须使用 `scanRepository()` 和 `taskIndex.buildBoard()`，不能在 HTTP 路由中另写任务推导。
- `read_only`、幂等、路径白名单、UTF-8、大小限制、`clientSequence` 和 Git 收敛契约保持不变。
- Tauri 控制窗口仍属于本地可信窗口；关闭权限不得扩大为可绕过服务端责任人校验。
- 产品交互采用“独立窗口、首次提示、关闭后静默入队、托盘恢复”；不改成完全静默或主窗口内嵌队列。

## Out of Scope

- 重新设计团队实时同步协议或责任人确认产品语义。
- 自动替用户 commit、push、merge 或修改 Git 全局配置。
- 重写 Trellis 扫描器或更换 SQLite。
- 把所有真实未提交修改降级为通知；真实修改他人的任务仍要求显式确认。
- 将待确认状态迁移到服务端持久化；本任务只保证客户端本地关闭窗口不丢待处理事件。
