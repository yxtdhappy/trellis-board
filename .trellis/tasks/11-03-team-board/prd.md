# 升级 Trellis Board 团队版

## Goal

将现有单机版 `trellis-board` 升级为公司内部共享的团队任务控制面。团队任务统一在服务端维护的项目 Git 工作副本中创建、委派和修改，再推送回项目配置的共享分支；开发机通过 Windows Agent 同步该分支，继续使用 Trellis 文件和流程完成实际开发。

## Background

当前仓库已经具备跨项目 Trellis 扫描、阶段推导、项目与负责人筛选、任务创建、负责人更新、人工阶段、计划字段、保存视图、依赖、事件和 SQLite 持久化。团队版应复用这些能力，不重写 Trellis 工作流。

当前单机版必须具备以下前提才能团队化：

- `server/index.js` 固定监听 `127.0.0.1`，没有登录和角色。
- 项目配置指向运行服务的本机绝对路径，没有服务端 Git 工作副本。
- 任务创建和负责人更新直接操作本机仓库，没有共享写入入口和 Git 推送。
- 开发机仓库、用户身份和 Trellis workspace 没有统一绑定关系。
- 写操作没有可信操作者、授权结果和推送审计。

已确认的产品方向：

- 服务端为每个项目维护一份权威 Git 工作副本。
- 项目首次接入时必须由管理员显式选择并绑定一个已存在的共享分支，不设全局默认分支；例如某项目可以约定 `dev`，另一个项目可以使用其他分支。
- 同步分支在项目创建时绑定，启用后不可原地修改；配置错误时必须停用并由管理员重新接入，MVP 不迁移已有任务的共享分支。
- 所有任务在服务端生成并提交、推送到该共享分支，不为每个任务创建独立分支或 Git worktree。
- 项目负责人和项目成员都可以创建任务，并委派给项目内任意有效成员。
- 被委派人在团队看板接受任务后，由本人 Windows Agent 将共享分支同步到本地仓库。
- 项目角色决定业务权限，设备只负责同步与展示状态，不拥有额外的任务写权限。
- 看板展示的服务端工作副本是团队任务事实源；Agent 不再把各自机器上的任务上传为团队任务来源。

## Requirements

### 团队访问与权限

- 团队服务必须通过统一入口供公司内部多名用户访问，不要求访问某台开发机的 `127.0.0.1`。
- MVP 使用自建账号，不接公司 SSO；管理员负责创建、禁用和重置账号。
- 首个系统管理员只能由服务器本机 CLI 初始化，不提供公开的“首次注册”HTTP 入口；后续管理员可在授权后通过管理页创建。
- 密码必须使用适合密码存储的慢哈希算法保存，登录后使用可撤销的服务端会话。
- 密码最少 12 个字符，界面不设置会削弱长口令的组合复杂度规则。
- 固定四类角色：
  - 系统管理员：管理用户、设备、项目和系统配置，但不会因管理员身份自动获得项目任务写权限。
  - 项目负责人：管理所属项目成员和 Agent 接入，可在项目内创建任务和重新委派。
  - 项目成员：可查看所属项目，并可在项目内创建任务和重新委派。
  - 只读成员：只能查看所属项目。
- 每个项目负责人和项目成员必须映射到该仓库中的一个 Trellis developer ID；只读成员可以为空。任务负责人只能选择已映射、具备项目写角色且 `.trellis/workspace/<developer-id>` 存在的成员。
- 未登录用户不能访问团队数据；用户只能访问拥有成员角色的项目。
- 禁用账号或撤销会话后，已有 Web 会话和 Agent 凭证必须立即失效。
- 系统管理员未获得项目角色时，不能创建、委派或修改任务。
- 系统管理员可以处理项目成员和负责人恢复，但不能移除最后一名有效项目负责人；项目负责人可以管理本项目成员。
- 任何操作都不能禁用或删除最后一名有效系统管理员；恢复入口仍是服务器本机 CLI。

### 服务端项目副本与 Git 同步

- 每个项目必须绑定一个 Git 远端和同步分支；共享分支在项目接入时逐个约定，不能假定所有项目都使用 `dev`。
- Git 远端不得在 URL 中携带密码、PAT、query 或其他凭证；HTTPS userinfo 一律拒绝，SSH 只允许非秘密的用户名，认证必须由服务端受控凭据机制提供。
- 服务端必须维护该项目的独立工作副本，定期从远端获取同步分支，并作为团队看板的任务来源。
- MVP 的任务文件写操作只包括创建任务和更新负责人 `assignee`；其他任务字段仍通过现有看板扩展数据管理。
- 服务端写入前必须先同步远端分支，并校验项目、任务路径、任务身份和预期版本。
- 服务端执行项目自带 `.trellis/scripts/task.py` 前必须校验管理员批准的工具链摘要；批准范围覆盖整个 `.trellis/scripts` 目录，任何脚本变化都会阻止任务写入并要求管理员重新批准。
- 团队模式禁止执行 `.trellis/config.yaml` 中的任务生命周期 hooks；检测到 hooks 时拒绝任务写入，不能把仓库配置变成服务账号上的任意 Shell。
- `task.py` 子进程必须使用参数数组、`shell:false`、限定工作目录和最小环境变量，不继承会话、Agent 或 Git 凭证。
- 写入成功后必须提交并推送到配置的共享分支；未成功推送的操作不得向用户显示为完成。
- 同一项目的 Git 写操作必须串行执行；并发修改同一任务时，后到操作必须整体拒绝，不能覆盖远端新版本。
- 推送发生非快进或冲突时，服务端可以安全重试任务目录内的无冲突变更；重试失败必须保留诊断并通知管理员，不能强推、覆盖远端或删除他人提交。
- 不使用每个任务独立分支，不为每个任务创建 Git worktree。
- Git 凭证不得写入数据库、审计正文、日志或前端响应；服务端使用受控凭据访问远端。

### 任务创建与委派

- 项目负责人和项目成员都可以在服务端创建任务，并指定项目内的负责人。
- 创建任务必须复用项目自己的 `.trellis/scripts/task.py create --no-start` 和现有字段校验。
- 新任务固定写入 `branch=<项目共享分支>`、`base_branch=null`，表示任务直接在共享分支工作且没有独立 PR 目标；客户端不能覆盖这两个字段。
- 派发负责人只能写入任务允许的 `task.json.assignee`，负责人必须同时是项目写成员、已映射 Trellis developer ID，并在该仓库 `.trellis/workspace` 中存在对应目录。
- 任务创建或负责人变更只有在 Git 推送成功后，才出现在团队任务队列并允许接受。
- 被委派人的任务状态分为“待接受”和“已接受”；接受动作必须记录操作者、时间和结果。
- 重新委派任务后，新的负责人必须重新接受。
- 接受任务不会修改 Trellis 任务身份；它只记录团队协作状态。
- MVP 不提供拒绝任务后的审批流，项目负责人通过重新委派处理。

### Windows 同步 Agent

- 每台参与开发的 Windows 10/11 机器必须安装并运行团队版 Agent。
- Agent 必须绑定具体用户、设备和已授权的本地项目目录。
- Agent 只能同步项目绑定的共享分支，不创建任务分支或任务 worktree。
- Agent 提供本地命令行完成配对、选择仓库、项目绑定、状态查看和诊断；桌面图形安装器不属于 MVP。
- 负责人接受任务后，Agent 对本地仓库执行受控的 fetch 和 fast-forward 同步，使任务文件出现在本地工作目录。
- 如果本地仓库不是配置的共享分支，或存在未提交修改，Agent 必须阻止自动同步并显示用户可处理的阻塞原因；不得自动 stash、reset、checkout 覆盖或丢弃用户改动。
- Agent 离线、版本过旧、凭证撤销、本地分支不匹配或同步失败时，团队看板必须明确展示状态。
- Agent 只执行白名单内的仓库校验、fetch、fast-forward pull、状态上报和凭证管理，不接受任意 Shell 命令或任意路径。
- Agent 凭证不得明文持久化，支持单独撤销；撤销后下一次请求立即失效。
- Agent 支持登录后后台运行和异常恢复；macOS 和 Linux 不在首版范围。

### 团队看板与审计

- 团队看板必须展示服务端同步分支中的真实 Trellis 任务，保留现有阶段推导、父子任务、人工阶段、计划字段、依赖、事件和保存视图。
- 团队看板默认提供跨授权项目的扁平任务列表，也可切换到单项目分组看板；两种视图都由服务端筛选、分页和返回完整匹配总数。
- 保存视图、WIP 上限和撤销范围必须按当前账号隔离；团队模式不能复用全局单机状态，也不能撤销其他成员的操作。
- 人工阶段、计划字段、标签和依赖属于项目共享任务数据，修改必须经过项目写权限校验并写审计。
- 看板必须展示项目 Git 同步状态、Agent 离线/版本过旧/本地未同步状态，以及任务待接受/已接受状态。
- 服务端 Git 拉取失败或工作副本不可用时，不能把旧缓存当作实时数据；必须展示数据更新时间和同步错误。
- 所有账号、角色、项目成员、设备、任务创建、委派、接受和 Git 失败操作必须写入只追加审计记录，包含操作者、时间、项目、动作、结果和关联操作 ID。
- 系统管理员可查看全局审计，项目负责人可查看所属项目审计；普通成员通过任务事件查看与任务相关的变化，不提供任意跨项目审计查询。
- 审计和接口错误不得泄漏密码、会话令牌、Agent 凭证、Git 凭证或完整敏感请求。

### 兼容性与容量

- 现有单机模式的数据和工作方式必须保留；团队模式通过显式配置启用。
- 数据库升级必须可回滚，保留升级前快照，不能静默删除现有项目、人工阶段、计划字段、依赖或事件。
- 团队模式在目标规模下使用单实例 Node.js 服务与 SQLite WAL，并通过按项目加载、轻量状态轮询和有界 Git 调度控制负载。
- MVP 目标容量为 400 个账号、200 个在线用户、100 个逻辑项目和 10,000 个当前任务快照。
- 团队 Web 不得一次下发所有项目的全部任务；跨项目视图使用服务端索引和稳定游标，单项目视图读取分组投影。
- 只有 release 容量测试证明单实例无法满足正确性或响应目标时，才在设计确认后升级为共享数据库、任务队列或多实例。

## Acceptance Criteria

- [ ] 团队成员通过统一入口登录并访问看板，未登录请求被拒绝。
- [ ] 四类固定角色的系统权限和项目权限按定义生效；系统管理员未获得项目角色时不能执行项目写操作。
- [ ] 项目负责人/成员完成 Trellis developer ID 映射后才能成为任务负责人；无映射或 workspace 不存在的用户会被拒绝。
- [ ] 项目负责人和项目成员都能从自己的设备创建任务并委派给项目内任意有效成员。
- [ ] `.trellis/scripts` 工具链摘要与管理员批准值不一致或存在生命周期 hooks 时，服务端拒绝任务写入，且不会执行该脚本。
- [ ] 新项目在摘要批准与 hooks 预检通过前保持 `provisioning`，不显示任务且不能写入。
- [ ] `needs_repair` 项目不能靠普通刷新绕过；只有管理员 repair 重新对清 Git/本地状态后才恢复写入。
- [ ] 任务创建和负责人变更由服务端写入项目工作副本，并通过审计记录确认已提交、推送到配置的共享分支。
- [ ] 新建任务的 `branch` 等于项目共享分支且 `base_branch` 为 `null`，避免现有 `task.py archive` 把共享分支误判为独立任务分支。
- [ ] 服务端不会为任务创建独立 Git 分支或 worktree。
- [ ] 被委派人看到待接受任务；接受后 Agent 在本地分支干净且匹配时完成 fast-forward 同步，任务文件在本地仓库可见。
- [ ] 本地分支不匹配或存在未提交修改时，Agent 不覆盖本地内容，明确报告阻塞原因并允许用户处理后重试。
- [ ] 远端更新将覆盖本地 ignored 文件时，Agent 同样阻止同步而不覆盖文件。
- [ ] 两个用户并发修改同一任务时，只有一个操作能基于匹配版本成功；另一个收到冲突且远端文件不被覆盖。
- [ ] Git 推送失败时，接口不返回成功，任务不能进入待接受状态，审计包含失败原因和关联操作 ID。
- [ ] Agent 离线、版本过旧或被撤销时，团队看板显示状态，并禁止该设备继续同步。
- [ ] 项目 Git 同步失败或工作副本过期时，看板明确标记数据未更新，不把旧缓存展示为实时状态。
- [ ] 两个成员各自保存视图和 WIP 上限时互不覆盖；撤销只作用于当前用户自己的可逆操作。
- [ ] 团队模式下列出、修改人工阶段/计划字段/标签/依赖的旧接口均执行项目授权和审计，只读成员不能写。
- [ ] 现有单机模式自动测试继续通过；数据库升级、账号权限、Git 写操作、任务版本冲突、审计和 Agent 同步均有自动化测试。
- [ ] 真实端到端验证覆盖“项目经理或成员创建并委派 → 服务端提交推送 → 负责人接受 → Agent 同步本地 → 本地任务可读取”。
- [ ] 在 400 个账号、200 个在线用户、100 个逻辑项目和 10,000 个任务快照的重复压测中，服务保持单实例 SQLite 部署且满足既定响应和正确性门槛。
- [ ] 团队模式支持跨授权项目混合分页任务和单项目分组看板；两种查询都不得一次下发全系统任务正文。

## Out of Scope

- 为每个任务创建独立 Git 分支、Git worktree 或自动 Merge Request。
- 原地切换已启用项目的共享分支或迁移该分支上的历史任务。
- 自动批量导入所有本机仓库或迁移旧单机个人视图；团队项目由管理员逐个接入，现有 `repositories.id` 可供升级时保留项目级扩展数据。
- 让各开发机直接写自己的仓库副本并跨机器合并任务。
- 阻止有仓库写权限的用户绕过 Board 直接向共享分支提交任务文件；MVP 会同步并按 Git 提交信息识别外部变化，但强制隔离需要仓库分支保护/服务端钩子另行实施。
- 自动切换用户当前 Git 分支、自动 stash、自动 reset 或自动解决代码冲突。
- 公司 SSO、自定义角色、逐操作 ACL、评论、站内通知、提醒升级和审批流。
- macOS 或 Linux Agent。
- Agent 自动升级、代码签名和桌面 GUI；首版通过审核包+校验和分发，并展示版本过旧。
- Git 分支保护策略改造；服务端凭据必须有权限向配置分支推送，否则明确报错。
- 第一版引入微服务、外部消息队列、多实例会话或跨地域高可用。
- 跨项目视图渲染完整父子分组和全部泳道；跨项目 MVP 使用分页扁平列表，完整分组在单项目看板中查看。
