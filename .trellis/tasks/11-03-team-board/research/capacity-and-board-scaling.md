# 容量与团队看板加载契约

## 目标规模

- 400 个账号。
- 200 个在线 Web 用户。
- 100 个逻辑项目。
- 10,000 个当前任务快照。
- 容量测试按每名在线用户最多 2 台设备模拟 400 个 Agent 心跳/长轮询连接，这不是硬性设备上限。

## 现有多机容量证据

当前 `data/scan-cache.json` 为 2,390,377 字节，包含 641 个任务快照。按任务数量线性估算，10,000 个快照约 37 MB；这只是本地数据的数量级估算，不是保证值。团队模式不能把全系统全部任务作为一次 `/api/board` JSON 广播给 200 个在线用户。

## 看板加载

- `GET /api/team/projects` 返回当前用户有权访问的项目摘要、任务计数、`boardVersion`、Git/Agent 状态。
- `GET /api/tasks/query` 提供跨项目服务端筛选、分页和不透明游标，默认返回扁平任务行，可筛选全部项目或“我的任务”；它只返回当前页，不返回全部任务正文。
- Team 模式的 `/api/board` 必须指定单个 `projectId`，并支持 `limit`（默认 100，最大 200）和不透明 `cursor`；用于当前项目的完整分组看板。
- 跨项目视图使用 `team_task_index` 查询，不合并并解析 100 个项目的完整 JSON；项目切换后再读取对应项目的分组投影。
- `GET /api/team/status` 返回每个可见项目的最新 `boardVersion`、跨项目 `queryRevision` 和 `queryDay`。Web 以约 3 秒间隔轮询轻量状态，只有相关版本或自然日变化时才重新请求当前任务页。
- 项目任务响应提供 `ETag`；支持 `If-None-Match` 时返回 304。服务端仍先做会话和项目授权。
- 前端切换跨项目/单项目范围或修改筛选条件时重置游标；筛选、总数和稳定排序由服务端基于完整授权结果执行，不能只过滤当前页。

## 单实例容量前提

- 服务端仍为一个 Node.js 进程和一个 SQLite WAL 数据库，团队模式不预先引入外部数据库、消息队列或多实例。
- 团队 Web 状态轮询从 standalone 的 750 ms 调整到约 3 秒；200 个在线用户约 67 次状态请求/秒。
- 400 个 Agent 按 15 秒心跳约 27 次请求/秒；`last_seen_at` 每台设备最多每 30 秒写一次。
- 100 个项目按 60 秒最小拉取间隔调度，使用抖动和最多 4 个并发 Git fetch；禁止同一时刻集中启动全部项目。
- 看板解析继续使用 Worker 和按项目原子缓存；跨项目查询读取规范化 `team_task_index`，项目分组看板读取对应项目缓存。
- 所有查询必须批量读取项目/Agent 状态，禁止按任务执行 N+1 查询。

## 验收门槛

- 400 账号、100 项目和 10,000 任务快照的重复容量测试必须在 release 前通过。
- 模拟 200 个 Web 会话和 400 个 Agent 连接，记录 p50/p95、SQLite 锁等待、事件循环延迟、内存和项目扫描耗时。
- 常规已授权状态/任务读取目标 p95 不超过 500 ms；Git fetch/push 和扫描作为显式异步状态展示，不伪装成同步读延迟。
- 不允许串项目数据、重复幂等发布、丢失审计或旧缓存冒充实时数据。
- 如果单实例无法通过容量或正确性门槛，必须回到设计阶段评估共享数据库、任务队列或多实例；不能以降低验收数据掩盖问题。

## 风险

- 100 个项目各保留一份服务端 Git 工作副本，磁盘容量取决于各仓库历史大小，部署前必须实测并提供清理/扩容方案。
- 单实例没有跨机高可用；服务停机期间团队任务写入和 Agent 同步都不可用。
- 跨项目默认是分页扁平列表；完整父子分组和泳道在单项目看板中查看。如果需要跨项目完整分组一次展示，必须另行设计聚合结构，不能回退到 10,000 任务单次响应。
