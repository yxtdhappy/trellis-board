# 个人执行：追溯与复盘

## Goal

让个人用户能解释任务为什么变慢、回看可信操作历史，并在误操作后撤销最近一次可逆变更。

## Dependencies

- 必须先完成并归档 `10-30-personal-plan-attention` 与 `10-30-personal-risk-flow`。
- 依赖稳定任务身份、append-only 事件、人工阶段事件、扫描阶段观察和依赖事件。
- 本任务不新增业务表；若前序实现与总体设计有偏差，先回到对应任务修复，不在本任务临时造替代模型。

## Requirements

- R1 任务详情展示按时间倒序排列的事件时间线，并区分人工操作、扫描观察和系统追踪起点。
- R2 用户可以查看当前任务最近一次尚未撤销的可逆操作，并在确认后撤销。
- R3 撤销通过追加补偿事件并恢复 `before` 状态完成，不删除、不改写原始事件。
- R4 当没有可逆操作、原操作已被撤销或当前任务身份无效时，撤销按钮禁用并解释原因。
- R5 撤销写入、投影恢复和补偿事件必须处于同一 SQLite 事务。
- R6 根据事件计算追踪后的 Lead Time、Cycle Time、阶段停留、阶段回流次数和阻断时间占比。
- R7 指标必须返回 `missing`、`partial` 或 `tracked` 完整度及缺失原因。
- R8 证据不足、追踪起点过晚或扫描存在缺口时，不显示精确数字。
- R9 同一事件集重复计算必须得到相同结果；所有计算可追溯到事件 ID。
- R10 任务归档后仍可通过稳定身份查看历史和指标。
- R11 历史或指标失败不得阻止任务标题、产物、阶段和现有操作显示。

## Acceptance Criteria

- [x] 详情按发生顺序正确显示前序任务生成的事件，并标明来源和操作者。
- [x] 计划字段修改后可撤销，API 读回值和 UI 显示均恢复为修改前内容。
- [x] 人工阶段确认后可撤销，`task_stage` 投影恢复且追加 `operation_undone` 事件。
- [x] 依赖创建或解除后可撤销，依赖活动状态与原始创建/解除时间可解释。
- [x] 同一操作组只允许撤销一次；再次请求返回“没有可撤销操作”且不写新记录。
- [x] 活动任务归档后，历史仍按稳定身份关联，不因相对路径变化消失。
- [x] `tracking_started` 不计作阶段停留；旧任务没有阶段事件时指标为 `missing`。
- [x] 扫描只观察到部分阶段时指标为 `partial`；完整覆盖时标记 `tracked`。
- [x] 相同夹具重复计算得到完全一致的指标对象。
- [x] 历史/指标接口失败时，任务详情其余内容仍可用。
- [x] `npm test`、JavaScript 语法检查、真实 API 验证和浏览器页面验收通过。

## Out of Scope

- 无限级撤销、跨任务全局事务撤销和版本回滚。
- 回填启用前历史或按文件 mtime 推算指标。
- 团队绩效、评分、排行榜和预测模型。
- 持久化聚合指标；MVP 直接从事件计算。

## Product Decisions

- 撤销范围是当前任务最近一次尚未撤销的可逆操作组。
- 历史指标只从事件记录启用后累计，旧任务明确显示历史缺失。
- 指标追求可解释和可重建，不追求对旧任务给出看似完整的历史。
