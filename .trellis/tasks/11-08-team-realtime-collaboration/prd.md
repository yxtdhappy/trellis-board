# 团队模式客户端实时双向任务同步

## Goal

让 Trellis Board 在单机模式和团队模式下都具备准实时的任务状态更新能力：单机模式继续监听本机项目；团队模式由已关联项目的客户端监听本地 `.trellis`，上报未提交的任务状态内容，服务端汇总后实时通知团队其他客户端。

## Background

- 单机模式已经由 Board 服务端通过 `server/watcher.js` 监听本地白名单仓库的 `.trellis`。
- 团队模式 Board 服务端当前不启动该本地 watcher，主要依赖 Git 轮询、项目刷新和 Agent SSE 事件。
- 桌面客户端 sidecar 当前没有 `.trellis` 文件 watcher。
- 现有本地项目绑定已经支持项目权限、同步分支和 Git 远端强校验，但桌面端尚无登录后的项目关联 UI。
- 产品要求允许客户端上报尚未 commit 的 `.trellis` 任务内容，以降低多人重复处理同一任务的风险。

## Task Map

| 子任务 | 交付 |
| --- | --- |
| `11-08-desktop-account-login` | 账号密码登录、团队项目展示、本地项目关联、Git 远端强校验 |
| `11-08-team-realtime-task-sync` | 复用 watcher、客户端监听与上报、服务端汇总与广播 |

项目实施顺序：

1. 先完成项目关联和客户端身份链路。
2. 再完成实时任务同步协议。
3. 父任务最后验证两个子任务组合后的端到端行为。

## Requirements

- 单机模式继续使用现有 watcher 行为；本需求不得破坏单机实时刷新。
- 团队模式服务端不得执行单机版的本地 `.trellis` 文件监听。
- 团队模式的 watcher 必须复用单机 watcher 的核心能力，不复制一份独立监听实现。
- 客户端只为服务端已关联且绑定有效的项目启动 watcher；团队成员完成 Git 身份校验后绑定立即有效，不进入人工审批。
- `read_only` 项目成员可以接收实时内容，但客户端 watcher 不得上传其本地修改。
- 客户端 watcher 感知 `.trellis` 变化后，允许读取尚未 commit 的文件内容并上报服务端。
- 服务端必须验证客户端、团队成员、项目绑定和文件路径后才能接收上报。
- 服务端汇总多个客户端的上报，并向同一项目其他已关联客户端广播准实时任务变化。
- 接收方客户端和 Board 页面应尽快显示任务状态变化，不能依赖下一轮 Git 轮询。
- 正常网络下，从来源端本地文件保存完成到其他在线客户端完成 Board 和本地文件更新，P95 不超过 3 秒。
- 接收方客户端必须把服务端最新任务内容自动写入本地 `.trellis`；服务端版本是冲突时的最终事实源。
- 本地文件被远端版本覆盖前必须备份；用户可一键恢复被覆盖的本地版本。
- 一键复原必须把恢复内容作为新的服务端版本上传并广播，重新成为所有客户端的最新状态。
- 非任务责任人推进或修改他人负责的任务时，必须出现显眼提示，明确当前责任人并建议先沟通。
- 警告后选择“继续推进”必须保留原责任人并记录审计；只有显式选择“接管任务”才变更责任人。
- 警告以发起修改的客户端为主，并阻断上报；原责任人只接收通知，不要求在线确认。
- 同一客户端不重复消费自己上报的事件。
- 断线、重连、重复事件、乱序事件和同一任务并发修改不能导致状态静默丢失。
- 服务端按请求到达顺序分配单调版本；后到达并成功提交的版本成为最终最新版本。
- 并发合并粒度为文件：不同任务文件可合并，同一文件由后到版本覆盖。
- 被后到版本覆盖的客户端必须先备份本地文件，再应用新版本；一键复原产生更新版本。
- 实时版本持续作为服务端最新状态，直到 Git 中对应文件内容与实时版本一致；不一致时不得用旧 Git 内容静默回退看板。

## Acceptance Criteria

- [ ] 单机模式修改本地 `.trellis` 后，原实时看板刷新行为保持不变。
- [ ] 团队模式服务端进程不监听本地 `.trellis` 文件。
- [ ] 单机服务端与客户端 sidecar 使用同一 watcher 核心模块，不维护两套目录过滤和事件归一化逻辑。
- [ ] 客户端只监听已关联且绑定有效项目的 `.trellis`；绑定由团队成员身份和 Git 强校验自动生效。
- [ ] `read_only` 绑定只接收服务端版本，不上传本地修改。
- [ ] 客户端 A 修改未提交任务状态后，客户端 B 无需等待 Git 轮询即可看到对应变化。
- [ ] 正常网络下，来源端保存到其他在线客户端 Board 与本地文件完成更新，P95 ≤ 3 秒。
- [ ] 客户端 B 本地 `.trellis` 对应文件自动更新为服务端最新版本。
- [ ] 本地存在不同内容时，覆盖前生成可识别的备份，并显示冲突提示。
- [ ] 覆盖后可通过一键复原恢复本地备份，并明确复原是否形成新的服务端版本。
- [ ] 一键复原形成新的服务端版本并广播，其他客户端按相同的备份后覆盖流程应用。
- [ ] 非责任人修改任务时出现显眼提示，显示责任人并提供继续、取消和接管选项。
- [ ] 选择“继续推进”后责任人保持不变并留下审计；只有“接管任务”会变更责任人。
- [ ] 操作者取消后本地恢复为服务端版本；操作者继续或接管后才允许上报。
- [ ] 原责任人收到变更通知，但其他客户端的操作不依赖原责任人在线确认。
- [ ] 服务端拒绝未授权客户端、未批准绑定、越界路径和超大上报。
- [ ] 重复或乱序上报不会产生重复任务或错误回退。
- [ ] Git 内容仍落后于实时版本时继续保留实时状态，不静默回退任务阶段。
- [ ] 两个客户端并发修改时，服务端按到达顺序处理，后到版本成为最终状态，先到方本地按备份后覆盖流程收敛。
- [ ] 两个客户端并发修改同一任务的不同文件时两份修改都保留；修改同一文件时后到版本覆盖。
- [ ] 两个子任务分别通过验收后，组合流程在 Windows 真实客户端上完成 E2E。

## Out of Scope

- 客户端新增服务端 Git 项目；项目只能先由服务端维护。
- 绕过项目权限、绑定审批和 Git 远端强校验。
- 用实时事件完全替代 Git 提交、推送和最终一致性校验。
