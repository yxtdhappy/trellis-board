# 分支监听状态与主动解绑生命周期

## Goal

让用户能够明确区分三种分支状态：当前有客户端监听、暂未监听但仍保留关联、所有客户端已主动解除关联。桌面客户端提供按分支解绑的快捷操作；服务端汇总真实监听状态，并在所有客户端均解除关联后显著提示该分支可能不再需要。

## Background

- 需求最初基于旧 Node sidecar 结构编写；当前 `main` 已迁移为 monorepo，桌面 Agent
  位于 `apps/desktop/src-tauri/src/agent`，旧结构只作为设计与迁移来源。
- 同一项目分支对应独立 taskSpace，同一分支可被多个客户端绑定。
- 当前 binding 只表示客户端曾建立关联，不能证明客户端仍在监听该分支。
- 当前 Agent 心跳需要上报运行时实际激活的 binding，而不是配置中的全部 binding；服务端在线判断不能只看 approved binding 和设备级 `last_seen_at`。
- 客户端解绑必须同时停止本地同步并通知服务端撤销 binding；只删除本地配置会留下永久有效关联。
- 当前项目栏按分支展示本地关联状态，但只反映当前桌面客户端的本地信息，无法看到其他客户端的绑定与监听汇总。
- 当前 taskSpace 状态集合包含 `active`、`indexing`、`error`、`disabled`，但没有“所有客户端主动解除关联”的独立业务状态。

关键证据：

- [agent/runtime.rs](../../../apps/desktop/src-tauri/src/agent/runtime.rs) 负责 Agent 心跳和运行时 binding。
- [team/sync-agent-service.js](../../../apps/server/team/sync-agent-service.js) 保存设备心跳与监听子协议。
- [ProjectRail.tsx](../../../apps/web/src/components/layout/ProjectRail.tsx) 按 taskSpace 渲染分支行并读取本地 association。
- [task-space-service.js](../../../apps/server/team/task-space-service.js) 负责 taskSpace、binding、监听聚合和权威解绑。
- [database.js](../../../apps/server/database.js) 定义了 `sync_agent_binding` 与 taskSpace 状态约束。

## Terminology And State Model

- `已关联`：存在 `approved` binding，表示该客户端保留以后同步该分支的资格。
- `在线监听`：Agent 在线、binding 已批准，且运行时实际激活了该分支 taskSpace。
- `暂未激活`：仍有 approved binding，但当前没有任何客户端实际监听；原因通常是所有客户端都切到其他分支或离线。
- `无客户端关联`：所有客户端均明确解绑，已没有 approved binding。
- `已停用`：taskSpace 被全局停用，属于后续独立管理流程。

状态优先级：

1. taskSpace 已停用：显示“已停用”。
2. 在线监听数大于 0：正常，显示在线监听数和已关联数。
3. approved binding 为 0：显示“无客户端关联”，使用醒目警告。
4. 仍有 approved binding，但没有任何客户端上报过监听协议：显示“旧客户端，监听状态未知”。
5. 仍有 approved binding，且至少一个客户端上报过监听协议，但当前在线监听数为 0：显示“当前未激活，关联保留”。

## Requirements

### R1 分支切换与主动解绑必须区分

- 客户端仅从分支 B 切换到分支 A 时，不得撤销、删除或解绑 B 的 binding。
- B 只从“在线监听”集合移除，仍保留 approved 关联，并标记为“暂未激活”。
- 客户端切回 B 后，应恢复为在线监听，不需要重新建立 taskSpace。
- 只有用户明确执行“不再同步此分支”时，才撤销当前客户端的 binding。

### R2 客户端必须提供按分支解绑快捷操作

- 桌面客户端应在项目栏对应分支行提供快捷操作，用户可明确选择“不再同步此分支”。
- 操作前必须二次确认，说明仅解除当前客户端与该分支的关联，不影响其他客户端，也不删除服务端任务与历史。
- 操作开始后应暂停当前 binding 的 watcher、上传队列和补同步，避免解绑过程中继续写入。
- 服务端解绑成功后，客户端必须删除对应本地 binding 和 cursor。
- 服务端暂时不可达时，客户端应停止该分支同步并显示“服务端解绑待确认”，后台重试，不能静默保持服务端 approved 状态。
- Rust 桌面 Agent 的解绑入口必须复用同一套“本地暂停、服务端权威解绑、失败待确认”生命周期；禁止只删除本地 binding 后继续让服务端保留 approved 关联。
- 不因删除本地 Git 分支而自动推断用户不再需要该 taskSpace；Git 分支操作与 taskSpace 解绑保持独立。

### R3 Agent 必须上报真实监听集合

- Agent 心跳必须上报当前运行时实际激活监听的 taskSpace，而不是配置中所有历史 binding。
- 服务端必须以该监听集合和 binding 状态计算在线监听人数。
- 设备在线但未激活某分支时，该分支不得计为在线监听。
- 设备超过心跳阈值未上报时，必须自动从在线监听集合移除。

### R4 服务端必须提供分支监听汇总

- 每个可读 taskSpace 至少返回 approved binding 数、在线监听数、最后监听时间和派生状态。
- 项目栏应能够显示 `在线监听数 / 已关联数`。
- 普通项目成员只能看到聚合数量；项目负责人、团队管理员和系统管理员可查看该分支下客户端名称、用户、绑定状态、在线状态、最后一次监听时间和绑定时间。
- 监听详情必须遵循现有项目与团队权限，不能跨团队或向无管理权限的成员泄露设备和用户信息。

### R5 解绑必须由服务端权威提交

- 新增当前 Agent 可调用的分支解绑能力，仅允许撤销属于当前 Agent 的 binding。
- 服务端解绑成功后应取消该 binding 下的待投递、已投递和运行中命令，并停止后续任务事件投递。
- 解绑应保留 binding 历史审计，禁止物理删除相关任务、冲突和审计记录。
- 重复解绑必须幂等；已撤销的 binding 再次解绑返回成功或稳定状态，不产生重复副作用。
- 解绑后，服务端不得再把该客户端当作该 taskSpace 的在线任务目标。

### R6 项目栏必须显著区分风险

- 仍有 binding 但当前无人监听：使用黄色弱警告，显示“当前未激活，关联保留”，不能声称分支已废弃。
- 所有客户端主动解绑后：使用红色醒目提示，显示“无客户端关联”。
- taskSpace 已停用：使用中性状态，不与“无客户端关联”重复告警。
- 告警必须定位到具体项目分支行，不能把单个分支的问题升级成整个项目离线。
- 状态刷新不得因客户端重启、短时网络抖动造成频繁闪烁；必须使用服务端统一心跳阈值。

### R7 现有系统必须保持兼容

- 新服务端应能识别旧版 Agent 不支持精确监听上报的状态；未知时不得伪造为在线。
- 新 Agent 与未升级服务端组合时，不能破坏既有绑定、同步、任务命令和项目栏。
- 协议升级应明确最低版本和降级提示，不能把旧客户端静默显示为正在监听。

### R8 无在线监听时禁止创建和改派

- Team 模式下，选中 taskSpace 的 `onlineListenerCount = 0` 时，前端必须禁用“创建并派发”和任务改派提交。
- 前端必须展示明确原因：“请先启动并绑定该分支的客户端”；`inactive`、`unassociated` 和 `unknown_legacy` 均按无在线监听处理。
- 服务端仍必须以真实监听状态做最终校验，不能只依赖按钮禁用；没有可投递的在线监听 Agent 时不得创建操作项。
- 同一分支只要还有一个客户端正在监听，就允许提交；具体目标负责人自身离线仍沿用现有 `AGENT_OFFLINE` 校验。

## Acceptance Criteria

- [ ] AC1 三个客户端绑定同一分支时，任一客户端切换到其他分支，只把该客户端从在线监听集合移除，binding 仍为 approved。
- [ ] AC2 三个客户端全部切换分支后，项目栏显示“0 在线监听 / 3 已关联”的黄色“当前未激活”状态，而不是“已废弃”。
- [ ] AC3 任一客户端执行快捷解绑后，只有该客户端 binding 变为 revoked；其他客户端和 taskSpace 不变。
- [ ] AC4 三个客户端全部主动解绑后，项目栏显示“0 在线监听 / 0 已关联”的红色“无客户端关联”状态。
- [ ] AC5 客户端关闭且不再发送心跳后，在统一超时阈值后自动从在线监听集合移除，但 approved binding 和“暂未激活”状态仍保留。
- [ ] AC6 解绑过程中 watcher、上传、补同步和任务命令不再写入该 taskSpace；服务端也拒绝旧客户端继续使用已撤销 binding。
- [ ] AC7 解绑成功保留任务快照、冲突、审计和历史，不删除 taskSpace。
- [ ] AC8 解绑接口重复调用幂等，并记录一次有意义的审计结果。
- [ ] AC9 普通成员无法通过监听详情或解绑接口读取或操作其他用户设备。
- [ ] AC10 项目栏在“全部项目”、具体项目和具体分支范围下均按 `taskSpaceId` 独立展示监听状态，不跨分支合并。
- [ ] AC11 Node 自动测试覆盖心跳监听集合、在线阈值、解绑权限、幂等、命令取消和状态聚合。
- [ ] AC12 桌面客户端测试覆盖快捷解绑、服务端失败时本地暂停与待确认、成功后本地 binding/cursor 清理。
- [ ] AC13 `onlineListenerCount = 0` 时创建和改派按钮不可提交并显示原因；直接调用接口也不会产生 `sync_task_command` 操作项。
- [ ] AC14 旧客户端未上报监听协议时显示 `unknown_legacy`，不计为在线，也不允许创建或改派。
- [ ] AC15 桌面快捷解绑在服务端可达时完成权威解绑；不可达时进入待确认并停止该分支同步，后续重试成功后清理本地 binding 与 cursor。

## Out Of Scope

- 不因 Git 分支删除自动停用或物理删除 taskSpace。
- 不自动删除 taskSpace、任务文件、冲突、审计或 Git 分支。
- 不在本任务中实现项目级或 taskSpace 级全局“停用/重新启用”管理界面；本任务只提供“无客户端关联”的可观测状态。
- 不自动把任务从无人关联的分支迁移到其他分支。
- 不自动合并不同分支任务内容。
