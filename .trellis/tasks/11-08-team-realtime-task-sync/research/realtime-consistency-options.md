# 团队实时任务同步一致性分析

## 问题

多个客户端可能同时拥有同一个 Git 项目的未提交 `.trellis` 工作副本。需要让任务状态变化在团队内准实时可见，同时不能静默覆盖本地工作或破坏 Git 历史。

## 已确认事实

- Board 的任务投影主要由 `task.json`、PRD/设计/实施/报告文件和 workspace journal 推导，不是单独的一组可任意写入数据库字段。
- 单机 watcher 只负责发现 `.trellis` 变化并触发重新扫描，本身不保存任务状态。
- 团队服务端已有 Git 工作副本、扫描索引和 SSE 事件，但当前没有未提交内容覆盖层。
- 客户端 sidecar 已有设备凭据、绑定、SSE 和 Git 同步能力，但没有 watcher。
- `.trellis` 可能包含用户正在编辑的 Markdown、JSONL 和脚本文件，直接写回其他工作区会破坏本地未提交工作。

## 方案 A：服务端实时覆盖层，Board 只读展示

服务端接收任务级未提交快照，保存为带版本的实时覆盖层。Board 查询时用覆盖层投影任务状态和可见内容；其他客户端收到事件后只刷新 Board。

优点：

- 最快解决“别人已经推进任务，而我看不到”的重复工作问题。
- 不修改其他开发者工作区，不会覆盖未提交文件。
- 事件协议可独立于 Git，失败时仍可回退到 Git 扫描结果。
- 便于做限流、审计、版本和冲突检测。

缺点：

- 其他客户端本地 `.trellis` 文件不会自动变化。
- 需要定义覆盖层与 Git commit 的收敛规则和保留期限。
- 详情里若展示任意大文件，需要限制文件集合和大小。

## 方案 B：服务端权威实时文件镜像并写回客户端

服务端接收变化文件内容，维护项目级实时文件版本；其他客户端收到事件后写入本地工作区。

优点：

- 真正做到本地文件层面的双向准实时。
- 任务文件和其他协作文档都能同步。

缺点：

- 任意文件写回可能覆盖开发者未提交工作。
- Git 工作区、实时覆盖和 commit 三方冲突复杂。
- Markdown、JSONL 和二进制文件很难自动合并。
- 断线补偿、删除文件、重命名和权限问题显著增加。

## 方案 C：仅广播“有变化”，由客户端执行 Git 同步

优点：

- 最贴近现有 Git 架构，实施成本最低。

缺点：

- 未提交内容不在远端，其他客户端无法获得，无法满足用户当前要求。

## 已确认基线

采用方案 B，并增加数据保护：

1. 客户端 watcher 读取变化的已允许任务文件，生成任务级快照。
2. 服务端按项目和任务保存单调版本、来源设备、文件摘要和内容。
3. Board 列表和详情优先使用实时覆盖层，Git 同步成功后将其收敛。
4. 其他客户端刷新 Board，并把服务端最新文件写入本地 `.trellis`。
5. 本地文件内容与服务端不同时，先备份本地文件，再以服务端内容覆盖。
6. 一键复原会把备份内容作为新的服务端版本上传并广播，重新成为所有客户端的最新状态。
7. 非责任人修改有责任人的任务时，由发起方客户端阻断上报并显示警告；“继续推进”保留原责任人并审计，“接管任务”才变更责任人；取消则先备份再恢复服务端版本。
8. 服务端按请求到达顺序串行分配单调版本；并发修改以最后成功到达的版本为最终最新版本，先到方先备份再被覆盖。
9. 并发合并在文件级执行：不同文件各自保留，同一文件由后到版本覆盖。

## 数据保护约束

- 备份必须位于项目工作区之外或不会被 watcher 再次扫描为任务文件的位置。
- 备份记录需要包含项目、任务、原始文件路径、服务端版本、本地与远端摘要、备份时间。
- 自动覆盖必须采用临时文件加原子 rename，不能留下半写文件。
- watcher 写入远端版本时需要抑制自触发上报，避免广播风暴。
- 覆盖失败时不得删除备份，并应暂停该项目的自动应用。
- 一键复原必须在 watcher 暂停或抑制窗口内执行，防止恢复动作立即被当成新修改上传。

## 仍需决定

- 实时覆盖层的字段范围和最大文件大小。
- 未提交状态的保留期限及其与 Git commit 的收敛方式。
