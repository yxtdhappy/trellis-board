# 按 CPU 热点优化状态刷新

## Goal

在保证任务同步、关联、冲突处理和状态恢复语义不变的前提下，降低桌面客户端空闲 CPU。
只把经测量确认会显著消耗 CPU 的状态刷新改为事件驱动，不为实现“零轮询”而改造低成本路径。

## Background / Confirmed Facts

- 当前客户端空闲 CPU 基线约为 Board `5.99%`、归档 `6.72%` 单核，最高约 `18.75%`；
  旧版约 `100%` 的周期尖峰已消失，但仍未达到 `<2%` 的目标。
- `useBoard` 每 3 秒请求一次 Team 状态：
  [useBoard.ts](../../../apps/web/src/hooks/useBoard.ts:215)。
- 选中具体 taskSpace 时，`useBoard` 每 3 秒请求一次任务操作列表：
  [useBoard.ts](../../../apps/web/src/hooks/useBoard.ts:282)。
- 任务操作列表定时器在 Team 模式下始终创建；未选择具体 taskSpace 时不会请求网络，但会重复写入
  空操作列表并触发无意义的状态更新。
- 创建任务和改派任务会返回异步 operation，详情查询约按
  `700ms → 1.4s → 2.8s → 4s` 退避：
  [useBoard.ts](../../../apps/web/src/hooks/useBoard.ts:307)。当前轮询使用的状态判断同时包含
  `failed`，因此失败终态也可能无限继续查询。
- `ProjectRail` 每 3 秒分别读取本地关联和 sidecar 状态：
  [ProjectRail.tsx](../../../apps/web/src/components/layout/ProjectRail.tsx:383)、
  [ProjectRail.tsx](../../../apps/web/src/components/layout/ProjectRail.tsx:393)。
- 本地关联读取会进入 ownership 投影，可能读取 Git HEAD 和任务目录；其缓存 TTL 为 15 秒：
  [task_sync.rs](../../../apps/desktop/src-tauri/src/agent/task_sync.rs:1133)。
- 控制窗口每 750 毫秒读取一次待处理事件；窗口隐藏后 Webview 仍然存在：
  [ControlApp.tsx](../../../apps/web/src/desktop/ControlApp.tsx:396)。
- 插件页每 5 秒刷新，只在插件页面打开时运行：
  [PluginsView.tsx](../../../apps/web/src/features/plugins/PluginsView.tsx:73)。
- 项目接入流程每 5 秒检查一次推送状态，只在接入对话框打开时运行：
  [ProjectOnboardingDialog.tsx](../../../apps/web/src/features/board/dialogs/ProjectOnboardingDialog.tsx:442)。
- 上一轮同步性能任务已消除相同 revision 的重复快照拉取、全量任务扫描和无效 cursor 重写；
  当前任务不重复修改该算法。
- 低成本轮询不一定值得事件化。事件链路、跨进程通知和漏事件恢复本身也有维护成本；
  只有 CPU 收益明确时才进入本轮。

## Requirements

### R1 先测量再决定

- 在同一构建、同一数据规模和同一机器上采集修复前基线，至少记录：
  - Board 与归档空闲时的进程树平均 CPU、P95 和峰值；
  - 各候选路径的请求次数或 Tauri 调用次数；
  - 关键同步和状态事件次数；
  - 是否存在与固定间隔对应的周期性 CPU 尖峰。
- 候选路径必须能归因到具体调用链；不能仅因为“它是定时器”就事件化。
- 每个优化项必须有独立的修复前后对照，无法证明 CPU 收益的改动不进入交付。

### R2 优先处理高成本路径

- 第一优先级：`list_local_associations` 的 3 秒读取。该路径涉及 Tauri IPC、本地配置和 cursor
  读取、ownership 投影以及可能的 Git/任务目录访问，是当前最值得事件化的候选。事件建立后仍保留
  10 秒可见兜底，不在页面隐藏时运行。
- 第二优先级：控制窗口的 750 毫秒读取。调用本身可能很轻，但空闲时每分钟约 80 次唤醒，
  且隐藏窗口仍存活，CPU 和唤醒开销明显高于普通 3 秒轮询。
- 第三优先级：`/api/team/status` 的 3 秒读取。它包含网络请求、完整状态 JSON 解析、ETag 计算和
  React 状态更新。该路径统一改为 ETag 条件请求和 10 秒可见兜底；只有在基线归因证明其仍是显著
  热点时，才增加 Board SSE 事件驱动。
- 每个优先级单独实现、单独测量、单独回退；前一项未达到收益或出现稳定性问题时，不得继续扩大改造。

### R3 低成本路径不强制事件化

- sidecar `{ running, paused }`、任务操作列表、插件页和接入流程推送检查不因本任务强制移除轮询。
- 创建和改派本身不需要轮询；当前详情查询只用于显示异步 Agent 命令的进度和失败原因。除非实测
  证明它是显著 CPU 热点，本任务不要求为其新增 Board SSE 操作事件。
- 如果高成本路径已经建立可复用事件通道，可以把低成本状态作为同一事件的附带主题；
  不为单个低成本状态另建一套事件协议。
- 任务操作必须做两个低风险修正：`failed` 读取到终态后停止自动查询，用户显式重试时再恢复；
  操作列表定时器只在选中具体 taskSpace 时运行，相同结果不重复 `setState`。
- 对其他低成本路径可以先做无行为变化的最小优化，例如相同结果不重复 `setState`；
  只有测量显示 CPU 占比明显时才升级为事件驱动。
- 不以“前端源码中不再出现 `setInterval`”作为验收条件。

### R4 稳定性优先

- 事件只是“状态可能变化”的失效通知；REST 查询或 Tauri 查询仍是权威数据源。
- 初次加载、窗口重新聚焦、页面恢复可见、SSE 重连和 Tauri 监听恢复时各执行一次主动对齐，
  防止监听注册前或断线期间丢失事件。
- 事件必须按主题合并，避免一次任务批量变化触发大量重复读取。
- 请求进行中再次收到事件时，只保留一次后续刷新；旧响应不得覆盖新状态。
- 任何优化都不能改变任务正文同步、CAS、冲突处理、ownership、分支门禁、deferred 和 cursor 语义。
- 每个事件化路径必须可以单独回退到原轮询实现，不影响其他路径。

### R5 可观测与回归

- 记录修复前后 CPU、请求/Tauri 调用次数，以及事件触发后的界面更新时间。
- 自动测试覆盖事件合并、初始对齐、漏事件恢复、相同结果不重绘和请求竞态。
- 真实 Windows 客户端验证 Board、归档、控制窗口、本地关联和断线重连。
- 若 CPU 改善不明显，保留原实现并报告归因，不通过扩大事件化范围掩盖无效优化。

### R6 事件化范围

- 本地关联：使用 Tauri `desktop-state-changed` 事件，不新增服务端 SSE；可见页面保留 10 秒兜底。
- 控制窗口：使用 Tauri `live-control-changed` 事件；可见窗口保留 10 秒兜底，隐藏时停止。
- Team 状态：先使用 ETag 条件请求和 10 秒可见兜底；只有 A/B 测量证明它仍是显著热点时，
  才新增服务端 SSE `team.status.changed`。
- sidecar：附带在 `desktop-state-changed` 的 `sidecar` 主题中；可见页面保留 10 秒兜底。
- 创建/改派进度与任务操作列表：本轮不新增 SSE；只修正终态继续查询、空 taskSpace 定时器和重复
  状态更新。
- 插件页、接入推送检查：本轮保持原轮询，因为它们只在特定页面或对话框打开时运行。
- Agent 心跳、Agent SSE 重连、暂停状态等待、SSE 心跳、待执行命令补偿、插件健康检查、插件自定义
  定时器、每日备份和安装进度心跳：保持协议或后台运行机制，不改成 SSE 状态事件。
- “改成事件”不等于全部改成 SSE：浏览器/服务端状态变化使用 Board SSE，本地桌面状态使用 Tauri
  事件，进程存活和维护任务继续使用各自协议。

## Acceptance Criteria

- [ ] 采集并保存同一条件下的修复前、逐项修复后和最终组合 CPU 基线。
- [ ] 每个进入交付的事件化路径在空闲 30 秒内不再按固定间隔发起原有请求/Tauri 调用。
- [ ] 本地关联状态变化后，ProjectRail 在事件到达后更新，不依赖 3 秒轮询；漏事件最迟由 10 秒兜底补齐。
- [ ] 控制窗口收到队列变化事件后更新；空闲时不再每 750 毫秒读取待处理事件，漏事件最迟由 10 秒兜底补齐。
- [ ] 创建/改派仍可展示异步执行进度；操作进入 `failed/succeeded/cancelled` 后不再自动查询，
      用户显式重试 `failed` 操作时恢复查询。
- [ ] taskSpace 为 `all` 时不存在任务操作列表定时器，也不会周期性写入空数组。
- [ ] Team 状态始终使用 ETag 条件请求和 10 秒可见兜底；`304` 不更新 React 状态。
- [ ] 如果 Team 状态仍被确认是显著热点，则增加服务端事件后应用只发起一次条件请求。
- [ ] 本轮新增的服务端 SSE 事件不超过 `team.status.changed` 一个；本地关联和控制窗口只使用
      Tauri 事件。
- [ ] 窗口聚焦、页面恢复可见、SSE 重连和监听恢复时均可补齐期间遗漏的状态变化。
- [ ] 相同本地关联、sidecar、Team 状态或操作快照不会创建新的业务状态或触发重复渲染。
- [ ] 最终 Board 和归档页面在相同测量条件下 CPU 明显低于修复前基线，目标为 30 秒平均 `<2%` 单核，
      且不出现新的周期性尖峰。
- [ ] 若某候选路径经 A/B 测量没有明显 CPU 收益，该路径保持原实现并在报告中说明。
- [ ] 现有任务同步、冲突、ownership、deferred、分支门禁和断线恢复测试全部通过。
- [ ] 不新增服务端 Git、WebSocket、任务正文 SSE 或新的高成本后台扫描。

## Out Of Scope

- 为了“完全无轮询”而把插件页、接入推送检查、sidecar 或创建/改派进度整体改造成事件协议。
- 修改任务快照、ownership、冲突或 cursor 协议。
- 服务端接入 Git、WebSocket 或任务正文推送。
- 删除 Agent 心跳、SSE 心跳、插件健康检查、备份和维护型定时任务。
- 把 Agent 心跳、SSE 重连、命令补偿、插件健康检查或后台维护任务改造成 SSE 状态事件。
- 在没有 CPU 归因证据时重写大范围状态架构。

## Confirmed Decisions

- 本任务的唯一优化目标是降低 CPU 消耗。
- 稳定性优先于形式上的“完全去轮询”。
- 只有高成本热点值得改造成事件驱动。
- Team 状态、本地关联、sidecar 和控制窗口的可见兜底间隔固定为 10 秒；页面或窗口隐藏时停止。
- 用户自己的本地操作、窗口聚焦、页面恢复可见、SSE/监听重连继续立即刷新，不等待 10 秒。
- 行为恢复能力继续依赖初次加载、focus/visibility、重连和监听恢复的一次性主动对齐。
