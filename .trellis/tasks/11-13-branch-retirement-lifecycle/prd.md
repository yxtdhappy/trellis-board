# 分支弃用生命周期与安全移除

## Goal

让项目负责人能够把已经完全弃用的 taskSpace 从日常分支视图中移除，并在满足安全条件后彻底清除其服务端数据，避免项目分支列表随历史分支持续膨胀。

## Background / Confirmed Facts

- 当前 taskSpace 状态包含 `active`、`disabled`、`indexing`、`error`；`disabled` 只阻止写入，并不表示分支已弃用或应从列表中隐藏。
- `/api/team/status` 使用 `listStatusReadable()`，会包含 `disabled` taskSpace：[task-space-service.js](../../../apps/server/team/task-space-service.js:1166)。
- 项目栏直接遍历 `project.taskSpaces`，因此所有返回的 taskSpace 都会进入分支列表：[ProjectRail.tsx](../../../apps/web/src/components/ProjectRail.tsx:637)。
- 当前服务端只有客户端解绑和 binding 撤销，没有 taskSpace 硬删除接口；已有设计明确将“按分支批量硬删除 taskSpace”排除在解绑生命周期之外：[design.md](../../archive/2026-11/11-12-branch-listener-unbind-lifecycle/design.md:220)。
- 现有 `scripts/task-space-duplicate-cleanup.js` 的职责是清理重复任务和冲突，不是通用的分支弃用或 taskSpace 生命周期工具。
- `sync_task_space` 是 taskSpace 的聚合根，关联任务文件、binding、索引、命令、冲突、审计等数据；物理清除必须明确级联范围和不可逆风险。
- 服务端不管理真实 Git 分支。本任务移除的是 Board 中的 taskSpace 及其数据，Git 分支继续由 Git 管理。

## Requirements

### R1 区分分支生命周期状态

- `active`：正常显示、可关联、可创建和同步任务。
- `retired`：用户明确标记为已弃用；默认不出现在日常分支视图和任务操作选择器中，保留只读数据和恢复能力。
- `purged`：完成物理清除后不再存在；清除必须由显式管理员操作触发，并允许从 `active` 或 `retired` 状态直接执行，不设置固定保留期。
- 不能把“当前没有客户端监听”直接等同于“分支已弃用”。

### R2 弃用操作

- 项目负责人、团队管理员和系统管理员可以发起弃用，普通成员不能执行。
- 弃用前必须展示分支名称、任务数量、最后活动时间、当前监听数和本地关联数。
- 弃用后禁止新关联、创建任务、改派任务和同步写入。
- 弃用是可恢复的管理动作，不应立即删除任务、冲突、审计或其他服务端数据。

### R3 默认视图收敛

- 普通项目栏、创建任务和改派任务的分支选择器默认不显示 `retired` taskSpace。
- `retired` taskSpace 仅对项目负责人、团队管理员和系统管理员可见；普通成员不能看到对应的项目栏分支、任务选择或只读任务入口。
- 分支弃用、恢复和物理清除统一放在服务端管理台的项目页面，桌面客户端不提供这些管理操作。
- 服务端管理台必须提供“分支管理”区域，可查看活跃分支、已弃用分支、监听数、任务数和最后活动时间。
- 如果当前客户端仍关联某个已弃用分支，必须明确提示并停止同步，不能静默隐藏仍在工作的绑定。

### R4 物理清除资格

- `active` 和 `retired` taskSpace 都可以进入物理清除流程。
- 物理清除与弃用使用同一权限层级，项目负责人、团队管理员和系统管理员均可直接执行。
- 清除前服务端必须校验权限、taskSpace 状态和关联数据，管理台展示将要删除的数据摘要。
- 管理员在完成两次明确确认后可以立即执行清除，不要求等待固定天数，也不要求先单独标记为 `retired`。
- 在线监听和 approved binding 不阻断清除；服务端必须强制撤销全部 binding、取消进行中的命令并清理对应 cursor。
- 清除确认界面必须展示会被中断的在线客户端、绑定数和同步任务，避免管理员误判影响范围。
- 未归档任务不阻断清除；确认界面必须列出未归档任务数量和任务名称摘要，管理员确认后一并删除。
- 清理不要求所有客户端先解绑；所有客户端解绑和监听数为 0 只作为管理提示，不作为删除前置条件。
- 清除必须是事务性操作，并生成可追溯的清除审计和数据库备份。
- 清除不得影响同项目的其他 taskSpace。

### R5 独立操作

- 管理台同时提供“弃用”和“移除分支”两个独立操作。
- “弃用”只把 taskSpace 转为 `retired`，保留数据并支持恢复。
- “移除分支”不要求先弃用，经二次确认后直接执行物理清除。

### R6 恢复

- 在物理清除前，管理员可以恢复已弃用分支为 `active`。
- 恢复后分支重新进入默认视图，但不得自动恢复旧的客户端监听状态。

### R7 兼容和迁移

- 现有 `disabled` taskSpace 不能被静默当成已弃用数据删除。
- 迁移或上线后，已有 `disabled` taskSpace 必须由管理员明确选择“弃用”或保留，不自动物理清除。

## Acceptance Criteria

- [x] 管理员可以把一个没有继续使用需求的分支标记为 `retired`，之后普通项目栏和任务选择器不再显示该分支。
- [x] 普通项目成员完全看不到 `retired` 分支及其只读任务入口；管理者仍可从管理入口查看。
- [x] 桌面客户端不出现弃用、恢复或物理清除操作，这些操作只能在服务端管理台完成。
- [x] 服务端管理台的项目页面能查看分支监听、任务和活动时间摘要，并从这里执行弃用、恢复和物理清除。
- [x] 被弃用分支仍然可以在“已弃用分支”管理入口中查看，并显示任务数、最后活动时间和监听信息。
- [x] 已弃用分支无法被重新关联、创建任务、改派任务或同步写入。
- [x] 管理员可以只弃用分支而不删除数据，并在之后恢复它。
- [x] 管理员可以在物理清除前把已弃用分支恢复为 `active`；恢复不会自动恢复旧 binding 或监听状态。
- [x] 物理清除前必须展示数据摘要、权限校验结果和不可逆确认。
- [x] 管理员可以在标记弃用后立即执行物理清除，不要求等待固定保留期。
- [x] 管理员可以从 `active` 分支直接点击“移除分支”，经过二次确认后立即物理清除。
- [x] 项目负责人、团队管理员和系统管理员都能执行弃用、恢复和物理清除；普通成员不能执行。
- [x] 即使仍有在线监听客户端，管理员确认后仍可清除该 taskSpace；服务端会撤销全部 binding、取消命令并清理 cursor。
- [x] 即使仍有未归档任务，管理员确认后仍可清除该 taskSpace；确认页会展示任务数量和名称摘要。
- [x] 客户端解绑数不会阻塞管理员物理清除；管理员可以在仍有已关联客户端时强制删除。
- [x] 物理清除事务成功后，taskSpace 及其明确列出的关联数据消失；同项目其他 taskSpace 数据不受影响。
- [x] 物理清除前后都有可核对的审计和数据库备份记录。
- [x] 仅因客户端离线、监听数为 0 或心跳过期不会自动触发弃用或物理清除。
- [x] 现有 `disabled` taskSpace 不会在日常视图迁移时被静默删除。
- [x] Git 分支不会被服务端删除或改写。

## Out of Scope

- 自动删除真实 Git 分支。
- 仅凭无人监听自动物理清除 taskSpace。
- 自动合并不同分支上的任务内容。
- 删除同项目中的其他 taskSpace、项目权限或 Git 仓库。
- 在没有显式管理员确认的情况下清理历史审计数据。
