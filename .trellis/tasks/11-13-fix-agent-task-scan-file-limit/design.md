# Agent 任务扫描与上传批次边界设计

## 1. 目标边界

本次只修改 0.3 Rust Agent 的任务快照分组和实际上传校验边界。

不修改：

- Team 服务端 API。
- taskSpace 数据库 schema。
- 1024 文件、64 MiB、单文件 1 MiB 常量。
- 分支保护、CAS、冲突和 pending 协议。
- 单个超大任务目录的自动拆批。

## 2. 当前问题

`group_task_snapshot_files` 同时承担“结构分组”和“上传批次限额”两种职责。

它被全 taskSpace 扫描调用，因此 1561 个文件在按任务目录拆分前就被拒绝。服务端实际请求边界已经独立执行 1024 限制，Agent 只需在实际构造上传批次时保留同样保护。

## 3. 目标职责

### 3.1 `group_task_snapshot_files`

只负责：

- 路径规范化与单文件校验。
- 重复路径拒绝。
- 活动/归档混批拒绝。
- 按 `task_dir` 分组和排序。

移除：

- 全量文件数 `> 1024` 拒绝。
- 全量聚合正文 `> 64 MiB` 拒绝。

### 3.2 新的上传批次校验

增加单一纯函数，例如：

```rust
fn validate_upload_batch(files: &[Value]) -> AgentResult<()>
```

它只检查实际将写入 pending 或已经存在于 pending 的文件数组：

- 文件数最多 1024。
- 正文总字节最多 64 MiB。

调用位置：

- `upload_persisted_batch`：写 pending 前。
- `retry_pending_batch`：重试旧 pending 前。

这样不会先写入一个必然失败的 pending 批次，也能阻止旧 pending 无条件绕过限制。

## 4. 数据流

```text
全量扫描 1561 文件
  -> 校验每个文件和路径
  -> 按 task_dir 分成多个 SnapshotGroup
  -> 每次选择一个任务目录构造上传文件
  -> validate_upload_batch(该任务目录文件)
  -> 写 pending
  -> HTTP 上传
```

多任务目录合计超过 1024 可以正常同步；单个实际上传数组超过边界仍失败。

## 5. 错误语义

- 全量分组不再返回“单批任务文件不能超过 1024 个”。
- 实际上传数组超限时保留明确错误，并在可能时附带任务目录和当前文件数。
- 超限错误发生在 pending 写入前，避免形成无法自动恢复的超大 pending。
- 已存在的超大 pending 在重试时会明确失败，不静默丢弃或截断。

## 6. 测试设计

Rust 单元测试：

1. 1100 个文件分布在两个任务目录，每个 550 个，分组成功并返回两个 group。
2. 1024 个文件的实际批次通过 `validate_upload_batch`。
3. 1025 个文件的实际批次被拒绝。
4. 64 MiB 和 64 MiB + 1 字节边界由纯函数验证。
5. 重复路径、活动/归档混批等原有分组校验继续通过。

验证限制：

- 当前机器没有 `cargo`、`rustc` 或 `tauri`。
- 实施后先做源码与 Node 边界检查；Rust 编译需要具备工具链的 CI 或另一台机器完成。

## 7. 回滚

变更集中在 `task_sync.rs`。回滚时恢复：

- 分组函数中的全量限制。
- 去除新增的实际上传批次校验。

不需要数据迁移或服务端回滚。
