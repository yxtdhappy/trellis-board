# 修复桌面同步残留锁与托盘恢复状态

## Goal

桌面 Agent 在重启、异常退出或客户端重新打开后，不能因为残留单实例锁而长期无法恢复同步；托盘必须根据真实运行状态为用户提供唯一、明确的恢复入口。

## Background

### 本次现场

- 2026-11-12，Agent 最后一次心跳为 `14:22:52`，服务端随后记录 `ECONNRESET`。
- `14:23:41` 起新 Agent 连续 6 次以 `LOCKED` 退出；桌面端完成 5 次退避重试后主动停止自动重启。
- `14:39:32` 重新打开客户端后再次尝试 6 次，仍全部 `LOCKED`。
- 旧锁记录 PID `14592`、hostname `local`，当前机器名为 `Z0198-YHJ-E`；PID 已不存在但锁未回收。
- 移走旧锁后，新 Agent PID `27680` 成功启动，新锁 hostname 为 `Z0198-YHJ-E`，同步状态恢复为“运行中”。
- 托盘菜单固定显示“暂停同步”，没有“恢复同步”；通过两次点击同一菜单项分别切换暂停和恢复后才启动 Agent。

### 已确认根因

- R1：锁 metadata 使用 `process.env.COMPUTERNAME || 'local'`，见 `agent/lock.js:56`。
- R2：锁文件 hostname 与当前进程不一致时，代码不检查 PID 是否存活，而是在 24 小时内始终认为锁有效，见 `agent/lock.js:85`。
- R3：桌面重启先 `kill()` 旧子进程后立即启动新子进程，没有等待旧进程退出和释放锁，存在锁竞争窗口，见 `desktop/src-tauri/src/sidecar.rs:562`、`desktop/src-tauri/src/sidecar.rs:589`。
- R4：`LOCKED` 与普通崩溃共用 5 次重试上限；确定性锁冲突耗尽后监督器永久停止重启，见 `desktop/src-tauri/src/sidecar.rs:524`。
- R5：托盘菜单文案创建时固定为“暂停同步”，之后不更新，见 `desktop/src-tauri/src/main.rs:712`；切换逻辑只翻转 `paused`，未按 `running` 提供恢复动作，见 `desktop/src-tauri/src/sidecar.rs:575`。
- R6：Agent 被强制结束时不保证写入 `runtime.json` 的 stopped 状态，遗留的 `running` 与旧 PID 会误导诊断。

## Requirements

### R1 本地死锁可自动回收

- 锁文件位于当前用户本地 Agent 数据目录时，记录中的 PID 已明确不存在就必须能够回收，不得因历史 hostname 为 `local` 或其他不一致值等待 24 小时。
- PID 仍存活、检测返回 `EPERM` 或无法确认不存在时，不得删除锁。
- 必须避免仅凭 PID 回收时误删被系统复用的其他进程；采用能验证锁持有者身份或启动时间的机制。

### R2 重启与锁释放有序

- 终止旧 Agent 后，新 Agent 必须等待旧进程结束并释放单实例锁，或在有限窗口内自行重试接管。
- 正常关联成功后仍应触发一次受控重启，确保新 binding 开始首次同步；不能通过删除重启能力规避问题。
- 重启失败必须产生可定位的日志，且不能让桌面端误以为 Agent 已运行。

### R3 可恢复状态与崩溃退避分离

- `LOCKED` 属于可恢复的生命周期状态，不得与业务崩溃共用同一条“5 次后永久停止”的终态策略。
- 重试只能覆盖旧进程正在退出的短暂窗口，不能替代锁回收根因修复；确定性死锁必须在首次启动判断时清理或进入明确阻塞态。
- 重试耗尽后不得继续盲目拉起 sidecar；托盘必须保留一次点击即可重置退避并恢复的入口。
- 如果锁仍被真实存活进程持有，必须报告“同步被占用/锁未释放”，不得假装可以靠重复启动解决。
- 托盘“恢复同步”在任何情况下都必须能重置退避并立即尝试启动一次。
- 自动重启超过 5 次仍未成功时，桌面端必须主动弹出系统级模态框，明确提示连续重启失败，并提供“强制重启同步”按钮；弹窗不能只写日志或依赖用户主动打开托盘。
- “强制重启同步”必须防止重复点击和并发执行，执行后重置暂停/退避状态，并在成功或明确失败后给出结果。

### R4 托盘状态与动作一致

- Agent 正在运行且未暂停时，菜单显示“暂停同步”，点击后暂停。
- Agent 已暂停时，菜单显示“恢复同步”，点击后恢复。
- Agent 未运行但未主动暂停时，菜单显示“恢复同步”，点击一次即启动，不得要求用户点击两次。
- 菜单文案必须随状态变化，不要求重启客户端才能刷新。
- 启动失败时应保留“恢复同步”入口，不能在重试耗尽后失去可操作恢复动作。

### R5 强制重启恢复链路

- 强制重启必须至少依次完成：终止当前 Agent 进程组、等待进程退出、校验本地锁持有者、回收已死亡或已确认属于本次被终止进程的锁、重新启动 Agent、验证新 Agent 仍存活。
- 强制重启不得删除仍被无法确认状态的活进程持有的锁，也不得删除用户配置、凭证、任务数据或同步游标。
- 如果相关进程已退出但锁仍存在，允许将锁文件改名备份后再启动，便于后续诊断且避免永久阻塞。
- 只有新 Agent 启动并保持运行后，界面和弹窗才能显示“强制重启成功”。
- 如果服务端不可达、凭证失效、sidecar 缺失或锁仍被合法外部进程持有，必须保留明确错误和再次尝试入口；这些外部条件不能被“保证成功”掩盖。
- 用户点击“强制重启同步”后，如果 Agent 级强制重启仍未成功，允许自动重启整个桌面客户端作为最后一级兜底。
- 客户端重启只能由用户本次强制重启操作触发，不能由普通自动重试触发，避免形成无限重启循环。

### R6 可验证性

- 增加 hostname 不一致、PID 已死亡、锁未满 24 小时时的回收测试。
- 保留 PID 存活和 `EPERM` 时拒绝接管的测试。
- 增加“终止旧 Agent 后立即启动新 Agent”不会产生 `LOCKED` 的生命周期测试。
- 增加托盘菜单在运行、暂停、未运行三种状态下的文案与单击动作测试。
- 增加连续 5 次失败后只弹一次恢复模态框、强制重启防重入、进程终止等待、锁备份和新 Agent 存活校验测试。
- Windows 实际安装包必须验证：模拟锁阻塞后自动恢复或单击恢复成功，项目栏显示“运行中”。

## Acceptance Criteria

- [x] 死 PID 的本地锁即使 hostname 为 `local`、写入不足 24 小时，也能在首次启动时安全回收。
- [x] 活 PID 或 `EPERM` 场景仍拒绝接管，不误删有效锁。
- [ ] 关联成功触发的重启在旧进程退出阶段不再导致确定性的 `LOCKED`。
- [ ] 安全回收锁后，桌面端一次操作即可恢复 Agent，不需要移走运行时文件或连续点击两次。
- [ ] 托盘菜单按 `running/paused` 显示“暂停同步”或“恢复同步”，状态变化后下一次打开菜单即正确。
- [ ] Agent 未运行时点击“恢复同步”一次即可启动，并在项目栏显示“客户端后台：运行中”。
- [ ] 自动重启超过 5 次后自动出现“强制重启同步”模态框；点击一次只执行一条强制重启链路。
- [ ] 强制重启能终止当前 Agent 进程组、安全处理本地残留锁，并在新 Agent 存活后报告成功。
- [ ] Agent 级强制重启失败时自动重启桌面客户端；客户端重启后继续按正常启动与重试策略工作。
- [ ] 强制重启遇到真实外部阻塞时保留具体错误，不能误报成功或破坏配置、凭证和任务数据。
- [ ] 相关 Node、Rust 和 Windows 桌面验收通过，既有同步、关联和安装流程不回退。

## Out of Scope

- 不改变 tasks-only 快照、CAS 冲突、实时文件合并和命令协议。
- 不新增系统服务、第二套 sidecar 协议或跨机器共享锁。
- 不重构项目接入向导、登录流程或项目栏视觉设计。
- 不为历史多个客户端版本的运行时文件执行破坏性清理；只修当前版本可安全识别的状态。
