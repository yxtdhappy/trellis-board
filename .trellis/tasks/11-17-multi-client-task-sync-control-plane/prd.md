# 重构多客户端任务同步为上报与控制面分离

## Goal

消除多客户端下把所有活动任务正文写入每个本地仓库造成的未跟踪文件、重复任务和
活动/归档状态漂移；让客户端只上报本人已认领任务的变化，服务端负责 Board 实时事实、
任务归属、租约和归档生命周期，普通任务正文最终由 Git 收敛。

## Background

- 当前服务端把同一分支的活动任务快照下发给客户端，客户端直接写入
  `.trellis/tasks/**`，但不执行 Git 暂存；两人测试时已经产生同一任务的活动与归档
  双副本。
- 当前活动任务同步和 `archive/**` Git 导入是两条独立链路。归档提交可以从 Git
  活动目录移动到归档目录，但服务端活动快照没有自动形成删除墓碑。
- 当前 `/api/tasks` 和 `/api/tasks/assign` 都先要求被委派人存在唯一在线 Agent，
  再下发 `create_task`/`assign_task` 命令执行；被委派人离线时返回
  `AGENT_OFFLINE`，无法提前排队。
- 当前多人共享同一分支时，客户端只按活动状态和分支筛选任务，没有按任务认领
  状态限制本地落地范围，因此参与者越多，本地污染和并发冲突风险越高。
- 现有很多任务由用户和本地编码 Agent 直接通过 Trellis 在本地仓库创建，不经过
  Board 创建接口；服务端必须在收到该用户客户端上传的首次任务快照时建立权威任务
  记录，并让任务立即出现在 Board 上。
- Git 只能保证已完成提交、拉取和推送后的最终收敛，不能替代任务租约、离线命令、
  归档墓碑和旧客户端防复活。

## Confirmed Decisions

- 动态负责人、阶段、活动/归档状态以服务端数据库为唯一事实源。
- `task.json` 是客户端认领后生成和维护的工作副本，不再作为 Board 动态元数据的事实源。
- 服务端可以在没有任何目标客户端在线时先保存任务或委派记录，待目标客户端上线后
  再完成认领和本地落地。
- Git 负责任务文档的最终历史；服务端负责实时看板、控制状态和协调门禁。

## Requirements

### R1 内容数据面只上报

- 客户端只上传本人已认领或明确负责的活动任务变化。
- 服务端继续维护 Board 所需的标题、状态、负责人、阶段、更新时间、摘要和搜索投影。
- 非任务负责人的客户端默认不接收完整 PRD、设计、实施文档和附件正文。
- 普通任务正文在客户端之间通过 Git 获取，不再由服务端覆盖所有参与者工作区。

### R2 控制信息定向下发或按需拉取

- 服务端只向目标用户或目标客户端提供最小控制信息：任务 ID、归属、租约、状态、
  版本、认领结果和归档墓碑。
- 客户端不得因为收到控制信息就自动覆盖其他用户的完整任务目录。
- 完整任务内容仅在首次认领、明确接管、冷启动修复或用户主动查看时按需读取。
- Board 查询仍以服务端实时索引为准，不依赖所有客户端立即完成 Git pull。

### R3 支持离线创建与委派

- Board 创建或改派任务时，只要求被委派人属于项目可写成员，不要求目标 Agent
  当场在线。
- 服务端必须先创建可查询的任务记录和委派状态，而不是等待目标客户端执行
  `task.py create` 后才产生任务。
- 任务或委派先保存为服务端待交付状态，Board 立即显示负责人和
  `pending_delivery`/`等待客户端接管`。
- 被委派人下次登录或连接目标 taskSpace 后，获取属于自己的待交付任务并完成认领。
- 目标客户端确认落地后，状态收敛为 `claimed`/`materialized`；拒绝或超时后允许改派。
- 旧客户端、已撤销客户端和错误分支客户端不得把待交付或已改派任务重新写回。

### R3.1 本地 Agent 直接创建任务

- 用户和本地编码 Agent 在 `.trellis/tasks/**` 创建任务后，客户端通过现有 watcher
  在防抖周期内上传首次活动任务快照。
- 服务端首次接收该快照时创建 `sync_task` 权威记录：
  - `created_by_user_id` 使用已认证的客户端用户，不信任 `task.json.creator`；
  - 默认负责人为创建者，除非快照带有可验证的项目成员负责人；
  - 任务状态为已 materialized，因为创建者本地已经有完整任务目录；
  - 任务立即进入 Board，不要求创建者再通过 Board 创建接口。
- 本地任务可以由创建者自己完成，也可以在 Board 或本地 Agent 中委派给项目其他
  可写成员。
- 委派给他人时，服务端更新权威负责人，为目标用户生成待认领控制信息；不向所有
  客户端广播完整任务正文。
- 创建者本地副本保留，直到收到任务归档或明确的清理确认；其写权限由租约和最新
  负责人决定。

### R3.2 委派完成后的创建者副本清理

- 委派目标认领任务后，不能仅凭“目标本地已生成目录”删除创建者副本。
- 目标客户端必须先把完整任务内容上传到服务端，服务端完成摘要、版本和索引校验后，
  才允许进入创建者清理阶段。
- 清理采用可恢复的两阶段确认：
  1. 目标进入 `materialized` 并提交本次 materialization 的 task version、文件
     摘要和上传 revision；
  2. 服务端将 handoff 标记为 `source_cleanup_pending`，向创建者发送轻量清理通知；
  3. 创建者检查本地副本是否由 Agent 管理、是否未修改、是否未被 Git 跟踪；
  4. 满足条件时删除本地活动副本并 ACK；不满足时保留副本或移动到备份并报告冲突。
- 对“Agent 管理、未被 Git 跟踪、内容未修改”的创建者副本，默认允许自动删除；
  删除前写入轻量备份和审计记录，不要求用户逐次确认。
- 目标完成认领和 materialization 后，创建者客户端显示“任务已被认领”的单向通知：
  - 不需要创建者确认；
  - 不打开模态窗或控制窗口；
  - 不聚焦、不激活、不提升主窗口；
  - 不阻塞键盘、鼠标或当前编码 Agent；
  - Board 窗口可见时使用页内 toast，隐藏或最小化时使用系统通知；
  - 同一 handoff 状态只通知一次，重复事件按幂等键去重。
- 通知失败或系统通知权限不可用不能阻塞 handoff 清理；创建者下次打开 Board 时显示
  非阻塞状态提示。
- 创建者离线时清理状态持久化，下次连接继续执行，不依赖创建者当时在线。
- 被 Git 跟踪的任务文件不得由该机制静默删除；必须走 Git 明确变更或用户确认流程。
- 清理完成后服务端记录 handoff 完成，Board 不再把创建者视为可写副本。

### R4 任务级写租约

- 同一任务同一时间只能有一个客户端持有写租约。
- 租约包含用户、客户端、taskSpace、任务 ID、获取时间、心跳时间和过期时间。
- 心跳过期后允许其他授权客户端申请接管；旧客户端恢复连接后只能只读或进入冲突确认。
- 租约必须阻止同一用户的两个设备或不同用户同时修改同一任务。

### R5 归档生命周期

- 任务归档必须形成统一状态迁移：活动快照、Board 活动索引和客户端本地活动副本
  不能继续表现为正常活动任务。
- 服务端必须生成活动任务删除墓碑；归档 Git 索引与活动索引不能长期同时出现同名
  活动/归档行。
- 客户端收到归档墓碑后，只删除由 Agent 管理且未修改的本地活动副本。
- 本地存在未提交修改时，先保留冲突备份并提示用户，不得静默删除正文。
- 持有有效写租约时，归档必须先释放租约或由用户确认；未完成写入不能被无提示覆盖。

### R6 Git 最终收敛与旧写保护

- 客户端执行 Git pull 后应得到已提交的任务文档和归档历史。
- 服务端根据任务版本、摘要、所有权和活动状态拒绝旧客户端上传的过期或已归档任务。
- Git 冲突仍由标准 Git 流程处理；服务端不得把 Git 冲突误判为可静默覆盖的普通同步。
- 客户端长时间离线和 Git 未拉取时，Board 必须显示本地版本可能落后，不能宣称实时一致。

### R7 迁移、清理与可观测性

- 升级时必须识别现有“活动目录已未跟踪、同名归档已跟踪”的重复副本。
- 自动清理只允许处理可证明来自旧服务端活动快照且内容未变化的副本；其他情况保留
  备份并进入人工确认。
- Board/客户端状态必须区分：正常、待交付、待认领、已认领、租约过期、版本落后、
  pending 等待、冲突和已归档。
- 诊断信息不得包含任务正文、Token、Cookie、私钥或完整本机路径。

## Acceptance Criteria

- [ ] 两个客户端连接同一 taskSpace 时，客户端 A 修改自己认领的任务，客户端 B
      的工作区不会新增或覆盖该任务正文，B 的 Board 能在目标延迟内看到最新元数据。
- [ ] 同一个项目的多个活动任务不会自动写入所有参与者的 `.trellis/tasks/**`；
      非本人任务只可通过 Board 远程查看，或在明确认领后按需落地。
- [ ] 被委派人离线时仍可在 Board 创建并委派任务，任务立即显示为待交付；目标用户
      上线后能够只拉取属于自己的待交付任务并完成认领。
- [ ] 用户和本地 Agent 直接创建任务后，创建者客户端能在正常防抖和网络延迟内把
      任务元数据上传到 Board；创建者可以自己继续完成，也可以委派给项目其他成员。
- [ ] 本地创建的首次快照必须使用认证用户作为 creator；即使 `task.json.creator`
      被伪造，也不能改变服务端创建者身份。
- [ ] 创建者委派给目标用户后，目标完成 materialization 和内容上传，创建者收到
      清理状态；未修改的 Agent 管理且未跟踪副本被自动备份后删除，已修改或 Git
      跟踪副本不会被静默删除。
- [ ] 创建者离线时，handoff 清理状态持久化；创建者重新连接后继续收到一次性清理通知。
- [ ] 创建者收到“任务已被认领”通知时不出现确认框、不切换页面、不抢焦点；
      通知重复事件不重复弹出，系统通知不可用时仍有页内状态。
- [ ] 同一任务被两个客户端同时修改时，只有租约持有者可以写入；另一客户端得到
      明确的租约冲突或可申请接管状态。
- [ ] 任务归档后服务端活动索引、活动快照和归档索引收敛到唯一定义，不再长期同时
      展示活动和归档两份状态。
- [ ] 客户端本地活动副本未修改时，归档墓碑可安全清理；存在本地修改时保留备份并
      提示用户确认。
- [ ] 离线较久的客户端重新连接并尝试上传旧版本或已归档任务时，服务端拒绝复活，
      本地数据不丢失且可恢复。
- [ ] 现有两人测试产生的两个活动/归档重复副本可以按迁移规则识别，清理前后均有
      可审计记录，不误删用户正文。
- [ ] 关闭服务端完整任务正文下发后，日常同步请求只包含必要的元数据、控制信息和
      本人任务内容；全量快照只作为显式修复路径。
- [ ] 单元测试、服务端/Agent HTTP 测试、桌面 Rust 测试、Web 类型检查和真实双客户端
      E2E 覆盖上述主路径与失败恢复。

## Out Of Scope

- 不在本任务中重写 Trellis `task.py` 的阶段推导规则。
- 不在本任务中把所有任务迁移成纯数据库对象并彻底取消 Git 文件。
- 不为普通 HTTP Git 服务实现通用远端写协议。
- 不自动解决 Git merge/rebase 冲突。
- 不在本任务中清理与多客户端任务同步无关的历史冲突数据。
