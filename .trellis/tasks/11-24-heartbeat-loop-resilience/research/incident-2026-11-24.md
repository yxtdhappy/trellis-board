## 症状

服务端重启（停机约 11 秒）后，Board 分支页「在线监听」从 1 掉到 0，状态栏显示「当前未激活，关联保留」；四位成员的绑定仍是「已批准 / 已关联 4」。同一进程的客户端**仍在同步**（上传、ownership 校验正常），但服务端 `agent_device.last_seen_at` 不再前进。重启客户端进程即可恢复。

- 06:39 UTC 那次重启：三台客户端 `last_seen_at` 同时冻结在 `06:39:25`–`06:39:36`。
- 08:41 UTC 那次重启：本机与 KYF 的客户端冻结，之后 6 分钟无任何恢复。

## 推断

`write_state`（`runtime.rs:596-606`）不去重，心跳每次失败都会重写 `runtime.json`；成功心跳会推进 `last_seen_at`。两者同时停止 ⇒ 08:41:18 之后**心跳循环既没成功也没失败**，即已经停摆，而不是“在退避重试”。

`[profile.release] panic = "abort"`（`packages/desktop/src-tauri/Cargo.toml:68`）意味着 panic 会终止整个进程；客户端进程存活且持续同步，故排除 panic，结论是**心跳任务永久阻塞在某个 await**（最可能是 `heartbeat_once` 里的 `task_sync.update_bindings`）。

## 已排除

| 假设 | 排除依据 |
| --- | --- |
| 服务端未恢复/不健康 | `/api/health`=200，SSE 连接在，重启后上传成功 |
| 认证失败 | 认证分支会写 `AUTH_REVOKED` 并 `stop()`；实际状态是无错误码的网络错误 |
| 网络/代理 | 同一进程重启后上传、拉取、事件全部正常 |
| 分支/仓库不一致 | 5 个绑定仓库的 HEAD 与绑定分支逐一核对一致 |
| 配置/游标锁残留 | 无 `.config.lock`、`.live-cursors.lock`，`live-cursors.json` 仍在更新 |
| 用户暂停 | `toggle_pause` 会 `stop_runtime()` 并写 `stopped`，现场不符 |
| git 子进程卡死 | 系统中无 git 进程 |
| panic | release `panic=abort`，进程存活 |
