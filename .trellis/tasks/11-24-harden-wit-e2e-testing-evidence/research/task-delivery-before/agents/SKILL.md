# Trellis Task Delivery

运行条件：目标仓库包含 `.trellis/scripts`；端到端验证需要 `wit-e2e-testing` Skill；UI E2E 还需要可用的 Chrome MCP/浏览器工具。

把 Trellis 任务从需求评审推进到可验收、可提交、可归档的完整交付。这个技能的价值在于守住顺序：计划确认前不编码，代码检查通过前不让用户重启，真实 E2E 通过前不提交。

## 核心原则

- 先查证任务与权威需求，再决定创建或复用任务。任务创建批准不等于实施批准。
- 把需求、设计、实施和 E2E 证据写到文件，聊天上下文可能被压缩，文件不会。
- 一次只推进一个可独立验收的任务。复杂需求拆父任务和子任务，依赖写进子任务文档。
- 开发期间不反复构建。全部代码写完后再统一做一次完整测试和编译。
- 质量检查必须在首次真实重启之前完成，避免用户重启半成品。
- 真实 E2E 必须使用 `wit-e2e-testing`；页面存在时接口 E2E 和 UI E2E 都要做。
- E2E 通过后再提交，提交后再归档。不要在验收前制造“已完成”的假象。

## 0. 判定运行模式

先确认当前工作模式，后续步骤依赖它：

- **默认模式**：代码检查通过后停止，等待用户手动重启最新服务。用户回来后再执行 E2E。
- **连续模式**：只有用户明确说“不要停”“你自己启动”“由你重启并继续 E2E”时，才可在授权范围内启动/重启本地服务。
- **Inline 模式**：工作流标记为 `codex-inline` 时，主会话直接实施和检查，不派发 implement/check 子代理。
- **Sub-agent 模式**：工作流要求时，按顺序派发 `trellis-implement` 和 `trellis-check`，主会话负责规划、门禁、重启、E2E、提交和归档。

连续启动权限只覆盖当前任务需要的服务和端口。不要扩大到无关服务，也不要删除未知进程。

## 1. 建立 Trellis 上下文

1. 运行：

   ```bash
   python ./.trellis/scripts/get_context.py
   python ./.trellis/scripts/get_context.py --mode phase
   python ./.trellis/scripts/get_context.py --mode packages
   ```

2. 检查当前任务、状态、git 工作区和最近提交。
3. 读取 `AGENTS.md`、Trellis workflow、相关 spec 索引和共享指南。
4. 识别已有任务，优先复用；只有没有合适任务且用户同意时才创建。

请求属于简单对话或小改动时，只询问是否需要创建 Trellis 任务。用户说不需要就不要为了流程而创建任务。

## 2. 评审并收敛任务

### 2.1 找权威需求

按以下顺序找事实：

1. 用户当前明确指令。
2. 权威研发对齐版 PRD、接口文档、页面原型和目标仓库代码。
3. 父任务设计、现有子任务 PRD/design/implement。
4. 历史任务归档、E2E 报告和 Trellis spec。

不要因为任务目录里已有 PRD 就默认它是最新需求。检查权威路径、版本冲突、过时假设和相互依赖。

### 2.2 收敛范围

把内容拆开写：

- `prd.md`：目标、范围、业务规则、验收标准、依赖、不做项。
- `design.md`：架构边界、数据模型、接口契约、数据流、事务、兼容、风险和回滚。
- `implement.md`：有序实施步骤、每步验证点、最终测试命令、重启/E2E/清理计划。
- `implement.jsonl` / `check.jsonl`：相关 spec 和研究文件，不列即将修改的代码文件。
- `research/*.md`：关键技术调研、框架源码结论和未决问题。

复杂任务缺少 `prd.md`、`design.md` 或 `implement.md` 时不得启动实施。涉及数据库、接口、跨层字段、鉴权、异步或 E2E 时，设计文档必须给出可执行契约。

### 2.3 规划评审门禁

完成文档后给出简短评审摘要：

- Goal
- In scope
- Out of scope
- Acceptance criteria
- Key decisions
- Risks
- 将修改的模块和测试边界

等待用户明确确认后再运行 `task.py start`。如果用户在同一轮已经明确写出“确认实施”且要求使用当前已收敛文档，可直接进入实施，但仍要先保存文档。

## 3. 激活任务

1. 校验任务上下文：

   ```bash
   python ./.trellis/scripts/task.py validate <task-dir>
   ```

2. 启动任务：

   ```bash
   python ./.trellis/scripts/task.py start <task-dir>
   ```

3. 读取 Phase 2 step detail，并按项目工作流派发实施或直接实施。

子代理派发提示必须以 `Active task: <task path>` 开头，并明确其角色，禁止 implement/check 子代理互相再派发同类代理。

## 4. 实施

开始修改前，加载 `trellis-before-dev` 或执行工作流要求的等价步骤。先列出修改边界：

- 当前行为与目标行为的差距
- 行为真正所在层
- 必须修改的文件及原因
- 明确不做什么
- 会破坏哪些调用方、测试、fixture、配置或导出

实施要求：

- 优先复用现有模式、组件和公共能力。
- 最小修改解决问题，不添加未被需求要求的功能和抽象。
- 数据库、接口和前端字段必须围绕同一契约收敛。
- 后端完成时同步处理调用方和测试；前端页面存在时完成最小 API 适配。
- 新增非平凡逻辑要有可抓住回归的测试。
- 开发阶段不做反复 Maven 编译或前端 build。只在全部开发完成后的代码级验证阶段统一执行。

## 5. 代码级验证与质量检查

### 5.1 分层验证

全部实现完成后，按项目命令一次执行：

- 后端聚焦测试
- 后端模块编译或 type-check
- 前端单元测试
- 前端 type-check/build（如果页面存在）
- SQL、配置、脚本语法检查

验证结果必须可引用：测试数量、失败数、命令退出码、构建产物或时间戳。

### 5.2 Trellis 质量检查

按工作流派发 `trellis-check` 或加载 check skill，对照：

- `prd.md`
- `design.md`
- `implement.md`
- 相关 backend/frontend spec
- 跨层数据流和调用方

检查发现问题时直接修复，并重跑受影响测试。检查后若又修改了编译代码，必须重新执行对应构建。

### 5.3 重启前门禁

只有同时满足以下条件才允许用户重启：

- 规划文档已确认
- 实施完成
- 聚焦测试通过
- 模块编译/type-check 通过
- 最终质量检查没有未处理阻塞项
- 工作区没有混入无关任务改动

记录“代码侧已绿”的证据，再进入重启阶段。

## 6. 启动或等待最新服务

### 6.1 默认：停下等待用户

停止当前轮次，明确告诉用户：

- 当前代码/测试状态
- 需要重启的服务和端口
- 如何判断是新进程：PID、启动时间、启动完成日志
- 用户重启后需要回复什么，才能继续 E2E

不要在用户尚未重启时用旧服务执行 E2E。

### 6.2 连续模式：由 AI 启动

只有用户明确授权后才启动：

1. 只读确认端口和现有进程。
2. 确认要停止的进程确实属于当前服务，记录旧 PID。
3. 用最新编译产物启动服务；后台进程使用隐藏窗口。
4. 核对新 PID、监听端口、启动时间和关键启动日志。
5. 确认 Flyway、迁移、鉴权和入口正常。
6. 若启动失败，先修复启动问题；不要把环境失败误报成 E2E 失败。

不得使用未授权的大范围进程终止或破坏性命令。

## 7. WIT 接口与 UI E2E

加载 `wit-e2e-testing`，先做前置检查：

- 被测版本真的是最新进程
- 前端、后端、鉴权入口可达
- 日志源明确
- 测试数据前缀、创建方式和清理方式明确
- 探针数据使用正确租户字段
- 页面存在时确认使用哪种浏览器工具

### 7.1 单步闭环

每一步严格执行：

1. 记录日志偏移。
2. 执行一次接口请求或页面操作。
3. 读取对应增量日志。
4. 确认请求出现、结果成功/失败、没有未捕获异常。
5. 再核对接口响应、页面状态和数据库结果。
6. 把证据写入 E2E 报告。

不要连续执行多个操作后再一起看日志，否则无法归属证据。

### 7.2 用例覆盖

至少覆盖：

- 正向：核心流程可用
- 反向：非法输入、业务限制、权限或不存在目标
- 回归：相邻查询、分页、状态切换或已有页面
- 对照：关键计算、租户过滤或数据一致性

接口 E2E 始终要做。存在 UI 页面时还必须做 UI E2E。优先使用现有 Chrome MCP/浏览器工具；没有明确必要，不额外引入 Playwright。

### 7.3 数据与清理

- 统一使用 `E2E_` 或任务专属前缀。
- 写数据库前确认目标表、租户和字段。
- 每轮结束清理探针并再次查询确认。
- token、密码、Cookie 和 Secret 不出现在回复、报告、提交或日志摘要中。

## 8. E2E 缺陷修复循环

E2E 发现问题时：

1. 先分类为环境/脚手架问题或被测代码缺陷。
2. 真缺陷要修根因，不绕过调用方。
3. 补一条能抓住该缺陷的回归测试。
4. 重跑代码级验证。
5. 重新启动最新服务。
6. 用同一路径复测到通过。
7. 更新 E2E 报告和任务文档。

若代码变化，继续沿用旧 PID 的 E2E 结果无效。

## 9. 报告、Spec、提交

### 9.1 E2E 报告

在任务目录写 `e2e-report.md`，包含：

- 环境、进程、端口、日志路径和版本生效证据
- 测试数据策略
- 每步操作、日志、响应/UI、数据库和结论
- 自动化测试与构建结果
- 已知限制
- 清理结果

### 9.2 Spec 同步

加载 `trellis-update-spec`。出现新接口、数据库迁移、跨层契约、非显然坑或新约定时，必须写回 `.trellis/spec/`。

### 9.3 提交

只有在 E2E 通过后才提交。用户已明确要求提交时，可直接准备提交计划；否则先请求一次确认。

提交前：

- 检查 `git status --porcelain`
- 只暂存当前任务文件
- 排除其他并行任务、用户手工改动和无关未跟踪目录
- 检查 staged diff 和秘密信息
- 不 push，除非用户明确要求

提交顺序：

1. 工作提交
2. 任务归档提交
3. 会话日志提交

## 10. 收尾

工作提交完成后执行 `trellis-finish-work`：

- 检查已完成任务
- 区分当前任务和并行任务脏文件
- 归档当前任务
- 用工作提交 hash 记录 journal
- 最终确认 git log 顺序和当前活动任务状态

## 停止点

遇到以下情况停止并请求用户决定：

- 需求文档冲突或缺失，无法定义可验收行为
- 需要创建任务但用户尚未同意
- 规划文档未评审，用户尚未确认实施
- 实现需要扩大范围到其他业务域
- 默认模式下代码检查已通过，等待用户重启
- E2E 需要未授权的数据写入、服务重启或外部系统变更
- 当前任务与其他并行任务改动无法安全区分

## 最终报告格式

使用以下结构，保持简洁：

```markdown
已完成：<一句话结果>

实施：
- <核心变更>

验证：
- 代码级：<测试/编译结果>
- 接口 E2E：<结果>
- UI E2E：<结果或不存在页面>
- 数据清理：<结果>

提交：
- <工作提交 hash>
- <归档提交 hash>
- <日志提交 hash>

风险/限制：
- <仍需后续处理的问题>
```

## 常见错误

- 先写代码再补 PRD、design、implement。
- 用旧的后端进程做 E2E，却声称测试了新代码。
- 把质量检查放在用户重启之后，导致发现代码问题时还要再次重启。
- 只看页面或响应正常，不核对对应日志。
- 接口 E2E 通过就漏掉 UI E2E。
- E2E 失败后只改测试脚本，不判断是否为真实代码缺陷。
- E2E 探针没有统一前缀或没有清理。
- 提交时 `git add .`，把其他并行任务和用户改动一起带走。
- 把多个修复反复 amend 到旧提交；除非用户明确要求，不要改写历史。
