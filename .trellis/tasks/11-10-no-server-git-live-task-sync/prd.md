# 服务端无 Git 实时任务同步

## Goal

彻底替换 Team Board 的“服务端接触项目 Git”运行模式：由客户端提供并持续更新
`.trellis/tasks/**`，服务端持久化任务快照、生成任务索引并向其他客户端广播，从而消除服务端
Git 克隆、拉取延迟和旧实时路径回灌问题，同时保留客户端自身的 Git 工作流。

## Background

### 已确认事实

- 当前 Team Board 同时维护两条独立链路：
  - 客户端 Agent 将 `.trellis` 实时文件上传到服务端 SQLite 实时覆盖层；
  - 服务端维护项目 Git 稀疏克隆，默认每 60 秒 fetch/fast-forward，然后扫描任务。
- Team Board 页面展示的是“服务端 Git 克隆 + SQLite 实时覆盖层”合并后的结果，不是客户端
  工作区的实时镜像。
- 服务端 Git 当前还承担项目接入、基础任务扫描、Web 端任务创建/接受/修改、commit/push、
  分支和工具链校验等职责。
- Board Web 端创建、接受或修改任务时，服务端在 Git 克隆中调用项目自己的 `task.py`，
  然后 commit 并 push 到项目远端。
- 修复前，服务端清理实时覆盖层时只在同一路径内容与 Git 一致或同一路径两边都删除时收敛，
  不识别任务从普通目录移动到归档目录；本次已补齐该收敛路径。
- 客户端启动已关联项目时会从 `afterRevision: 0` 全量拉取服务端实时文件，未优先使用
  已持久化的本地游标。
- 2026-11-10 的实际事故中，本地已完成任务归档但尚未 push，服务端仍停留在未归档提交；
  客户端重启后全量应用旧实时文件，重新创建了未归档 PRD 并显示冲突。
- “服务端最新 revision”是项目级实时批次编号，不等于某个任务文件比本地 Git 版本更新。
- 当前实现中用户账号和 Agent 设备不是一对一关系：每次新安装、强制新建或在不同机器登录，
  都可能生成新的 `agent_device`；一个设备可分别绑定多个项目。
- 当前代码没有“一个用户只能有一个有效 Agent 设备”的数据库约束，管理页按设备展示并支持
  单独撤销。
- 当前本地数据库中同一用户已有多个历史 Agent 设备记录，其中存在同一设备名但不同设备 ID
  的重复绑定，因此任务执行目标不能默认等同于用户账号。
- 新设备无法继承旧设备保存的本地仓库绝对路径；项目成员权限可以属于账号，但“哪个本地目录
  对应哪个 Team Board 项目”的物理绑定必须在当前设备重新建立并校验远端身份和分支。
- 当前 Board 写操作中，只有创建任务和改派任务依赖服务端 Git 修改项目文件；计划字段、
  阶段检查点、依赖、撤销均只写服务端 SQLite，接受任务只更新委派状态，不需要下发 Agent 命令。
- 当前 Agent 的 `sync_branch` 使用整仓 `git status` 判断 clean；工作区任意未提交或未跟踪
  文件都会阻止同步。该规则适合全仓 fast-forward，不适合只新增或修改指定任务目录的命令。
- `.trellis/scripts/**` 是可执行工具链，`.trellis/config.yaml` 可声明生命周期 hooks，
  两者改变后会影响客户端实际执行逻辑；当前服务端会对 `.trellis/scripts` 计算工具链摘要。
- `.trellis/spec/**`、`.trellis/workflow.md` 和 `.trellis/agents/**` 是团队共享的项目规范、
  工作流和 Agent 提示词，应当保持一致，但属于需要评审和版本记录的项目文件。
- Codex、OpenCode、Pi 等工具适配目录位于仓库根目录，不是共享的 `.trellis` 任务数据。

### 已知约束

- 客户端项目仍可能使用 Git 管理源码、任务历史、分支和团队协作。
- 服务端不再读取项目 Git 后，仍必须支持首次项目接入、浏览器刷新、任务索引重建，
  以及新客户端或离线客户端重新获取完整任务状态。
- 广播本身不能充当持久化状态；服务端必须保存可恢复的任务快照和可重放的变更顺序。
- 不能在没有替代机制的情况下静默丢失 Web 端任务操作、离线修改或多客户端冲突。

## Requirements

- 服务端不再负责创建或初始化项目；项目由客户端选择本地 Git 仓库后发起接入。
- 客户端只能接入 Git 仓库根目录，禁用普通目录和 Git 子目录。
- 客户端以规范化后的 Git 远端地址作为项目身份；协议、用户名、默认端口和 `.git` 后缀等
  等价差异归一为同一个项目。
- 任务同步空间以“规范化 Git 远端 + Git 分支”为唯一键；同一仓库不同分支各自维护独立的
  `.trellis/tasks`，不得互相聚合或广播。
- Team 模式的任务列表必须选择具体任务空间，不把同一仓库不同分支的任务卡或 revision 混合在一起。
- 客户端绑定固定的 Git 分支和任务空间；外部切换分支时本次只提示风险，不自动接管、迁移 pending
  批次或修复切换后的任务污染。
- 客户端同步未完成时必须显示醒目提示，告知用户此时切换 Git 分支可能造成任务错位或污染，
  建议等待同步完成后再切换。
- 本次不禁用分支切换入口、不阻止终端或 IDE 中的外部切换，也不实现切换后的自动恢复或
  污染修复；只提供明确风险提示。
- 规范化 Git 远端与分支组成的任务空间在服务端全局唯一，不按团队复制；团队和项目成员只用于
  控制项目可见性与操作权限。
- 客户端首次创建全局任务空间时，用户从所属团队中选择归属团队，默认使用当前团队；该团队
  成为项目所有者，同团队成员按项目角色访问。
- 其他团队接入相同任务空间时不得直接获取任务内容，只能看到“项目已存在，需要访问授权”；
  所有者邀请后加入同一个全局任务空间，不创建重复项目。
- 如果本地仓库没有 `.trellis`，客户端明确提示需要初始化；用户多选本机需要的编码 Agent
  工具后，由客户端执行项目自己的 Trellis 初始化流程。
- 如果本地仓库已有 `.trellis`，跳过初始化，直接校验并同步任务。
- 新初始化仓库在首次 Git 推送前保持“等待推送”状态；客户端通过比较本地 `HEAD` 与
  `git ls-remote origin refs/heads/<branch>` 的 SHA 判断是否推送成功。
- 首次推送确认还必须验证初始化文件已进入当前 HEAD，且相关共享初始化路径没有未提交文件；
  网络不可达时只能显示“无法确认”，不得判定为未推送。
- 编码 Agent 配置属于客户端本机：同一项目允许不同客户端选择不同工具，同一客户端也可以
  后续增加或切换多个编码 Agent，不要求所有客户端一致。
- 客户端安装包必须携带固定版本的 Trellis CLI 和 Node 运行环境，缺少 `.trellis` 时由当前客户端
  离线执行初始化，不要求用户预装 `trellis`/`npx`，也不调用服务端初始化项目。
- 客户端首次关联项目时上传完整 `.trellis/tasks/**` 任务快照；后续上传增量文件操作。
- 服务端在 SQLite 或等价持久化介质中保存当前快照、文件摘要、删除墓碑和任务空间级 revision。
- 服务端只保存当前 tasks 快照、删除墓碑、变更审计、来源信息、冲突双方备份和定期备份；
  不建设完整的任务文件历史或任意 revision 回滚界面，历史版本由客户端 Git 负责。
- 服务端直接基于持久化快照扫描任务、构建 Board 并广播变更，不再 fetch/push 项目 Git。
- 服务端只接收 `.trellis/tasks/**`；spec、scripts、config、workflow、agents、workspace、
  `.developer` 和编码 Agent 适配目录均不进入实时同步协议。
- 客户端自身仍可正常 commit/push 到项目 Git 远端，服务端不代理 Git 凭据。
- 服务端把相同 Git 项目的各客户端任务内容整合为一份项目快照，并广播给该项目的其他客户端，
  使相同项目的客户端看到同一组 Trellis 任务。
- 服务端任务扫描不得依赖未上传的 `.trellis/scripts`、`.trellis/spec`、config、workflow、
  workspace 或 `.developer`；这些内容的一致性、评审和版本管理完全由客户端 Git 负责。
- Web 端创建带负责人的任务或改派任务时，服务端只校验并下发 Agent 命令；实际任务初始化、
  `task.py create`、负责人修改和文件写入全部由被委派用户的客户端 Agent 执行。
- 接受创建/改派命令的 Agent 必须属于被委派用户、已绑定目标项目、绑定已批准且当前在线。
- 一个用户账号同一时刻只能有一个有效 Agent。重复安装、换设备或显式新建设备后，
  新 Agent 生效时必须撤销旧设备凭证、停止旧设备事件流并取消其待执行命令。
- 设备替换后保留用户的项目成员权限，但旧设备项目绑定不得直接作为新设备可用绑定；
  新设备重新选择并校验本地仓库后，项目才能接收任务创建/改派命令。
- 换设备后的项目恢复采用用户手动逐个选择本地仓库，不做磁盘扫描或项目的自动发现。
- Agent 执行成功后通过现有实时文件同步链路上传任务文件，服务端基于上传内容更新 Board。
- 目标 Agent 不在线或没有可用项目绑定时，服务端拒绝本次创建/改派并返回可操作的原因。
- 创建/改派命令使用独立“操作项”展示进度，不向正式任务索引插入临时任务或伪造任务 ID。
- 创建操作至少区分待投递、已投递、成功、失败和取消；失败后允许使用同一幂等键重试或取消。
- 改派操作成功前继续保留原负责人并显示“改派中”；创建成功后正式任务才通过实时文件同步出现。
- 创建/改派不得因仓库其他无关文件未提交而直接拒绝；安全检查应限定到命令实际影响的路径。
- 创建任务时允许无关源码和其他任务存在未提交修改，但目标新任务目录不得冲突。
- 改派任务时要求目标任务目录 clean 且本地任务版本与服务端快照基线一致；其他路径可以 dirty。
- 所有命令仍必须校验仓库根、origin、当前分支，以及不存在进行中的 merge/rebase/
  cherry-pick/revert 等 Git 操作。
- 任务文件写入采用文件级乐观锁：每个更新或删除携带服务端基线摘要，当前摘要不一致时
  返回冲突，不得后写覆盖。
- 同一 Agent 批次涉及多个文件时使用单个事务校验和写入；任一文件基线过期则整批拒绝，
  不允许只写入部分任务文件。
- 冲突响应必须包含任务名称、相对路径、服务端当前 revision、服务端最后修改人、
  最后修改设备、修改时间、客户端基线和可执行的处理建议。
- 冲突提示使用用户可理解的语言，不直接展示无解释的 SHA、HTTP 状态码或内部错误码；
  内部标识可以放在展开的技术详情中。
- 冲突后提供四个明确动作：查看差异、使用服务端版本、用我的版本覆盖、仅保存本地副本。
- “使用服务端版本”和“用我的版本覆盖”都必须在操作前自动备份双方版本；“覆盖”需要二次
  确认并记录审计日志。
- 第一版不自动合并 Markdown、JSON 或 JSONL，避免生成结构合法但语义错误的任务数据。
- 客户端首次接入既有任务空间时先执行同步预检，界面提供“暂不接入”“查看并处理差异”
  “仅同步无冲突项”三个入口。
- “暂不接入”不得修改本地或服务端、不得建立 Agent 绑定、不得推进同步游标。
- “仅同步无冲突项”只处理两边相同和服务端独有的完整任务目录；跳过本地独有、内容冲突和
  移动删除争议，不上传任何本地内容。
- “查看并处理差异”按任务目录展示差异，用户可以下载服务端任务、导入本地任务、处理冲突或
  保存本地副本，最后统一应用结果。
- 同步预检必须按完整任务目录成组处理，不能只写入一个任务目录中的部分文件。
- 不自动执行全仓 merge、reset、stash 或 checkout；需要全仓 fast-forward 时继续使用现有
  `sync_branch` 命令及其整仓 clean 规则。
- 已关联客户端重启时使用持久化游标，只在首次关联或显式重建时执行全量快照。
- 文件移动、归档、删除和离线重连必须具备可判定、可恢复的语义。
- 服务端重启、索引重建或客户端回退不得丢失已提交 tasks 快照、删除墓碑、任务空间游标和项目访问关系。

## Acceptance Criteria

- [x] 产品范围明确为彻底替换现有服务端 Git 模式，不保留双模式长期并存。
- [x] Web 创建带负责人的任务或改派任务要求目标用户至少一个符合项目绑定条件的 Agent 在线。
- [x] 同一账号在新设备完成登录或配对后，旧 Agent 立即失效，旧客户端无法继续心跳或领取命令。
- [x] 同一账号重复安装后最终只保留一个有效 Agent，项目绑定迁移或重建后仍可唯一执行任务命令。
- [x] 新设备未重新选择本地仓库前，不能因为账号相同而错误显示项目 Agent 已就绪。
- [x] 新设备提供明确的本地项目选择入口，选择并校验成功后恢复该项目绑定。
- [x] 目标 Agent 离线、只读绑定或未绑定项目时，Web 明确拒绝操作且不会生成服务端任务文件。
- [x] Agent 在本地成功调用 `task.py` 后，任务通过实时同步出现在 Board，不依赖服务端 Git。
- [x] 创建或改派执行期间，Board 只显示独立操作项，不在正式任务列表中生成临时任务卡片。
- [x] 创建/改派失败时，Board 显示具体错误，并支持同一幂等键重试或取消。
- [x] 两个客户端基于同一版本修改同一文件时，只有第一个写入成功；第二个收到明确冲突，
  服务端内容不被静默覆盖。
- [x] 同一批次一个文件发生版本冲突时，整批文件均不写入。
- [x] 冲突提示能显示“谁在什么设备、什么时间修改了该任务文件”，并给出下一步操作建议。
- [x] 冲突提示不要求普通用户理解 revision、SHA-256 或 HTTP 状态码。
- [x] 冲突后可以向用户提供查看差异、使用服务端版本、用我的版本覆盖、仅保存本地副本四个操作。
- [x] 使用任一覆盖动作前均保留双方内容，覆盖动作经过确认并产生审计记录。
- [x] 首次接入既有任务空间时先展示同步预检，不直接覆盖本地或上传服务端。
- [x] “暂不接入”不产生本地文件、服务端 revision、项目绑定或同步游标变化。
- [x] “仅同步无冲突项”只下载完整且安全的服务端任务目录，跳过所有本地独有和冲突内容。
- [x] “查看并处理差异”支持按任务目录统一选择和应用结果，不能生成半个任务。
- [x] 改派成功前，任务仍显示原负责人和“改派中”状态。
- [x] 服务端不 clone、fetch 或 push 项目 Git 时，仍能从持久化任务快照构建完整 Board。
- [x] 客户端可选择 Git 仓库发起项目接入，不需要管理员预先创建项目。
- [x] Git 仓库没有 `.trellis` 时，客户端提示初始化：用户选择本机编码 Agent 后完成初始化；
  已有 `.trellis` 时跳过初始化。
- [ ] 没有安装系统 `trellis` 或 `npx` 的 Windows 客户端仍能使用安装包内置的固定 Trellis runtime
  完成初始化。
- [x] 新初始化项目只有在本地 HEAD 与远端分支 SHA 相同、初始化文件已提交且相关路径干净后
  才进入可用状态。
- [x] 首次推送检测支持定时检查、窗口重新聚焦和用户手动检查，成功后停止轮询。
- [x] 远端分支不存在、本地领先、远端领先、分叉和网络不可达使用不同提示。
- [x] 同一客户端可为同一项目追加多个编码 Agent，其他客户端无需安装相同工具。
- [x] 使用 HTTPS 和 SSH 形式指向同一 Git 仓库时，服务端识别为同一个项目。
- [x] 同一 Git 仓库的不同分支在 Board 中归属同一项目，但任务数据和 revision 完全隔离。
- [x] Team 模式的任务列表必须选定具体任务空间；“全部项目”只展示分支摘要，不混合任务卡。
- [x] 同步进行中客户端显示“切换分支可能造成任务错位或污染”的醒目提示。
- [x] 风险提示不阻止用户继续操作，也不承诺自动处理外部切换后的任务污染。
- [x] 同一 Git 仓库、同一分支被多个客户端接入时始终命中同一个全局任务空间，不产生团队级
  重复项目和重复任务索引。
- [x] 首次接入新任务空间时必须确认归属团队，项目创建后由该团队拥有。
- [x] 非所有者团队接入既有任务空间时不能读取任务内容，必须经过邀请或授权。
- [x] 同一项目的客户端上传任务后，其他客户端收到并应用一致的 `.trellis` 任务内容。
- [x] 服务端同步协议只接受 `.trellis/tasks/**`，拒绝 spec、scripts、config、workflow、
  agents、workspace、`.developer` 和本机编码 Agent 适配目录。
- [x] 服务端任务扫描不依赖未被同步到服务端的工具链或项目配置。
- [x] 缺少 `.trellis/workspace`、`.developer`、scripts 和 spec 时，服务端仍能投影任务，
  workspace 会话记录显示“服务端不判定”而不是伪造完成或失败。

## Out of Scope

- 自动物理删除旧服务端 Git 表、`data/projects/**` 或 `git-credentials.key`。
- 取消客户端项目自身的 Git 工作流和历史管理。
- 未经确认新增第二套任务文件格式或绕过 Trellis `task.py` 的任务写协议。
- 兼容旧服务端 Git 克隆、旧实时覆盖层结构、旧项目迁移状态或旧协议。
- 为现有数据执行自动迁移；重构分支从新的 tasks-only 数据模型开始。
- 阻断客户端或外部 Git 分支切换，以及自动修复切换分支造成的任务污染。
- 服务端通过访问 Git 远端独立证明客户端自报的项目远端真实存在。

## Decisions

- 服务端 Git 模式由客户端快照模式彻底替换，不作为可切换的长期兼容模式保留。
- 客户端自身仍可使用 Git；服务端不再 clone、fetch、commit 或 push 项目 Git 仓库。
- Web 创建带负责人的任务和改派操作采用“服务端下发命令、负责人 Agent 本地执行”的模式。
- 目标 Agent 必须在线；服务端不直接生成或修改任务文件。
- 创建/改派接口不能只传负责人用户 ID，还必须确定唯一的目标 Agent 项目绑定。
- 一个用户账号始终只有一个有效 Agent；新设备生效时自动踢下线并撤销旧 Agent。
- 设备替换时保留账号级项目权限，但必须重建当前设备与本地仓库的物理绑定。
- 新设备项目恢复采用手动逐个选择本地仓库，不实现工作区自动扫描。
- 创建/改派进度以独立操作项展示，不创建临时任务卡片。
- 正式任务和数据以 Agent 执行成功并通过实时同步上传后的结果为准。
- 任务命令采用路径级安全边界：客户端本地仓库结构、origin、分支和运行 `task.py` 所需的
  `.trellis/scripts` 必须正确，但服务端不做工具链摘要审批；无关源码和其他任务允许 dirty，
  只有命令实际影响的目标路径必须 clean 且版本一致。
- 管理员不再负责项目初始化和首次任务快照上传。
- 项目由客户端选择 Git 仓库发起接入；服务端以规范化 Git 远端识别同一个项目。
- 任务同步空间使用规范化 Git 远端与分支组合，不同分支不共享任务。
- Git 远端与分支组合在服务端全局唯一；团队不参与任务空间主键，只参与访问控制。
- 新任务空间由首次接入用户选择归属团队；同团队成员自动获得项目访问，其他团队必须邀请。
- `.trellis` 是否已存在决定是否执行初始化；编码 Agent 列表由当前客户端独立选择。
- 客户端安装包携带固定 Trellis CLI 和 Node runtime，初始化不依赖服务端或用户全局环境。
- 编码 Agent 工具配置不在客户端之间强制统一。
- 服务端实时同步范围仅为 `.trellis/tasks/**`；其他 `.trellis` 内容由客户端 Git 独立管理。
- Team 模式任务查询必须绑定具体任务空间，不跨分支混合任务卡和 revision。
- 任务写入采用文件级基线摘要校验；同一批次原子成功或整体拒绝。
- 冲突提示必须包含最后修改人、设备、时间和可操作建议，技术摘要放在次级详情中。
- 冲突后提供查看差异、使用服务端版本、用我的版本覆盖和仅保存本地副本四个动作。
- 第一版不做自动内容合并。
- 首次接入采用“暂不接入 / 查看并处理差异 / 仅同步无冲突项”三入口预检。
- 同步预检以完整任务目录为处理单位。
- 新初始化项目通过 `git ls-remote` 比较本地 HEAD 与远端分支 SHA，确认首次推送成功后才
  建立全局任务空间。
- 本次在独立分支 `codex/server-gitless-task-sync` 上进行破坏式重构，不保留旧服务端 Git
  模式、旧数据迁移或旧协议兼容。
- 数据库使用新增 `sync_*` 表承载新模式；旧表和旧目录保留为人工回滚材料，不自动清理。
- 同步期间只提示分支切换风险，不禁用操作；外部切换后的污染处理不在本次范围。
- 服务端保存最新 tasks 快照、删除墓碑、审计和冲突备份，不保存完整文件历史。
