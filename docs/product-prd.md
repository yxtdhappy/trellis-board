### 1.1 核心术语

| 术语 | 产品语义 |
| --- | --- |
| 任务 | 一个 Trellis 任务目录及其 `task.json`、说明文档和任务产物 |
| 阶段证据 | 能证明任务处于某个流程阶段的文件、人工检查点或子任务汇总 |
| 任务空间 | 由规范化 Git 远端和分支共同确定的同步范围；同一远端的不同分支属于不同任务空间 |
| 本地关联 | Windows 客户端把某个本地 Git 仓库目录绑定到某个任务空间的关系 |
| 操作项 | Web 发起创建或改派后产生的独立执行记录；成功前不等于正式任务卡或正式负责人变更 |
| standalone | 无账号鉴权的本机或可信局域网模式 |
| team | 启用账号、团队、项目权限、审计、任务空间同步和 Windows Agent 的团队模式 |

## 2. 产品摘要、问题与价值

Trellis Board 是 Trellis 任务流程的可视化执行与协作控制面。它读取任务目录中的真实证据，把分散在多个仓库、分支和团队成员手中的任务整理为可操作的流程视图；在 team 模式下，它进一步提供项目权限、任务空间同步、Windows 本地 Agent、Web 到客户端的命令闭环和系统审计。

### 2.1 用户问题

- 任务分散在多个仓库和分支，难以快速判断“现在该做什么”。
- 只看任务状态文字容易失真，无法判断需求、设计、实施、检查、验证和归档证据是否真实存在。
- 多成员协作时，任务负责人、项目权限、在线 Agent 和分支同步状态彼此割裂，容易出现“页面显示成功，但文件没有落盘”。
- 同一仓库不同分支混用同一工作目录时，容易把其他分支的任务错误同步到当前分支。
- 服务端直接操作项目 Git 会带来凭据、克隆延迟、双事实源和回灌冲突，不适合作为团队任务协作的唯一通道。
- 桌面客户端依赖多个后台进程或外部运行时时，安装、升级、故障定位和回收权限都更复杂。

### 2.2 产品价值

- 把“当前应该做什么、哪些需要关注、任务处在哪一步”放在同一决策入口。
- 让阶段位置尽量来自可证实证据，而不是文件修改时间或主观状态。
- 让团队在服务端权限边界内共享任务状态，同时保留客户端作为项目 Git 和工作区的唯一操作方。
- 让创建、改派、冲突和同步结果具备明确状态，不在正式结果出现前伪造任务卡或负责人变更。
- 通过任务空间、真实分支校验和多 worktree 规则，减少跨分支串写。
- 通过账号、团队、项目角色、设备撤销和审计，支持受控的团队协作。

Trellis Board 不是通用项目管理套件，也不是替代 Git 的远端服务。它关注 Trellis 任务流程的真实证据、个人执行决策和团队任务同步。

## 3. 目标用户、角色与典型场景

### 3.1 目标用户

| 用户 | 核心诉求 |
| --- | --- |
| 个人开发者 | 在本机多个仓库间快速找到下一步任务，看到阶段证据、阻断、截止和 WIP 风险 |
| 团队成员 | 查看授权项目任务，接受派发，推进自己负责的任务，并与其他客户端保持一致 |
| 项目负责人 | 管理项目成员和跨团队访问、查看项目 Agent 绑定与审计、判断项目风险并处理同步问题 |
| 团队管理员 | 管理所有者团队的项目协作、跨团队邀请、设备和系统审计状态 |
| 系统管理员 | 创建账号、团队和系统级配置，跨团队检查项目、设备和审计 |
| 只读干系人 | 查看授权项目、任务阶段和归档，不修改任务 |
| 实施或新成员 | 不阅读内部代码，也能理解产品能力、操作路径和限制 |

### 3.2 权限角色

| 角色 | 当前能力 |
| --- | --- |
| 系统管理员 | 管理账号、团队和系统能力；可直接读取所有有效团队的数据；可管理项目接入、成员、Agent 和审计 |
| 团队管理员 | 在所有者团队内管理项目接入、项目成员和跨团队邀请，查看 Agent 绑定与项目审计；也可查看获邀团队项目 |
| 项目负责人 | 管理项目成员、跨团队访问，查看 Agent 绑定与项目审计；可刷新项目、写任务和接受本人任务 |
| 项目成员 | 查看项目、写任务和接受本人任务；写任务还要求具备 developer ID 且任务空间可用 |
| 项目只读成员 | 查看项目、任务和归档；不能写任务、接受任务或上传同步内容 |
| 其他团队成员 | 可查看团队拥有或获邀共享的项目；团队身份本身不会自动赋予项目写角色或 developer ID |

服务端是权限判断的唯一事实源。未加入团队、团队没有项目访问关系、账号或项目已停用、设备已撤销时，相关数据按不可用或不存在的口径处理；前端隐藏入口不能替代服务端拒绝。

### 3.3 典型场景

- 开发者早晨打开 Board，先看推荐任务、注意力队列和流动信号，再进入任务详情执行。
- 项目负责人检查一个任务的开工条件、阶段证据和被阻断原因，确认是否继续推进。
- 成员在 Web 创建任务并派给另一名成员，等待目标用户的在线 Agent 在本地生成正式任务。
- 新成员在 Windows 客户端选择本地 Git 仓库，完成 Trellis 初始化、推送确认和首次任务差异处理。
- 两名成员修改同一任务文件，后提交者看到冲突并明确选择服务端版本、本地覆盖或保存副本。
- 团队管理员处理项目访问、成员角色、设备撤销和审计核查。
- 维护人员在 standalone 模式启用独立插件，扩展任务入口或外部 Agent 派发。

## 4. 产品形态与运行模式

### 4.1 两种运行模式

| 维度 | standalone | team |
| --- | --- | --- |
| 适用场景 | 本机、个人工作区或可信局域网 | 多用户、多团队、项目权限和 Windows Agent 协作 |
| 鉴权 | 无账号鉴权 | 账号登录、HttpOnly 会话、团队和项目权限 |
| 项目来源 | 本机白名单仓库 | 客户端选择本地 Git 仓库后接入全局项目和分支任务空间 |
| 扫描对象 | 白名单仓库中的 `.trellis/tasks` 和 `.trellis/workspace` 等本地证据 | 服务端持久化的 `.trellis/tasks/**` 快照 |
| 刷新方式 | 文件监听、防抖扫描、SSE 通知和手工刷新 | Agent 增量同步、Board SSE、客户端 cursor 和定时状态核对 |
| 任务写入 | 直接调用目标仓库的 Trellis `task.py` 或修改目标 `task.json` | Web 向目标用户唯一在线 Agent 下发命令，客户端本地执行并回传 |
| 多用户隔离 | 无 | 团队、项目角色、设备、任务空间和审计共同隔离 |
| 插件 | 可使用 standalone 插件机制 | 插件机制不加载，管理端点明确返回禁用状态 |
| 主要风险 | 无鉴权，只能在可信网络使用 | 部署、备份、Agent 在线、分支和同步一致性要求更高 |

两种模式共用同一套任务推导、流程阶段、看板查询和 SQLite 运行状态能力。standalone 的网页打开后先显示本地扫描缓存；后台文件变化会触发防抖扫描，扫描期间再发生的变化会排队再跑一轮。

### 4.2 运行边界

- standalone 服务监听所有网络接口且没有账号鉴权，不能直接暴露到不可信网络。
- team 服务同样监听网络接口；HTTP 可用于受控网络，非可信网络必须通过 HTTPS 访问。
- team 服务端不执行项目 Git 的 `clone`、`fetch`、`commit` 或 `push`，不保存项目 Git 凭据，也不创建项目工作副本。
- 项目源码、共享 `.trellis` 配置、`scripts`、`spec`、`workflow`、`workspace` 和本机编码 Agent 配置继续由客户端 Git 管理。
- team 服务端只持久化和广播 `.trellis/tasks/**`，并基于该快照生成任务索引和 Board。

## 5. 信息架构与全局交互

### 5.1 页面与区域

| 区域 | 主要内容 |
| --- | --- |
| 登录页 | team 模式账号登录、首次改密入口、无公开注册说明和错误反馈 |
| 顶栏 | 产品标识、任务流水线、团队视角、归档索引、插件、搜索、创建、团队筛选、用户菜单和管理入口 |
| 项目栏 | 团队筛选后的项目列表、分支任务空间、本地关联状态、监听状态、待处理归属、补同步和解绑入口 |
| 任务流水线 | 个人执行标题、内置/保存视图、组合筛选、流动信号、注意力队列、统计摘要和轻量 Kanban |
| 团队视角 | 跨项目任务查询、负责人统计、团队与分支筛选、分页任务表 |
| 归档索引 | 只读历史任务、完成证据、负责人、归档时间和分页查询 |
| 任务详情 | 状态、进度、条件检查、阶段证据、风险依赖、计划字段、任务产物和派发操作 |
| 操作项区域 | team 模式创建和改派命令的等待、执行、成功、失败、重试和取消 |
| 管理台 | 项目协作、用户账号、团队、Agent 设备和系统审计 |
| 插件页 | 插件版本、兼容性、运行状态、启停和日志 |
| Windows 客户端 | 环境检查、本地登录、Board WebView、托盘同步状态和冲突/差异控制窗口 |

### 5.2 全局交互原则

1. 首屏按“当前该做什么 → 哪些任务需要关注 → 任务处于流程哪一步”组织。
2. 任务详情按“状态与进度 → 条件检查 → 阶段证据 → 风险依赖 → 任务产物 → 派发操作”阅读。
3. 软提醒用于优先级、WIP、条件缺口和停滞；强门禁用于权限、数据一致性、目标 Agent 不可用和分支不匹配。
4. 覆盖服务端任务、替换本地分支绑定、解绑当前客户端或撤销设备等跨边界操作必须明确确认。
5. 长操作使用独立状态和错误信息，不提前生成正式任务、正式负责人或虚假的阶段完成结果。
6. 普通用户先看到可理解的业务原因和下一步，技术摘要只在需要排查时展开。

## 6. 核心功能域

### 6.1 任务发现、流程推导与个人执行控制

| 维度 | 当前设计 |
| --- | --- |
| 用户问题 | 任务多、项目多、状态不透明时，用户不知道下一步做什么，也不知道哪些任务正在变慢 |
| 当前能力 | 13 阶段视图、4 个泳道、9 个内置执行视图、组合筛选、推荐任务、注意力队列、流动信号、WIP 软上限和保存视图 |
| 设计思路 | 先帮助用户做执行决策，再展示完整 Kanban；风险信号只提示，不替用户做审批或阻断 |
| 核心交互 | 用户选择全部或“只看我的”，叠加项目、分支、负责人、优先级、阶段和阻断筛选，打开任务或保存组合视图 |
| 边界 | WIP 是 1–9 的软上限，不阻止任务推进；没有证据的阶段不会因时间流逝自动判定完成 |

当前显示 13 个阶段：

需求、调研、设计、实施计划、上下文编排、规划评审、实现、检查、真实验证、规范回写、工作提交、归档、会话记录。

进度百分比只统计 12 个必需阶段；真实验证是可选的补充证据，但仍始终显示。E2E 结果只接受报告文件中的明确执行记录，`implement.md` 里的“下一步做 E2E”等计划文字不会计为完成。

任务按四个泳道聚合：

- 规划：需求、调研、设计、实施计划、上下文编排。
- 待放行：规划评审完成但尚未进入实现。
- 实现：正在写代码或执行开发任务。
- 检查/收尾：检查、真实验证、规范回写、工作提交、归档和会话记录。

内置执行视图包括：

- 全部进行中。
- 今日焦点。
- P0/P1。
- 临近截止。
- 长时间未动。
- 实现中。
- 检查中。
- 被阻断。
- 阻断已解除。

流动信号展示实现中 WIP、当前阻断数、最近解除阻断数和开工/完成条件缺口。焦点建议综合逾期、阻断、临近截止、解除阻断、优先级、检查、实现和停滞等因素排序。注意力队列按紧急程度展示最多若干行，归档任务不进入当前注意力队列。

### 6.2 任务详情、证据与协作

| 维度 | 当前设计 |
| --- | --- |
| 用户问题 | 只看到任务标题或状态，无法判断任务为什么停在这里、是否可以开始或结束 |
| 当前能力 | 状态摘要、关注信号、阶段证据、开工/完成条件检查、风险依赖、计划字段、任务产物、任务目录定位和派发；任务卡另提供复制任务目录名 |
| 设计思路 | 把“可推进性”从主观判断转为阶段证据、条件缺口和依赖事实的组合 |
| 核心交互 | 点击任务卡打开详情，查看当前阶段和证据；处理条件缺口、查看依赖、预览产物或更新派发 |
| 边界 | 任务关系异常、阶段无证据或项目不可写时，系统显示原因而不伪造完成状态 |

#### 6.2.1 阶段证据

每个阶段显示完成状态、来源和证据说明。常见来源包括：

- `task.json` 状态。
- PRD、设计、实施计划和各类报告。
- 人工流程检查点。
- 子任务实施/检查汇总。
- 归档目录或明确的历史推断。

人工勾选只写入 Board 的运行数据库，不改写目标仓库的 `task.json`。没有持久化证据的阶段显示“待人工确认”，不会根据文件修改时间补造历史。

#### 6.2.2 条件检查

条件检查分为两类：

- 开工条件：对应需求、设计、实施计划和规划评审等准备证据。规划阶段缺失时提示“进入实现前需要补齐”，但不强制阻止操作。
- 完成条件：进入实现后检查实施报告、检查报告、PRD 验收项、工作提交和归档记录等完成证据。

条件表显示“对应阶段、缺失项、当前证据、下一步”。条件缺口是软提醒，用于降低返工风险，不替代权限门禁。

#### 6.2.3 依赖与风险

- 任务可建立“被谁阻断”和“阻断了谁”的双向关系。
- 建立依赖时可记录阻断原因。
- 解除依赖后保留已解除历史，并在后续统计中展示“阻断已解除”。
- 关系异常会显示在任务卡和详情中；父任务在关系异常时停止从子任务继承阶段。

#### 6.2.4 计划字段

任务支持截止日期、里程碑和标签。标签最多 10 个，每个标签最多 32 个字符。计划字段属于 Board 本地增强，只写入 Board 数据库，不改写目标任务的 `task.json`。

#### 6.2.5 任务产物

详情可读取并预览以下 Markdown 产物：

- PRD。
- Design。
- Implement。
- 实施报告。
- 检查报告。
- E2E 报告。

单个文件预览有长度截断，完整文件仍保留在仓库中，阶段判断继续读取完整文件。

#### 6.2.6 父子任务与复制任务名

- 同一任务组显示父任务和子任务列表，可跨仓库归组。
- 父任务可在子任务组证据满足时继承规划评审、实现、检查、真实验证、规范回写和工作提交阶段；除规划评审按已有子任务进入外，其余阶段要求全部子任务完成。
- 关系引用缺失、自引用、同一子任务多个父任务或父子循环会停止继承并显示原因。
- 任务卡提供复制任务目录名入口；详情显示团队、项目、分支和任务目录路径，便于在同级目录、终端或会话中定位任务。

### 6.3 跨项目、跨分支、团队视角与归档

| 维度 | 当前设计 |
| --- | --- |
| 用户问题 | 用户既需要看到组织内所有授权项目，又需要避免把不同分支或未授权团队的数据混在一起 |
| 当前能力 | 默认聚合全部授权团队和项目、团队筛选、任务空间筛选、跨项目团队查询、分支筛选和归档索引 |
| 设计思路 | 项目用规范化远端识别，任务用“远端 + 分支”隔离；团队筛选只收窄展示范围，不改变账号授权 |
| 核心交互 | 登录后直接进入全部授权项目；按团队/项目/分支筛选；在团队视角按负责人和阶段查询；在归档索引只读回看历史 |
| 边界 | 同一 `taskKey` 在不同分支是不同任务实例；未授权团队和任务空间不返回；归档任务不回流当前执行队列 |

当前 team 登录不要求用户先选择一个固定活动团队。默认展示用户全部授权团队的数据，用户可在顶栏按团队筛选。保存视图和个人 WIP 设置按团队展示范围维护，避免不同团队的偏好相互覆盖。

项目身份使用规范化 Git 远端。HTTPS、SSH、默认端口、末尾 `/`、`.git` 等等价差异归一为同一项目。任务空间身份是“规范化远端 + 分支”，同一远端同一分支在服务端全局唯一；不同分支拥有独立快照、revision、cursor、任务索引和命令。

团队视角用于回答“谁在推进，谁需要帮助”：

- 按负责人统计任务量。
- 跨项目混合排序和分页。
- 按团队、项目、分支、负责人、优先级、阶段和阻断状态筛选。
- 点击任务直接进入详情。

归档索引只展示历史任务：

- 展示任务、负责人、完成证据和归档时间。
- 支持搜索、分支筛选、负责人筛选和分页。
- 归档任务只读回看，不继续计入当前执行队列和注意力队列。
- 工作提交发生在归档前；`finish-work` 原子地完成任务并移动目录；归档后的会话记录不反向改变任务状态。

### 6.4 任务创建、派发、待接受与操作项

| 维度 | 当前设计 |
| --- | --- |
| 用户问题 | 任务创建和改派需要真实落到负责人本地项目，不能在 Web 端制造虚假成功状态 |
| 当前能力 | standalone 直接写入；team 通过目标用户唯一在线 Agent 执行；独立操作项；失败重试/取消；待我接受队列 |
| 设计思路 | 将“命令已提交”和“正式任务已落盘”分开，用幂等操作项表达中间状态 |
| 核心交互 | 选择项目/分支、填写标题/标识/描述、负责人和优先级；提交后查看操作项；目标用户接受派发 |
| 边界 | team 目标 Agent 离线、未绑定、非写成员或项目停用时，在创建操作项前拒绝 |

#### 6.4.1 standalone 创建与改派

- 创建任务调用目标仓库自己的 Trellis `task.py create --no-start`。
- 新任务进入 planning 状态。
- 改派只更新指定任务的 `task.json.assignee`。
- 接口只允许操作项目白名单中的仓库，不允许任意路径读取或写入。

#### 6.4.2 team 创建与改派

1. Web 校验当前用户、目标负责人、项目角色、项目同步状态和目标任务空间在线监听状态。
2. 校验通过后返回独立操作项，状态先为“等待投递”。
3. 目标账号唯一在线 Agent 收到命令，领取执行租约。
4. Agent 在本地仓库执行 Trellis 创建或原子修改负责人。
5. Agent 通过 tasks-only 快照同步上传结果。
6. 服务端索引确认任务或负责人已更新后，操作项才显示成功。

操作项状态包括：

- 等待投递。
- 等待 Agent 执行。
- Agent 正在执行。
- 已完成，正式任务已同步。
- 执行失败。
- 已取消。

失败操作可使用同一幂等键重试；重试不会创建第二个任务。成功或取消后不能重试。

#### 6.4.3 待我接受

被派发的任务进入“待我接受”队列。任务展示项目、优先级和负责人，用户可以明确接受。创建或改派期间，正式任务卡和正式负责人只在本地文件上传并被服务端索引后出现。

### 6.5 Windows 客户端环境门与本地项目接入

| 维度 | 当前设计 |
| --- | --- |
| 用户问题 | 团队成员需要把本机 Git 仓库安全接入共享任务空间，同时又不能让远程网页访问任意本地路径或代管 Git |
| 当前能力 | Windows 客户端选择仓库、Trellis/Agent 初始化、推送确认、只读预检、首次差异处理、本地绑定和快速追加编码 Agent |
| 设计思路 | 本地路径只由客户端系统目录选择器产生；服务端只接收规范化远端、分支和任务快照 |
| 核心交互 | 选择仓库根目录 → 检查 origin/分支/tasks → 初始化缺失内容 → 手动 commit/push → 检查推送 → 预检差异 → 确认接入 |
| 边界 | 只接受 Git 仓库根；不会自动 commit 或 push；暂不接入不建立绑定、不写服务端；同一仓库在一个客户端只能绑定一个有效分支 |

#### 6.5.1 环境门

客户端冷启动先执行运行环境检查，再显示本地登录页：

- 检查客户端私有运行标志。
- 检查 PATH 中的 Node.js 与 Trellis CLI。
- 缺失时从受控镜像安装到客户端私有目录，显示下载、校验、解压和安装步骤。
- 版本满足要求时跳过安装并只写标志位。
- 环境准备成功后进入登录页；失败时停留在环境页并显示原因。

Node.js 和 Trellis CLI 用于环境门校验与项目初始化，不作为常驻后台服务运行。项目任务执行仍依赖本地 Git，以及 Trellis CLI 自身需要的运行环境。

#### 6.5.2 本地仓库检查

客户端只接受 Git 仓库根目录，并校验：

- origin 可规范化。
- 当前分支合法。
- `.trellis` 和 `.trellis/tasks` 是否存在。
- 当前仓库已有本地关联。
- 当前设备已初始化的编码 Agent 工具。

缺少 `.trellis` 或 `tasks` 时，用户可选择本机需要的编码 Agent 工具，由客户端使用固定 Trellis runtime 初始化。初始化只影响当前设备，其他设备无需选择相同工具。已有 `.trellis/tasks` 时跳过初始化。

#### 6.5.3 首次推送确认

客户端不会自动提交或推送初始化文件。用户需要自行检查、提交并推送，然后由客户端比较本地 `HEAD` 与远端目标分支。当前状态包括：

- 等待提交。
- 等待推送。
- 远端分支不存在。
- 远端领先。
- 本地与远端分叉。
- 暂时无法连接远端，无法确认。
- 已推送，可以接入。

网络不可达时只显示“无法确认”，不能误报为“未推送”。

#### 6.5.4 首次任务差异

接入前先执行只读预检。预检只返回项目、任务空间、revision 和文件元数据，不建立项目、绑定或 cursor，也不返回任务正文。

用户可选择：

- 暂不接入：只关闭向导，不修改本地绑定、cursor 或服务端。
- 仅同步无冲突项：只下载服务端独有的完整任务目录，不上传本地独有或冲突内容。
- 查看并处理差异：按完整任务目录统一选择服务端、本地、保存副本或跳过。

服务端没有快照时，用户明确确认后以 bootstrap 模式上传本地任务作为初始快照。双方一致时直接完成，不显示空差异窗口。

#### 6.5.5 本地关联与多分支

- 同一账号同一时刻只有一个有效 Agent。
- 同一 Agent 的同一本地仓库只能绑定一个已批准分支。
- 切换到另一个分支时会显示旧、新绑定差异；用户确认后替换本机绑定，但不删除旧任务空间、其他设备绑定或服务端任务。
- 需要同时同步多个分支时，必须为每个分支使用独立 Git worktree，并分别绑定。
- 项目栏显示本地关联、监听、同步、待补传、分支暂停和待归属状态。
- 解绑只解除当前客户端与该分支的关联，不删除服务端任务、冲突或历史；网络失败时本地先停止同步并保留“服务端解绑待确认”。

### 6.6 Tasks-only 同步、冲突与分支门禁

| 维度 | 当前设计 |
| --- | --- |
| 用户问题 | 多客户端需要及时共享任务文件，同时不能静默覆盖、混合分支或把服务端变成项目 Git 代理 |
| 当前能力 | 客户端任务快照、实时增量同步、文件级 CAS、原子任务目录、删除墓碑、cursor 恢复、显式补传、冲突处理、分支门禁和任务级归属 |
| 设计思路 | 任务内容只从客户端进入；服务端保存可恢复快照和审计；任何不确定情况先暂停确认，不自动合并或猜测 |
| 核心交互 | 文件变化后自动同步；冲突或差异进入控制窗口；用户处理后再恢复；项目栏持续显示同步健康状态 |
| 边界 | 服务端只接收 `.trellis/tasks/**`；不自动 merge Markdown/JSON/JSONL；不在错误分支上传、拉取或推进 cursor |

#### 6.6.1 同步范围

进入 team 同步协议的内容只有：

```text
Git 仓库
  └─ .trellis
      └─ tasks/**
```

以下内容不进入 team 同步，继续由项目 Git 管理：

- `.trellis/spec/**`
- `.trellis/scripts/**`
- `.trellis/config.yaml`
- `.trellis/workflow.md`
- `.trellis/agents/**`
- `.trellis/workspace/**`
- `.trellis/.developer`
- 仓库根目录中的 Codex、OpenCode、Pi 等本机编码 Agent 配置

#### 6.6.2 同步链路

```text
本地任务文件变化
  → 防抖聚合
  → 读取完整任务目录
  → 规范化文本并计算摘要
  → 以 baseSha256 校验上传
  → 服务端原子写入快照并增加 revision
  → 更新任务索引并广播
  → 其他客户端从 cursor 拉取
  → 原子替换完整任务目录后推进 cursor
```

关键约束：

- 同一批次任一文件基线变化时，整批拒绝，不写入部分任务。
- 删除使用墓碑；活动目录移动到归档目录时在同一个批次完成。
- 客户端按任务空间串行同步，只在完整任务目录应用成功后推进 cursor。
- 网络响应丢失时保留 pending batch，重试复用原批次标识，不重复生成 revision。
- 单文件、单批大小和文件数均有限制；超过限制时整批拒绝，任务快照不变。
- 常驻客户端从本地 cursor 增量恢复；首次接入或显式重建才执行全量快照。

#### 6.6.3 仅同步无冲突项与补传

首次接入选择“仅同步无冲突项”时，本地独有的任务被记录为 deferred，不会因为后续轮询、页面打开或 watcher 事件自动上传。

项目栏明确显示“N 个本地任务未同步”。用户点击补传后：

1. 系统再次校验项目、绑定、读写角色、真实分支和目标任务归属。
2. 用户确认上传范围。
3. 客户端通过正常同步队列和 CAS 上传。
4. 冲突仍进入控制窗口，不静默覆盖。

只读绑定不能执行补传。

#### 6.6.4 冲突处理

当同一文件基于旧基线提交时，服务端返回任务文件冲突，不覆盖服务端，也不推进客户端 cursor。冲突信息以用户可理解的任务名、文件、最后修改人、设备、时间和建议为主。

用户可执行：

- 查看差异：同时查看本地和服务端完整任务目录。
- 使用服务端版本：先备份本地完整目录，再用服务端目录原子替换。
- 用我的版本覆盖：二次确认后，服务端先保存双方内容并写审计，再接受本地版本。
- 仅保存本地副本：复制本地完整目录到客户端备份，不改变服务端。

第一版不自动合并 Markdown、JSON 或 JSONL，避免生成结构合法但语义错误的任务。

#### 6.6.5 分支门禁

客户端在以下操作前都读取本地真实分支：

- 首次接入。
- 上传与拉取。
- watcher 触发。
- pending 重试。
- 延后任务补传。
- 冲突覆盖。

真实分支与绑定分支不一致时：

- 不写本地任务目录。
- 不上传服务端。
- 不推进 cursor。
- 不自动 checkout、switch 或修复工作区。
- 项目栏显示实际分支错误和处理提示。
- 用户切回绑定分支后，重新校验并恢复同步。

同步进行中，项目栏还会提示“此时切换 Git 分支可能导致任务错位或污染”。客户端不拦截用户在终端、IDE 或其他工具中切换分支。

#### 6.6.6 任务级分支归属

绑定分支与真实 Git 分支一致，仍不能证明 `.trellis/tasks` 下每个任务都属于该分支。客户端和 service 还会校验任务目录中的分支归属：

- 任务明确属于当前绑定分支时，可同步。
- 任务明确属于其他分支时，本地保留但暂停上传。
- 任务分支为空，且服务端或项目模型能唯一确定归属时，可自动补齐任务分支。
- 多个任务空间给出不同归属时，项目栏显示“待确认归属”，由用户批量或逐项确认。

同一个待归属状态不会因 watcher 轮询或客户端重启反复产生新提示。

#### 6.6.7 多 worktree

一个普通 Git 工作目录不应同时承载多个分支的任务同步。需要并行处理多个分支时：

- 每个分支使用独立 Git worktree。
- 每个 worktree 用自己的本地仓库身份、当前分支和任务空间绑定。
- 不允许同一工作目录在多个分支绑定之间双写同一份本地任务。

### 6.7 账号、团队、项目权限、设备与审计

| 维度 | 当前设计 |
| --- | --- |
| 用户问题 | 多团队共用一套 Board 时，必须避免越权读取、重复项目、错误执行和不可追溯的设备操作 |
| 当前能力 | 无公开注册、系统管理员建号、团队与项目角色、跨团队项目邀请、单账号单活动 Agent、设备撤销和追加式审计 |
| 设计思路 | 团队边界在服务端查询层统一注入；项目角色覆盖业务操作；设备只执行其账号有权执行的项目命令 |
| 核心交互 | 管理员创建账号/团队和成员关系；项目负责人维护项目成员；用户可以追加或重新关联本机 Agent；管理员查看项目和系统审计 |
| 边界 | 团队管理员不能管理系统账号和团队本身；被停用团队、无权限项目和已撤销设备按不可用处理 |

#### 6.7.1 账号

- 不提供公开注册。
- 首个系统管理员只能通过服务器本机 CLI 创建。
- 其他账号由系统管理员创建并分配团队。
- 首次登录或密码被重置后必须先修改密码。
- 重置密码会使其他会话失效。
- team 会话由服务端校验，网页只持有 HttpOnly 会话 Cookie。

#### 6.7.2 团队和项目访问

- 一个用户可以加入多个团队。
- 系统管理员可创建、启用、停用团队并分配团队成员。
- 项目有所有者团队，也可邀请其他团队访问。
- 同一个 Git 项目只保留一个全局项目身份，不因多个团队访问而复制任务空间。
- 其他团队在获得访问前不能读取任务内容。
- 团队获得项目访问后，其成员可查看项目任务；写任务和接受任务仍要求具体项目成员角色与 developer ID。
- 用户被移出团队后，该团队项目访问应立即失效。

#### 6.7.3 项目角色

| 操作 | 系统管理员 | 团队管理员 | 项目负责人 | 项目成员 | 只读成员 |
| --- | --- | --- | --- | --- | --- |
| 查看项目任务 | 是 | 是 | 是 | 是 | 是 |
| 写任务 | 是 | 按项目角色 | 是 | 是 | 否 |
| 接受任务 | 仅本人被派发时 | 本人被派发且具备项目写角色 | 仅本人被派发时 | 仅本人被派发时 | 否 |
| 管理项目成员 | 是 | 所有者团队 | 是 | 否 | 否 |
| 查看项目 Agent 绑定 | 是 | 有团队访问关系 | 是 | 否 | 否 |
| 查看项目审计 | 是 | 有团队访问关系 | 是 | 否 | 否 |
| 管理项目接入 | 是 | 所有者团队 | 否 | 否 | 否 |
| 邀请共享团队 | 是 | 所有者团队 | 是 | 否 | 否 |
| 移除共享团队 | 是 | 按项目角色 | 是 | 否 | 否 |

任务写操作还要求账号具备项目写角色（系统管理员除外），且项目和任务空间处于启用状态。任务级编辑还依赖可用索引；索引陈旧、修复中或无法完成 materialization 时，界面显示原因并拒绝写入，不伪造成功结果。

接受任务始终只允许分派目标本人；管理员身份不能让用户代其他成员接受任务。

#### 6.7.4 设备与单 Agent

- 客户端设备凭证由 Rust 进程管理，系统级凭证使用 Windows DPAPI 保存。
- 一个账号同一时刻只有一个有效 Agent。
- 新设备生效后，旧设备立即失去 Agent 鉴权，旧 SSE 关闭，旧待执行命令取消。
- 用户可在管理台撤销设备；撤销后其绑定和待执行命令立即失效。
- 换设备不迁移本地仓库绝对路径、项目绑定、cursor 或 pending batch，新设备必须重新选择项目。

#### 6.7.5 管理台

当前管理台包含：

- 项目协作：选择有管理权限的项目，维护成员、developer ID、角色和团队访问，查看 Agent 绑定和项目审计。
- 用户账号：系统管理员创建账号、调整团队、状态、系统管理员权限和重置密码。
- 团队：系统管理员创建、启用或停用团队，并维护团队成员和团队角色。
- Agent 设备：查看设备、心跳、版本、协议、撤销状态和生成一次性桌面配对入口。
- 系统审计：按操作人等条件查看跨项目操作结果，服务端脱敏后再由前端隐藏密码、Token 等敏感键。

#### 6.7.6 审计和信息保护

- 项目访问、任务命令、冲突覆盖、解绑、设备撤销和管理操作产生追加式审计。
- 审计不以删除历史实现“撤销”，撤销本身也作为新事件保留。
- 未授权团队或项目不泄露是否存在。
- 反向代理和服务日志不得记录 Cookie、Authorization、配对码、任务正文或本地仓库绝对路径。

### 6.8 插件体系与边界

| 维度 | 当前设计 |
| --- | --- |
| 用户问题 | 不同团队希望把外部消息、任务入口或编码 Agent 接入 Board，但不应让集成代码侵入 Board 主进程 |
| 当前能力 | standalone 插件宿主、独立子进程、JSON-RPC 通信、版本/兼容性检查、启停、状态、日志、审计、插件面板和参考插件 |
| 设计思路 | 插件按进程隔离，核心只通过协议调用；插件故障不加载进主进程 |
| 核心交互 | 用户在插件页查看版本、兼容性、PID、错误和日志，启动或停止插件；插件可按配置注入 Board 视图面板 |
| 边界 | 插件不是沙箱；team 模式不加载插件；全局关闭开关可只启动核心 |

当前状态包括：

- 运行中。
- 启动中。
- 已停止。
- 错误。
- 已禁用。
- 反复崩溃。
- 不兼容。

仓库中的参考插件包括：

- `a2a-intake`：将外部 A2A 消息转为 Trellis 任务。
- `acp-dispatch`：把匹配的进行中任务派发给 ACP Agent。

插件以 Board 运行用户身份执行，默认可读写文件和发起网络请求，不是安全沙箱。`acp-dispatch` 默认允许编辑和执行工具调用，只应在受信仓库和专用账号下启用。

team 模式的插件接口明确返回禁用状态，当前不提供团队级插件运行和权限模型。

### 6.9 Windows 桌面客户端与分发

| 维度 | 当前设计 |
| --- | --- |
| 用户问题 | 团队用户需要一个可安装、可升级、能安全访问本地 Git 和任务空间的桌面入口 |
| 当前能力 | Tauri v2 单进程客户端、本地登录、Rust 进程内 Agent、环境门、项目接入、冲突控制窗口、托盘暂停/恢复和两种 Windows 分发方式 |
| 设计思路 | 客户端 Agent 与界面同进程，减少额外后台进程和进程间桥接复杂度；敏感凭证留在 Rust/DPAPI 边界内 |
| 核心交互 | 启动检查环境 → 本地登录 → 当前 WebView 打开 Board → 关联项目 → 托盘或控制窗口处理同步事件 |
| 边界 | 当前只支持 Windows x64；远程网页不能提交任意本地路径；冷启动必须重新登录 |

#### 6.9.1 单进程与 Agent

- Agent 的心跳、SSE、任务空间同步和命令执行全部在 `trellis-board-client.exe` 内以 Rust 实现。
- 客户端没有独立 Agent sidecar，也没有常驻内置 Node 运行时。
- Agent 每 15 秒心跳，SSE 断线按指数退避重连。
- 认证被撤销时停止同步并保留可诊断状态；用户主动暂停同步时停止循环但保留队列状态。
- 托盘同步项在当前只表达“暂停同步/恢复同步”。

#### 6.9.2 登录和控制窗口

- 冷启动始终进入本地登录页，登录成功后当前 WebView 才导航到 Board。
- 密码通过 Tauri IPC 和 Rust 发起 HTTP/HTTPS 请求，不进入命令行参数、环境变量或日志；非可信网络必须使用 HTTPS。
- 会话 Cookie 只存在当前 WebView Cookie Store 和 Rust 内存；冷启动后重新登录。
- 设备凭证由 DPAPI 保护；客户端配置会持久化服务器地址、登录名和密码用于登录回填，因此客户端机器本身必须处于受控状态。
- 首次同步差异、任务文件冲突、待确认归属和同步错误进入独立控制窗口。

#### 6.9.3 桌面分发和运行条件

支持两种分发：

- NSIS 安装包。
- 解压即用的 Windows x64 绿色 ZIP，包内只有一个客户端 EXE。

运行条件：

- Windows 10/11 x64。
- Microsoft Edge WebView2 Evergreen Runtime；Windows 11 通常预装，目标 Windows 10 机器需由 IT 确认。
- 绿色版无需管理员权限，不创建快捷方式或开机自启项。
- NSIS 安装和卸载前会结束运行中的旧客户端；绿色版升级前需要由用户先退出客户端，再替换程序文件。

## 7. 端到端核心流程

### 7.1 登录、团队范围与任务判断

1. team 用户打开登录页并完成会话登录。
2. Board 默认聚合该账号全部有效团队成员关系下的授权项目和任务。
3. 用户可在顶栏收窄到单个团队。
4. 首屏显示执行视图、流动信号、注意力队列和当前任务分布。
5. 用户打开任务，先看当前阶段、条件缺口和证据，再决定下一步。

### 7.2 创建任务并派发

1. 用户点击“创建”。
2. 选择项目、分支任务空间和负责人，填写标题、标识、描述和优先级。
3. team 模式先检查目标 Agent 在线性、项目写权限和任务空间状态。
4. 校验通过后生成独立操作项，而不是临时任务卡。
5. 目标 Agent 在本地执行并同步，服务端索引成功后显示正式任务。
6. 目标用户在“待我接受”中确认派发。

### 7.3 首次接入本地项目

1. 用户在 Windows 客户端选择 Git 仓库根目录。
2. 客户端检查 origin、当前分支、Trellis 和 tasks。
3. 缺失 Trellis 时选择本机编码 Agent 工具并初始化。
4. 用户手动提交、推送，并让客户端确认远端状态。
5. 用户选择归属团队和 Trellis developer ID。
6. 客户端执行只读预检。
7. 用户选择暂不接入、仅同步无冲突项或查看并处理差异。
8. 明确接入后建立 binding，完成首次同步并启动 tasks watcher。

### 7.4 实时同步与冲突

1. 本地 `.trellis/tasks` 变化触发客户端防抖聚合。
2. 客户端读取完整任务目录，校验真实分支和任务归属。
3. 客户端以基线摘要上传，服务端执行原子 CAS。
4. 服务端更新快照、revision 和任务索引，并通知其他客户端。
5. 其他客户端拉取后原子替换完整任务目录，再推进 cursor。
6. 基线冲突时停止自动处理，进入控制窗口等待用户选择。

### 7.5 分支切换和多 worktree

1. 用户在客户端外切换 Git 分支。
2. Agent 在下一次同步前发现真实分支与绑定不一致。
3. 客户端暂停该 binding 的写文件、上传、拉取和 cursor 推进。
4. 项目栏显示分支错误；用户切回绑定分支后重新校验并恢复。
5. 如需同时处理两个分支，用户建立两个 worktree，分别选择目录并绑定各自任务空间。

### 7.6 权限与审计

1. 管理员创建账号、团队和成员关系。
2. 项目负责人配置项目成员和角色，可邀请其他团队访问同一全局项目。
3. 每次受控操作在服务端校验当前账号、团队、项目角色和同步状态。
4. 关键管理、访问、命令和覆盖操作写入审计。
5. 用户被移出团队、项目停用或设备被撤销后，后续请求立即失败。

### 7.7 插件运行

1. standalone 管理员准备插件目录和运行配置。
2. Board 启动插件并检查版本、兼容性和端点冲突。
3. 用户在插件页启动、停止插件并查看日志。
4. 插件故障在独立进程内收口，不影响核心 HTTP 和任务扫描。
5. team 模式不加载插件，也不执行插件集成。

## 8. 设计思路与关键取舍

### 8.1 以证据驱动流程，而不是猜测状态

Trellis Board 优先使用任务状态、报告、计划和人工检查点推导阶段。这样可以避免把“文件最近修改过”误判为“某阶段已完成”，也能让团队看到为什么任务停在当前位置。

代价是部分阶段只能显示“待人工确认”，需要用户补充证据。这个代价小于伪造进度造成的管理误判。

### 8.2 Board 增强状态与 Trellis 任务文件分离

截止日期、里程碑、标签、保存视图、WIP、依赖、人工阶段和事件属于 Board 的本地增强状态，写入 Board 数据库，不写回目标仓库的 `task.json`。任务实体和正式阶段仍以 Trellis 文件为准。

这样避免 Board 修改业务仓库的数据模型，也避免多个工具争夺同一任务文件。代价是 Board 迁移或恢复时必须同时保护运行数据库。

### 8.3 先做执行决策，再做完整看板

推荐任务、注意力队列和流动信号先回答“现在做什么”，轻量 Kanban 再回答“任务处在流程哪一步”。对于个人用户，这比一开始展示全部列和全部任务更接近真实工作顺序。

### 8.4 软提醒与硬门禁分开

WIP、条件缺口、临近截止和停滞是软提醒，不阻止用户推进。权限、项目停用、目标 Agent 不可用、分支不匹配、任务归属不确定和文件基线冲突是硬门禁，必须阻止写入或要求确认。

这套分层避免把所有风险都做成审批流，也避免把数据一致性风险降级成提醒。

### 8.5 客户端负责项目 Git，服务端负责任务快照

当前团队模式将项目 Git 留在客户端，服务端只保存 `.trellis/tasks/**` 快照。这样服务端不需要项目 Git 凭据，也不会因服务端 clone、fetch 或 push 形成第二套事实源。

代价是任务同步依赖至少一个在线客户端提供任务内容，服务端不负责初始化、提交或修复项目 Git。

### 8.6 任务空间按分支隔离

同一远端的不同分支拥有独立任务空间、revision、cursor、索引和命令。这样同一分支可跨设备共享任务，不同分支不会互相覆盖。

代价是用户需要理解“仓库”和“分支任务空间”的区别；需要同时处理多个分支时，还必须使用多个 worktree。

### 8.7 长操作使用操作项和幂等重试

创建和改派在客户端真正落盘前只显示独立操作项。服务端使用命令租约、幂等键和索引确认，保证“操作已提交”不等于“正式结果已完成”。

这样用户可以理解等待和失败，但系统需要维护更多状态，UI 也必须明确区分操作项与任务卡。

### 8.8 单账号单活动 Agent

一个账号同一时刻只允许一个有效 Agent，可以确保 Web 创建和改派有唯一目标，也能防止旧设备继续领取命令。

代价是换设备会撤销旧设备并取消未完成命令，本地绑定和 pending batch 不能随账号自动迁移。

### 8.9 默认聚合全部授权团队

用户登录后默认看到全部授权团队，而不是固定在一个活动团队。团队筛选只改变展示范围，不改变身份或授权。

这减少了多团队成员反复切换和重复登录的成本，也要求所有查询、保存视图、WIP 和写操作都正确携带团队或项目上下文。

### 8.10 显式确认优先于自动修复

覆盖服务端、替换绑定、撤销设备和处理文件冲突都要求明确确认，系统不会自动 merge、checkout、reset 或猜测用户意图。

这会增加少量操作步骤，但能保留可恢复状态和审计，避免不可逆的数据覆盖。

### 8.11 历史替代关系

以下内容属于演进背景，不是当前功能：

| 历史方案 | 当前事实 |
| --- | --- |
| 服务端 clone/fetch 项目 Git，或维护稀疏检出与实时覆盖层 | 服务端不访问项目 Git；客户端上传 `.trellis/tasks/**` 快照 |
| Web 在服务端工作副本中直接创建、修改、commit 和 push 任务 | Web 向目标用户唯一在线客户端 Agent 下发命令，本地执行并同步 |
| Node SEA sidecar 与独立 `trellis-agent.exe` | Rust 单 EXE 进程内 Agent，无 sidecar |
| 绿色包携带 sidecar 和内置常驻 Node runtime | 单 EXE；首次启动环境门按需准备 Node 与 Trellis CLI |
| 登录时固定一个活动团队 | 默认聚合全部授权团队，按团队筛选 |
| Team 模式加载插件 | team 模式插件接口明确返回禁用；插件仅用于 standalone |

## 9. 状态、错误与异常交互

### 9.1 主要状态

| 状态域 | 用户可见状态 | 系统行为 |
| --- | --- | --- |
| standalone 扫描 | 正在更新、显示缓存、监听中、刷新排队 | 后台扫描与排队，不让最后一次变化丢失 |
| team 任务空间 | 当前、索引中/陈旧、需要修复、停用 | 正常读取与任务级编辑以“当前”为基线；非当前状态显示原因，停用时拒绝接入和写入 |
| 本地关联 | 未关联、正在同步、同步正常、待补传、待确认归属、分支暂停、同步异常、解绑待确认 | 项目栏显示原因和可用操作 |
| Web 操作项 | 等待投递、等待执行、执行中、成功、失败、取消 | 失败可重试或取消，成功后正式任务才出现 |
| 插件 | 运行、启动中、停止、错误、禁用、反复崩溃、不兼容 | 提供启停和日志，不兼容时禁止启动 |
| 客户端环境 | 检查中、下载/安装步骤、已就绪、失败 | 失败停留在环境页并显示中文原因 |
| 首次推送 | 等待提交、等待推送、分支缺失、远端领先、分叉、无法确认、已就绪 | 网络不可达不等于未推送 |

### 9.2 主要异常

| 异常 | 用户反馈 | 处理方式 |
| --- | --- | --- |
| 目标 Agent 离线 | 显示用户、项目和分支，并提示打开客户端或关联项目 | 在创建操作项前拒绝，不生成临时任务 |
| 项目无写权限 | 说明当前角色和所需权限 | 只读保留查看能力 |
| 项目或分支停用 | 显示已停用的项目或分支及当前不可用原因 | 拒绝接入和写操作，不伪造可用状态 |
| 绑定分支不匹配 | 显示实际分支、绑定分支和切回建议 | 暂停同步，不自动切换分支 |
| 任务归属不明确 | 显示待归属数量和批量/逐项入口 | 在确认前不上传该任务 |
| 文件基线冲突 | 显示最后修改人、设备、时间和冲突 ID | 要求选择处理动作，不覆盖 |
| 命令等待索引 | 显示命令已执行但投影尚未追上 | 保留可重试状态，不提前标成功 |
| 网络中断 | 保留 pending batch 和 cursor | 恢复后复用原批次重试 |
| 运行环境安装失败 | 显示具体步骤和错误 | 不进入登录页，提供重试 |
| 插件不兼容或崩溃 | 显示兼容性原因、错误和重启次数 | 禁止启动不兼容插件，隔离故障 |

### 9.3 错误信息质量

- 先说明业务原因，再提供下一步入口。
- 不要求普通用户理解 HTTP 状态码、SHA 摘要或数据库 revision。
- 技术信息只在展开详情或日志中出现。
- 不把“暂时无法确认”显示成确定失败。
- 任何可能覆盖数据或暴露权限边界的操作，都要在服务端再次校验。

## 10. 非功能要求

### 10.1 安全与隔离

- team 模式所有业务数据访问必须经过账号、团队、项目角色和项目同步状态校验。
- 未授权或不可见数据按不存在处理，批量请求中的显式越权 ID 整体拒绝。
- 非可信网络必须使用 HTTPS；反向代理必须正确传递安全协议信息。
- 项目 Git 凭据不进入 Team 服务端。
- 设备凭证由 DPAPI 保护；会话 Cookie 使用 HttpOnly。
- 日志、审计和 API 响应不得泄露密码、Token、Cookie、配对码、私钥、任务正文或本地仓库路径。
- standalone 无鉴权，只能部署在本机或可信网络。
- 插件不是沙箱，只允许在受信环境和专用账号下启用。

### 10.2 数据一致性与恢复

- 多文件任务更新按完整任务目录和原子批次处理，不允许半个任务落盘。
- 文件级 CAS 防止后写覆盖先写。
- 删除使用墓碑；活动到归档的移动作为同一批次完成。
- 客户端在目录完整应用成功后才推进 cursor。
- 服务端保留当前任务快照、冲突双方备份、文件审计和定期数据库快照，不建设完整任务历史版本浏览器。
- 项目历史版本由客户端 Git 负责。
- Team 数据库使用 SQLite WAL；维护、升级和恢复前应停止服务并同时处理主库、WAL 和 SHM。
- Team runtime 每 24 小时创建数据库快照并保留最近 7 份。
- 服务端日志按 `5 MiB × 5` 轮转，总量上限约 25 MiB；强制终止时未刷新的尾部日志可能丢失。

### 10.3 性能和容量基线

当前 Team Board 的已验证容量基线为：

| 指标 | 基线 |
| --- | --- |
| 账号数 | 400 |
| 在线 Web 用户 | 200 |
| 项目数 | 100 |
| 当前任务快照 | 10,000 |
| 在线 Agent 连接 | 400 |

这是单实例 Node 进程、SQLite 和内存 SSE 的容量基线。超过基线或需要多实例高可用时，必须重新设计共享数据库、SSE 广播和任务空间队列，不能把当前实现描述为高可用集群。

客户端验收目标包括：正常网络下，一个客户端更新任务后，另一客户端 P95 在 3 秒内同步。standalone 自动刷新会重新扫描全部白名单仓库，以正确计算跨仓库父子关系；每次有效变化后的后台扫描通常需要数秒，期间显示缓存并排队后续变化。

### 10.4 同步规模和边界

- 单任务文件上限 1 MiB。
- 单批正文上限 64 MiB，最多 1024 个文件。
- JSON 请求和大型 Agent 响应的运输硬上限为 96 MiB。
- 同一 Agent/taskSpace 的上传受速率限制，客户端串行发送并遵守等待间隔。
- 路径必须是 `.trellis/tasks` 下的合法任务目录或归档任务目录；拒绝越界、符号链接和非 UTF-8 内容。

### 10.5 可观测性和可运维性

- 服务端结构化记录扫描、同步、冲突、命令、备份和错误。
- 项目审计和系统审计按追加事件保存。
- 插件提供状态、进程信息、错误、重启次数和日志。
- Windows 控制窗口将差异、冲突、归属和同步错误转为用户可处理的事件。
- 运维手册提供升级、回滚、备份、SSE 代理、容量和故障处置步骤。

### 10.6 兼容性

- 服务端需要 Node.js 24 或更高版本。
- Windows 客户端当前支持 Windows 10/11 x64，并要求 WebView2 Evergreen Runtime。
- 当前明确不提供 macOS Agent 或 Linux Agent。
- standalone 文件监听当前面向 Windows/macOS 本机运行；Linux 或网络盘若不支持递归监听，需要替代监听方式，人工刷新可作为回退。

## 11. 非目标与当前限制

### 11.1 明确非目标

- 不提供评论。
- 不提供通知。
- 不提供审批流。
- 不提供 SSO。
- 不提供多实例高可用。
- 不提供 macOS Agent 或 Linux Agent。
- 不提供公开注册。
- 不提供 Team 模式插件运行。
- 不让 Team 服务端 clone、fetch、commit、push 或保存项目 Git 凭据。
- 不提供完整任务历史版本浏览或任意版本回滚。
- 不自动 merge Markdown、JSON 或 JSONL。
- 不自动 commit 或 push 用户项目初始化文件。
- 不允许远程网页访问任意本地路径。
- 不把 standalone 无鉴权服务作为公网部署方案。
- 不把归档任务重新计入当前执行队列。
- 不根据文件时间补造未记录的流程历史。

### 11.2 必须提前理解的限制

- team 任务创建和改派依赖目标账号唯一在线 Agent。
- 新设备登录会撤销旧设备，旧设备未完成命令会取消。
- 一个普通工作目录只能绑定一个分支；多分支必须使用多个 worktree。
- 服务端只拥有任务快照，不拥有项目源码、spec、脚本或 workspace。
- 首次接入和冲突处理需要用户确认，不能期待全自动合并。
- 未授权和停用数据可能显示为“不存在”，这是权限设计而非数据丢失。
- 当前容量基线不适用于多实例或更大组织规模。

## 12. 验收口径与证据索引

### 12.1 产品验收口径

Trellis Board 当前产品基线满足以下条件时视为可用：

1. 用户能从全部授权团队和项目中发现任务，并按团队、项目、分支、负责人、优先级、阶段和阻断状态筛选。
2. 任务卡和详情能显示 13 阶段、阶段来源、条件缺口、依赖、计划字段和任务产物，且不伪造未记录历史。
3. 个人执行视图能给出推荐任务、注意力队列、WIP 和流动风险，同时不阻止正常推进。
4. standalone 写操作只作用于白名单仓库；team 写操作只通过有权限的在线 Agent 落盘。
5. 创建、改派、接受和失败重试具有明确状态，正式任务和正式负责人只在真实同步后出现。
6. 同一远端不同分支拥有独立任务空间，绑定分支、任务归属和真实 Git 分支不一致时暂停同步。
7. 两客户端并发修改同一文件时不会静默覆盖；冲突差异、备份、覆盖和审计可操作。
8. 首次接入支持不接入、仅同步安全项和逐项处理差异，所有选择结果可恢复且不产生半个任务。
9. 账号、团队、项目角色、设备和审计按服务端权限隔离，未授权数据不会通过前端绕过。
10. Windows 客户端具备环境门、本地登录、单 Agent、Tasks-only 同步、分支门禁、冲突控制和单 EXE 分发。
11. Team 模式明确禁用插件；standalone 插件运行具备状态、日志和故障隔离。
12. 文档描述与当前源码、README 和运维边界一致，历史替代方案没有被写成现状。

本文没有定义未经业务确认的转化率、留存率或组织级 KPI。当前可验证的成功标准是上述产品行为与边界是否按现有源码闭环成立。
